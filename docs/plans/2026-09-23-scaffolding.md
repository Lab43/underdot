# Scaffolding

## Goal

Stand up the repository the rebuild happens in: the `underdot` package at the root with plugin packages as npm workspaces, TypeScript per the toolchain convention, the Node floor, tests with enforced full coverage, a type-aware linter, a pre-commit hook, GitHub Actions, and the q extension payload the package ships to sites. After this plan every later step adds code to a repo whose checks already run, and the first site-facing convention is published.

## Context

### What the repo holds today

- `package.json:1-14` names the package `underdot` at version `1.0.5` with `@lab43/q` as its only dependency, no `type`, no `engines`, no scripts, no `exports`, no `files`, no `workspaces`. Every field this plan adds is new, and the version is a v1 number that a plugin cannot peer-depend on.
- No `src/`, no `tsconfig*.json`, no lint config, no `.github/`, no `q-extension/`, no `docs/plans/` before this plan. Nothing here replaces an existing path, so no phase is a cutover.
- `.gitignore:1-4` ignores `node_modules`, `.idea`, the local Claude settings, and worktrees. Build output and TypeScript's build-info files are not ignored yet.
- `.claude-plugin/marketplace.json:5` registers only q's plugin. The payload this plan ships carries conventions and no plugin, so the marketplace does not change (source: @lab43/q conventions/extensions.md, Layout).
- `CLAUDE.md:17-33` indexes q's docs and this project's own. The payload needs a group of its own there, headed by the package name and its `q.description`, read from the working tree (source: @lab43/q conventions/extensions.md, Authoring).
- `README.md:20` is checklist step 1, which this plan delivers whole. `README.md:32` commits the package to shipping a q extension whose payload grows one step at a time.

### What the conventions fix

- `docs/conventions/toolchain.md`, Node floor: `engines` pins the oldest release with everything the code relies on, and nothing below it gets a shim. Decision 2 picks the release.
- `docs/conventions/toolchain.md`, Modules: every package is an ES module compiled with `module` and `moduleResolution` at `NodeNext`, relative imports carry `.ts`, and `rewriteRelativeImportExtensions` rewrites them on emit. Decision 4 sets the compiler options that honor this.
- `docs/conventions/toolchain.md`, TypeScript: all code is TypeScript compiled with `tsc`, with types published from the same build. Decision 4 and Decision 3 honor this, and Decision 6 records the one file that cannot.
- `@lab43/q conventions/extensions.md`, Identity, Layout, Description, and Pinning: an extension carries the `q-extension` keyword, ships a `q-extension/` directory named in `files`, states its territory in `q.description`, and pins `@lab43/q` exactly at the root. The pin is already exact at `package.json:12`. Phase 4 supplies the rest.
- `@lab43/q conventions/extensions.md`, Which rules ship: payload docs address consumers only and never name this repo, its practices, or its layout. The payload doc in Phase 4 therefore carries its rationale inline and cites no spec by path.
- `@lab43/q conventions/documentation.md`, Taxonomy: the briefing indexes every conventions doc, this repo's own payload included, grouped by where the docs come from. Phase 4 adds the group.
- `@lab43/q conventions/principles.md`, Prefer the strongest enforcement rung: a rule goes to lint before it goes to prose. Decision 5 puts the dependency and floor rules on lint, and Decision 9 keeps convention prose to what lint cannot express.

### What the specs fix for the payload doc

- `docs/specs/configuration.md`, The configuration file: the configuration is `underdot.config.ts` or `underdot.config.js`, a TypeScript one is checked against the package's exported types, and it runs on the runtime's type stripping so it uses only syntax the runtime erases. The payload doc in Phase 4 states a site's side of these commitments as rules.

### Which release lines the toolchain can stand on

- Node's test runner matches `**/*.test.ts` by default from 22, accepts glob arguments, and reports coverage behind `--experimental-test-coverage`, still at stability 1. `--test-coverage-include` and `--test-coverage-exclude` arrived in 22.5.0. The `--test-coverage-lines`, `--test-coverage-branches`, and `--test-coverage-functions` thresholds arrived in 22.8.0 and make the run exit 1 when unmet. `/* node:coverage ignore next */` excludes lines.
- Node 22 is in maintenance until 2027-04-30. Node 24 is the active LTS until 2026-10-20, then maintained until 2028-04-30. Node 26 becomes LTS on 2026-10-28.
- TypeScript 7.0.2 is the latest `typescript` release and ships no programmatic API. TypeScript 6.0.3 is the last release of the JavaScript compiler. `typescript-eslint` 8.70.1 declares `typescript >=4.8.4 <6.1.0` as its peer range.
- ESLint is at 10.11.0. `eslint-plugin-import` 2.32.0 declares ESLint peers up to 9 only. `eslint-plugin-import-x` 4.17.1, `@stylistic/eslint-plugin` 5.10.0, `eslint-plugin-n` 18.3.0, and `@eslint-community/eslint-plugin-eslint-comments` 4.8.1 all declare ESLint 10. ESLint loads a TypeScript config file natively only behind the `unstable_native_nodejs_ts_config` flag.
- `actions/checkout` is at v7.0.1 and `actions/setup-node` at v7.0.0. `@types/node` at major 22 is 22.20.4. `husky` is at 9.1.7 and `lint-staged` at 17.5.1.
- lab43 owns the unscoped `underdot-*` plugin names on npm. No `@underdot` scope has published anything.

### Whether the pieces compose without a build step

Proven in a scratch build run 2026-09-23 outside the repo, with TypeScript 6.0.3 and 7.0.2, `@types/node` 22, Node 24.19.0, and Node 22.18.0. They bear on Decisions 4, 5, and 7.

- `tsc` accepts `module: nodenext`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, and `rewriteRelativeImportExtensions` together, emits declarations, rewrites a `./index.ts` import to `./index.js`, and rejects an `enum` under `erasableSyntaxOnly`.
- `npm install` accepts a `workspaces` glob that matches nothing. A workspace declaring `"underdot": "file:../.."` in `devDependencies` gets `node_modules/underdot` linked to the repo root.
- With `exports` carrying a `development` condition that points at `src/index.ts`, `node --conditions=development --test` runs a workspace's tests against the root package's source with no `dist` present, and `tsc --noEmit` with `customConditions: ["development"]` type-checks both packages the same way. Type stripping applies because the symlink resolves to the real path, which is not under `node_modules`. Without the condition the same import resolves to `dist`.
- With `customConditions` still set, a composite plugin project that references the core's build config builds through a root solution file with `tsc -b`: core emits first, the plugin's declaration file imports `underdot` by name, and a consumer without the condition runs the plugin from `dist`.
- Coverage thresholds at 100 on lines, branches, and functions fail an uncovered function with exit 1 and pass a fully covered tree, on both Node lines. An empty module scores 100. A `node:coverage ignore next` comment restores the pass.

## Decisions

1. **The core package sits at the repository root, and plugins are workspaces under `plugins/`, each published as `underdot-<name>`.** The payload of a q extension lives at the root of the package that ships it, so the package that ships it is the repo root, and the README fixes the core there. `plugins/` names what the directory holds, since the one package that is not a plugin is not in it. The unscoped `underdot-` prefix is what lab43 already owns on npm, and a v1 site upgrading a plugin takes v2 as a major bump. Each plugin's plan picks its own name. Rejected: `packages/` for the workspaces directory, the conventional name, because it would hold every package but the main one. Rejected: an `@underdot` scope, which needs an npm organization created first and leaves the owned names stranded at v1.

2. **The Node floor is `>=22.18.0`, `@types/node` is pinned to major 22, and CI runs the floor, the latest 22, 24, and 26.** 22.18.0 is the oldest release that strips types without a flag or a warning, loads ES modules through `require()`, and runs `.ts` tests with thresholds and include filters, which is everything the code relies on. The types pin keeps the code from leaning on an API newer than the floor. The matrix proves the floor is real rather than nominal. Rejected: `>=24.0.0`, which skips a line with under a year of life left when v2 ships but deviates from the convention's rule with no shim to show for it. *(deviation: "the latest 22" was dropped in review, which shares its major with the floor and could only catch a regression in a later 22 patch release. CI runs the floor, 24, and 26.)*

3. **TypeScript is pinned at `~6.0.3` until `typescript-eslint` supports TypeScript 7.** The linter's type-aware rules run on the compiler's programmatic API, and 7.0 ships none. The language, the errors, and the emitted JavaScript are the same in both, so the move to 7 is a version bump once the peer range admits it. Rejected: TypeScript 7 for the build with 6 installed under an alias for lint, two compilers checking one repo. *(deviation: "until `typescript-eslint` supports TypeScript 7" was reframed in review as a standing constraint, keeping `typescript` inside `typescript-eslint`'s peer range, and moved the exit condition out of the doc into issue #27.)*

4. **One `tsconfig.base.json` at the root carries the compiler options. The root `tsconfig.json` checks every package's source and tests with `noEmit`. Each package has a `tsconfig.build.json` that emits its `src/` minus tests as a composite project, a plugin's referencing the core's. A root `tsconfig.solution.json` references every build config, and `tsc -b` on it builds them in dependency order.** The convention's options are `module` and `moduleResolution` at `nodenext`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, and `rewriteRelativeImportExtensions`. Added on top: `strict`, `noUncheckedIndexedAccess`, `noEmitOnError`, `skipLibCheck`, `declaration`, `types: ["node"]`, and `customConditions: ["development"]` (see: Decision 7). `erasableSyntaxOnly` is the compile-time guarantee that the source runs under the runtime's type stripping. `noUncheckedIndexedAccess` is there because a build engine indexes maps by path and URL and every miss must be handled. Rejected: one config per package that both checks and emits, which either ships compiled tests or leaves them unchecked. Rejected: a `tsconfig.json` per package for checking, since the root config reaches every package's source through one include list and one run.

5. **ESLint 10 with `typescript-eslint`'s `strictTypeChecked` and `stylisticTypeChecked` presets, `@stylistic/eslint-plugin` for layout, `eslint-plugin-import-x` for import order, `eslint-plugin-n` for undeclared imports and the Node floor, and `@eslint-community/eslint-plugin-eslint-comments` so every disable states a reason. No formatter.** Layout is enforced as lint rules that report and never rewrite unless `--fix` is asked for, which is the behavior wanted. `n/no-extraneous-import` fails an import of a package the importing workspace does not declare, which is what makes npm's hoisted `node_modules` safe for separately published plugins. `n/no-unsupported-features/node-builtins` and `es-syntax` fail code using an API newer than `engines`, putting the floor on the lint rung. `lint` runs with `--max-warnings 0` so a warning-level preset rule still fails. Rejected: Prettier, which reprints whole files. Rejected: Biome and oxlint, each an order of magnitude less used than ESLint and either partial on type-aware rules or pre-1.0 on formatting. Rejected: `eslint-plugin-import`, whose peer range stops at ESLint 9.

6. **The ESLint config is `eslint.config.js`, the one JavaScript file in the repo.** ESLint loads a `.ts` config only behind an unstable flag. The file carries an exception marker naming the toolchain convention's TypeScript section with this reason (source: @lab43/q conventions/documentation.md, Markers).

7. **Every package's `exports` carries a `development` condition pointing at its source, and tests and type checks run with that condition, so neither needs a build.** A plugin imports core as `underdot`, and without the condition that resolves to `dist`, making every test run wait on a compile of every package below it. With it, `node --conditions=development` and `customConditions` reach `src/` directly, coverage measures the same file identity the tests exercise, and `tsc -b` is for publishing only. The `development` entry comes before `types` in every `exports` map. TypeScript matches conditions in object order and always carries `types`, so with `types` first it would resolve to `dist` even under `customConditions` and the no-build type check would fail. Node never matches `types`, so the order changes nothing at runtime. A `types`-first checker such as publint would flag the order, and the repo runs none. Consumers never pass the condition and get `dist`. Rejected: building before every test run. Rejected: emitting tests into `dist` and filtering them out of the tarball.

8. **Tests are `node:test` files colocated as `*.test.ts` beside the code, and every test run reports coverage with lines, branches, and functions each held at 100.** The runtime ships the runner, so it costs no dependency and no transform, and the tests exercise the exact source the runtime executes. There is one `test` script and it always measures, because a threshold that only runs in CI is one people meet after the push. The run covers `src/**` and `plugins/*/src/**` and excludes test files from the measure. A line that cannot run under test carries a `node:coverage ignore next` comment stating why. A whole file is excluded only through the test script's exclude list, so every exclusion is visible in one place. Rejected: Jest, which needs a transform to read TypeScript, a loader the convention forbids. Rejected: Vitest, which runs a transformed copy of the code through esbuild.

9. **The conventions record only what lint cannot hold.** Two entries go to `docs/conventions/toolchain.md`: the TypeScript major pin and its exit condition, and the `development` condition every package's `exports` must carry. *(deviation: "its exit condition" is tracked in issue #27 rather than the doc, per Decision 3.)* A new `docs/conventions/testing.md` carries the coverage rule and its escape hatch. Everything the ESLint config enforces stays out of prose (source: @lab43/q conventions/conventions.md, Documentation is the last rung).

10. **CI is one workflow with three jobs: `lint`, `typecheck`, and `test`, the last a matrix over Node versions.** Each is its own check on the PR, so a failure names its cause without opening a log. Lint and typecheck run once, on 24, because their result does not depend on the runtime. The version is one the matrix already carries and moves when the matrix does. The workflow runs on pull requests, on pushes to `v2`, and by hand. Rejected: one job running `npm run check`, which reports one red check for three kinds of failure.

11. **A husky pre-commit hook runs `lint-staged`, which lints the staged files, and then the type check.** Both finish in seconds on this repo and catch what CI would otherwise report ten minutes later. Tests stay out of the hook, since the coverage run grows with the code and CI holds that gate.

12. **The version becomes `2.0.0-alpha.0`.** A plugin's peer dependency on `underdot` needs a v2 version to name, and `1.0.5` is what the published v1 is. Publishing is out of scope (see: Out of scope), so the version changes nothing on the registry.

13. **`src/index.ts` is an empty module with one test until step 2 gives it an export.** The scaffold ships the toolchain and nothing speculative. The test proves the runner strips types, matches the glob, and measures coverage. An empty module scores 100 on every measure, as the scratch build showed.

14. **The payload's first doc is `q-extension/conventions/configuration.md`, and `q.description` reads "Rules for writing a site built on Underdot: its configuration, source tree, templates, and plugins."** The doc carries two rules with their rationale inline: write the configuration as `underdot.config.ts`, because the package publishes the configuration's type and only a TypeScript file is checked against it in the editor, and keep it to syntax the runtime erases, because it runs on Node's type stripping with no compile step. Both premises are commitments the code does not honor yet: the exported type is step 2's work and the loader is too. The doc runs ahead of them by design. The payload reaches a site only when the package publishes, after the rebuild ships, and the README binds each step to write its site-facing rules as it ships rather than hold them for a consumer that cannot exist yet. The description names the territory the payload will cover as steps add to it, not the package's shape (source: @lab43/q conventions/extensions.md, Description).

15. **Delivery is a single PR.** The four phases are review units, each leaving the repo green, but none is worth reviewing apart from the others: the lint config is meaningless without the TypeScript layout it checks, CI without the scripts it runs, and the payload without the manifest that ships it. The change is configuration and one placeholder module, well within a scope one review holds, and a stack of four PRs of that size would spend more on mechanics than it returns in review. Rejected: stacked PRs, one per phase.

## Out of scope

- **Publishing to npm.** Declined. No step of the checklist publishes, and the version bump in Decision 12 exists only so plugins can peer-depend on it. `prepack` runs the build so a dry-run `npm pack` proves the tarball, which is as far as this plan goes.
- **A plugin package.** Declined. The workspaces glob and the linking mechanism ship here, proven by a throwaway workspace in Verification. The first real plugin arrives with step 4.
- **The `underdot` command and the exported configuration type.** Deferred to step 2, which owns configuration loading. The payload doc of Decision 14 states rules that rest on that type before it exists, which Decision 14 accounts for.
- **Linting the Markdown docs.** Declined. The docs are held to the writing rules by review, and a Markdown linter adds a tool for a surface the code checks never touch.
- **A driving manual.** Deferred to step 8, the dev server, which is the first thing that can be driven.
