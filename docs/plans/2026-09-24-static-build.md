# Static build

## Goal

Deliver checklist plan 2.2: the exported `build` function that takes a configuration, walks the source root, drops the excluded files, classifies every remaining file as a static file under the underscore and dotfile rules, plans each file's output path with the uniqueness check, and writes the destination so it holds exactly the planned files. After this plan a site with no plugins builds its static files from a script, and the command of plan 2.3 has a function to call.

- `docs/specs/source-tree.md`, Underscore prefix: an underscore-prefixed file or directory is never written, files inside an underscore-prefixed directory are not classified, and an underscore-prefixed static file still passes through file handlers. Decisions 5 and 6.
- `docs/specs/source-tree.md`, Dotfiles: a dotfile is classified like any other file. Decisions 3 and 4.
- `docs/specs/source-tree.md`, Output paths and Output paths are unique: a static file is written at its source path, and two sources writing one destination path are a build error naming both. Decision 6.
- `docs/specs/build.md`, Determinism: the same source, configuration, and plugins produce a byte-identical destination on every run and every machine, and nothing depends on the order files were read. Decisions 2 and 7.
- `docs/specs/build.md`, Order of work: classification completes before the destination is written. The phases between them have no units yet. Decision 1 orders `build` this way.
- `docs/specs/build.md`, Destination: after a successful build the destination contains exactly the files the build produced, and every other file in it is removed. Placement is the configuration's check, already made at `src/resolve-configuration.ts:44-57`. Decision 7.

- `docs/specs/build.md`, Errors: a build stops at the first unit that fails, units already running finish or are abandoned, nothing further starts, and a failed build leaves whatever it had written. Decisions 4, 7, and 8.

### The runtime lists the tree but cannot match it

Proven 2026-09-24 in a scratch run on Node 24.19.0, outside the repo, and by linting a probe file in the repo under the `n/no-unsupported-features/node-builtins` rule against the floor of `>=22.18.0`.

- `readdir` from `node:fs/promises` with `recursive` and `withFileTypes` lists every entry under a root, dotfiles and underscore-prefixed paths included. Each entry carries `parentPath` and `name`, and answers `isFile()`, `isDirectory()`, or neither. A symlink answers neither and is not descended, whether it points at a file or at a directory. The synchronous `readdirSync` differs: it descends a symlinked directory, a self-referencing one included, so the walk uses the promise form and never the synchronous one. The call passes the floor lint, as do `stat`, `mkdir`, `rm`, and `copyFile`. Decision 4 builds the walk on it.
- `path.matchesGlob` fails the floor lint: it is stable from Node 22.20.0 and 24.8.0, and the `n` rule reports it against `>=22.18.0`. `fs.promises.glob` fails it too, and its `**/*` lists no dotfile. Both share one behavior that rules them out regardless: `**` never crosses a dot-directory, so `**/.DS_Store` misses `.well-known/.DS_Store`, which the spec's "everywhere" forbids. Decision 3 rests on this.
- `minimatch` 10.2.6 with `{ dot: true }` matches `**/.DS_Store` against `.DS_Store`, `a/.DS_Store`, `.well-known/.DS_Store`, and `.a/.b/.DS_Store`, matches `**/*.draft` against `.hidden.draft` and `.hidden/h.draft`, matches `drafts/**` against `drafts/x/y.md`, and does not match `a` or `*` against `a/b.txt`. `picomatch` 4.0.7 gave the same answer on every case. minimatch had 519.7 million downloads in the week ending 2026-09-21 and picomatch 361.1 million, read from the npm downloads API. minimatch ships an ESM entry with types under its `import` condition, read from its `exports` map. ## Decisions

1. **`build(configuration: Configuration, projectDirectory = process.cwd()): Promise<void>` is the export. It resolves the configuration with `resolveConfiguration`, walks the source, drops the excluded files, classifies, plans the outputs, and writes the destination, in that order.** The spec says the function takes a configuration, and the configuration's paths are relative to the project directory, which for a script is the directory it runs in. Resolving inside `build` puts the unknown-setting and placement errors before any work starts whoever calls it, and keeps the command of plan 2.3 a thin layer over the same call. The parameter is typed `Configuration` because that is the site-facing type, and `resolveConfiguration` still checks the value at runtime because a JavaScript caller can pass anything. Nothing needs the outputs yet, so the promise resolves to nothing. Rejected: taking a `ResolvedConfiguration`, which makes every script call the resolver first and exposes a type the spec does not name. Rejected: an options object in place of the directory, which is a container for settings this plan has one of.

2. **Every path under the source root is held relative to it with forward slashes, and the walk's listing is sorted with the default sort before anything reads it.** The same string is a glob subject in this plan and a URL in step 3, and both use forward slashes. Sorting by code unit is the same on every machine, where a locale-aware sort is not, and a sorted listing is what keeps the collision error's two names and every later ordered step free of traversal order. Rejected: platform-native separators converted at the two points that need slashes, which spreads the conversion to every later step that adds a third.

3. **Exclude patterns are matched with `minimatch` in `{ dot: true }` mode against each file's relative path, and a pattern names files only. Phase 1 amends the spec's Excluded files section to say so.** Node's own matcher is off the table under the floor, and its dot behavior breaks the spec's "everywhere" in any case. Of the two packages that answer every probed case alike, minimatch is the more downloaded and is the engine Node vendors for its own glob functions, so a pattern means the same thing in a site's configuration as in the runtime. Dot mode is what the source tree's Dotfiles rule requires: a dotfile is an ordinary file there, so a pattern that skipped it silently would hide a file the author meant to name. Matching files only means `drafts/**` hides a directory's files and `drafts` hides nothing, which the amendment states so an author who writes the bare name learns why it did nothing. The rule is a commitment a site relies on when writing a pattern, and the user approved the amendment. Rejected: picomatch, fewer downloads and no bundled types. Rejected: raising the floor to 22.20 for the built-in. The floor lint reports the function as supported from 24.8.0 and backported to `^22.20.0`, so a plain `>=22.20.0` range still fails it, and the built-in misses dotfiles regardless.

4. **The walk is `readdir` with `recursive` and `withFileTypes`. A source root that does not exist, or is not a directory, fails the build naming it. An entry that is neither a regular file nor a directory fails the build naming it.** The recursive listing is stable on the floor and lists dotfiles, which the spec classifies like any other file. A symlink, a socket, or a device is something the build cannot classify, and an entry that vanished from the output silently would be found by the author from the missing file, so the build fails and says what it met. The user chose this over following symlinks. Rejected: skipping such an entry, which is the silent misfire. Rejected: following symlinks, which is machinery no site in scope needs.

5. **Classification takes the included paths and yields a `StaticFile` value per classified file: `{ path, private }`, with `private` true when the file's own name starts with an underscore. A path with an underscore-prefixed directory segment yields nothing.** No renderer is registered until step 3, so every classified file is static, and the function takes no renderer set until that step gives it one. The value holds what the spec makes true of the file by its path alone. A private static file is classified because the spec has it pass through file handlers, which step 5 adds, and it is never written, which the output planner enforces. A file inside an underscore-prefixed directory is not classified at all, so it is dropped here rather than carried as a third state. Rejected: dropping underscore-prefixed files at classification, which would have step 5 reclassify them for handlers. Rejected: an empty renderer set as a parameter now, which is a parameter nothing passes. *(deviation: at the local gate the user chose to return the record `SourceFiles { staticFiles: StaticFile[] }` rather than the bare array, so that step 3 adds `pages` and `templates` as fields instead of changing the signature that `build` and the output planner read. The planner takes the record.)*

6. **The output planner turns static files into `Output` values `{ source, output }`, skipping private files, sorts them by output path, and fails when two sources plan one output path, naming both.** In this plan every output path equals its source path, so no collision can arise, and the check is proven on values with a synthetic collision. It exists now because plan 2.2 owns the uniqueness rule and later steps add the sources that collide: pages in step 3 and renamed handler outputs in step 5. Both feed this planner. The error names the two sources in sorted order, so the same collision reports the same way on every machine.

7. **The destination is cleaned before it is written, against the planned set, and the outputs are then copied with `copyFile` through the unit runner (see: Decision 8).** Cleaning removes every entry that is neither a planned file nor a directory on the way to one: a stale file, a stale directory with everything under it, a file standing where a directory is needed, a directory standing where a file is needed, and anything that is not a regular file at a planned path. A file being replaced stays until its copy overwrites it, so a served destination never loses a page it is about to get back. After the copies, the destination holds exactly the planned files. Rejected: deleting the destination whole before writing, which drops every unchanged file from a served destination for the length of the build. Rejected: writing first and cleaning after, which cannot remove a directory standing where a file must go.

8. **Units run through one runner, `runUnits`, which keeps at most 10 in flight, starts no unit after one fails, waits for the units in flight to settle, and rejects with the first error.** The spec has the build choose the limit and keeps it out of the configuration, and no measurement is going to pick the number, so the code names one and a later step changes it in one place if a plugin's units prove it wrong. The runner is a function from a list of tasks to a promise, so its rules are proven on values with fake units, and every later step hands its units to the same runner: handlers, renders, producers. Letting the units in flight settle before rejecting is what keeps their rejections observed, since an unobserved rejection terminates the process. Rejected: deferring the runner to step 9, where image derivatives would give a limit something to measure against. No measurement was going to pick the number, and a default now serves every step between.

9. **Whole-site fixtures live under `test/fixtures/build/<case>/`, each a `source/` tree with a configuration file written as the payload rule prescribes, and every fixture's destination is the default `build`, ignored by git. The build's tests are one file, `src/build.test.ts`, and it is the only test that writes to a fixture.** The test runner runs each test file in its own process at once, so two files writing one destination would race. Value functions get value tests. The walk reads a fixture's source and writes nothing. The cleaning test plants a stale file, a stale directory, a file where a directory is needed, and a directory where a file is needed in the destination before building, because a stale entry cannot be committed into a directory the build deletes. The destinations are ignored by lint as well as by git, so a fixture may hold whatever a site holds without its copies being linted. An error case that needs no tree of its own, such as a missing source root or a placement error, passes a value against an existing fixture's directory. Rejected: a destination outside the fixture directory, which the placement rules forbid. *(deviation: at the local gate the user chose a flat fixture root, because every fixture is a project directory and a subject level named nothing. The sites live at `test/fixtures/defaults/`, `test/fixtures/excluding/`, and `test/fixtures/symlinked/`, the configuration loader's cases moved up from `test/fixtures/configuration/` beside them, and the ignored destination pattern is `test/fixtures/*/build/`. The testing convention's Fixtures section carries the rule.)* *(deviation: the user then ruled that a fixture is never written, because a shared fixture root with one permitted writer per destination invites the race it warns about. A test that builds copies its fixture to a temporary directory with `test/helpers/copy-fixture.ts` and builds the copy, so no destination exists under `test/fixtures/` and the ignore entries came out. `write-destination.ts` gained its own test on that footing, and the cleaning case moved there from `build.test.ts`.)*

10. **Delivery is a single PR.** The change is seven small modules, six test files, three fixtures, one dependency, and two doc edits, which one review holds.

## Out of scope

- **Pages, templates, and the renderer set.** Deferred to step 3, which registers renderers and gives classification its parameter.
- **File handlers and renamed outputs.** Deferred to step 5. Private static files are classified now and handled then.
- **The loader's return shape, and how a failure prints.** Deferred to plan 2.3, the loader's first caller. `build` takes a `Configuration`, so the command either has the loader return the raw export with its directory, or reaches the resolved form another way. Both are the command's call.
- **Following symlinks.** Declined (see: Decision 4).
- **A payload convention on exclude patterns.** Declined. The spec amendment carries the rule, and a convention restating it would be duplication.
- **A migration guide entry for the pattern rule.** Declined. v1 had no exclude setting, so no site has a pattern to rewrite, and the guide leaves out behavior that needs no edit.
