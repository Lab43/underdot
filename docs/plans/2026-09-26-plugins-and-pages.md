# Plugins and pages

## Goal

Deliver checklist plan 3.1: the exported plugin type with a name and renderers, the `plugins` setting, the errors for duplicate plugin names and duplicate extensions, classification of pages and templates by the registered extensions, frontmatter with its reserved keys, page output paths and URLs, and output uniqueness across pages and static files, proven with a fixture renderer. After this plan a site lists its plugins in the configuration, every page and template is classified, read, and checked, a page no longer reaches the destination as a static copy, and plan 3.2 has page and template values to resolve and render.

### What the YAML parser must do

Proven 2026-09-26 in a scratch run on Node 24.19.0, outside the repo, with `js-yaml` 5.4.2 and `yaml` 2.9.1 installed from the registry. Each bears on Decision 7.

- Neither parser turns an unquoted date into a date value by default. Both default to the YAML 1.2 core schema, where `2024-01-02` is a string. The YAML 1.1 schema each also ships turns it into a `Date`, and also turns a key or value spelled `on` or `yes` into `true`, so a frontmatter key named `on` becomes the key `true`.
- `js-yaml` exports `CORE_SCHEMA` and `timestampTag`, and every schema has a `withTags` method returning a schema with the tags added. `load(text, { schema: CORE_SCHEMA.withTags(timestampTag) })` yields a `Date` for `2024-01-02` and for `2024-01-02T10:00:00Z`, at any nesting depth, and leaves `on` and `yes` as strings. `yaml` reaches the same result with `parse(text, { customTags: ['timestamp'] })`.
- `js-yaml`'s `load` returns `unknown`. It returns the scalar for a scalar document, the array for a sequence document, and `null` for `~`. A numeric key becomes a string key.
- `js-yaml`'s `load` throws a `YAMLException` for an empty document, for one holding only whitespace, and for one holding only a comment, with the reason `expected a document, but the input is empty` and no mark. `loadAll` returns an empty array for each of those, one document for a mapping, and one element per document otherwise. For malformed YAML it throws with a `reason` such as `deficient indentation` and a `mark` whose `line` is zero-based within the text given, and a message whose first line is the reason followed by the one-based line and column.
- `js-yaml` throws on a duplicate mapping key, as does `yaml`.
- `js-yaml` 5.4.2 ships its own types, an `import` condition pointing at an ES module, and one runtime dependency, `argparse`, for its command-line tool. `yaml` 2.9.1 ships types and no dependencies. In the week ending 2026-09-24, `js-yaml` had 284.4 million downloads and `yaml` 195.0 million, read from the npm downloads API. `gray-matter`, which parses a frontmatter block whole, had 9.2 million.

## Decisions

1. **The package exports three types from a new `src/plugins/register-plugins.ts`: `Plugin`, `Renderer`, and `RenderContext`. A `Plugin` is an object with a `name` and an optional `renderers` map from extension to `Renderer`, keyed by the extension without its dot, so a plugin writes `renderers: { md: render }`. A `Renderer` is a function of a body and a `RenderContext` returning a string or a promise of one. The `RenderContext` declared here carries `page`, with the page's `url` and `output`, and `file`, with the path under the source root of the file being rendered and its `directory`.** *(deviation: at the gate the user cut `output`, because a renderer never writes a file, and `page.url`, because the URL reaches every renderer as the `_url` variable, and `directory` went as derivable from `path`, so the context is the file's `sourcePath` alone, unnested; the plugins spec's Render context list was amended to match.)* The spec's plugin surface grows with each step, and the type grows with it: helpers, file handlers, page hooks, and emit are fields later steps add. The context is declared now so the renderer's signature is the spec's from the first plugin, and it carries only what this plan computes. Variables and the `_chain` view arrive with plan 3.2, which computes them, and the reads, emit, and logger with step 4. Nothing calls a renderer in this plan. Rejected: keying renderers by the extension with its dot, as `path.extname` returns it. A plugin author writes the key by hand, and `md` reads as the extension where `.md` reads as a file name.

2. **`Configuration` gains `plugins?: Plugin[]`, and `ResolvedConfiguration` gains `plugins: Plugin[]`, defaulting to an empty list. Resolution checks that the setting is an array whose every item is an object with a string `name`, each failure an error naming the setting, and keeps the list in the order written.** The setting name joins the constant the unknown-setting check reads, so a configuration naming `plugins` stops failing as unknown the moment the build consumes it. The shape check is resolution's, as every setting's is, because a JavaScript configuration can pass anything. What a plugin registers is checked where it is registered (see: Decision 3). Order is the site's one tool to arrange handlers and hooks, so nothing here sorts. Rejected: checking duplicate names in resolution, which enforces the plugins spec from the configuration module.

3. **`registerPlugins(plugins: Plugin[]): Registry` in the same module builds the registry the build reads: a `Map` from extension to the renderer and the name of the plugin that registered it. Two plugins with one name fail naming it. Two plugins registering one extension fail naming both plugins and the extension. A `renderers` field that is present and not an object fails naming the plugin, and a renderer that is not a function fails naming the plugin and the extension. `build` calls it before the walk.** The spec makes each a build error and has a setup failure stop the run before any unit starts, and the walk is the first work, so registration precedes it. The registry is a value built from a value, so every rule is a unit test on object literals. The two shape checks exist for the JavaScript site the type cannot protect, since a renderer that is not callable would fail on the first page in plan 3.2 with a message about calling undefined. Rejected: a `Registry` class with a `register` method per plugin, which is the same checks behind a second surface. *(deviation: the object check copied the `isObject` guard of `src/configuration/resolve-configuration.ts`, so review had it extracted to `src/shared/is-object.ts`, which both modules import.)*

4. **`classifySource(paths, extensions: ReadonlySet<string>)` returns `SourceFiles` with three fields: `pages: PageFile[]`, `templates: TemplateFile[]`, and `staticFiles: StaticFile[]`. A path with an underscore-prefixed directory segment yields nothing, as today. Of the rest, a file whose extension is in the set is a template when its name starts with an underscore and a page otherwise, and every other file is static as today. A `PageFile` holds `path`, `directory`, `extension`, `output`, and `url`. A `TemplateFile` holds `path`, `directory`, `extension`, and `name`, the file name without its extension, so `_` and `_post`. *(deviation: the path fields are `sourcePath` and `outputPath`, on every file type and on `Output`, per the path-naming rule the user set at the gate.)* The extension is what follows the last dot of the file name, so a dotfile with no other dot has none and is static. The directory is the file's directory under the source root with forward slashes, and the empty string at the root.** Classification stays a function from paths to values, proven on values, and the renderer set is the one input the spec adds to it. A page's directory, output path, and URL are functions of its path alone (see: Decision 5), so they are set here, where the principle asks for the directory to be a field set at classification and never derived from the output path. A template's name is what plan 3.2's search compares, and a page's extension is what picks its renderer. The empty string names the root so a search that walks up directories ends at a value it can compare. Rejected: a fourth kind for files inside private directories, which the spec says are not classified at all. Rejected: reading each page's contents here, which makes a function on values a function on the disk (see: Decision 8).

5. **A page's output path is `<directory>/<name>/index.html`, or `<directory>/index.html` when the name is `index`, or `404.html` when the name is `404` and the directory is the root, with no leading slash and with the root directory contributing no segment. Its URL is a leading slash, then the output path with a trailing `index.html` removed.** These are the spec's rules restated as string operations, and the URL is derived from the output path exactly as the spec defines it, so `index.html` gives `/`, `about/index.html` gives `/about/`, and `404.html` gives `/404.html`. A `404` page below the root is an ordinary page, since the spec names the root one alone. Rejected: a URL setting in frontmatter, which nothing in scope needs.

6. **`planOutputs(sourceFiles)` plans one entry per page at its output path and one per non-private static file at its source path, runs the uniqueness check over all of them, and returns the static copies only.** The uniqueness rule now has two kinds of source to hold apart, and the planner is where the static build put it. The page entries take part in the check and are then left out of the result, because the writer copies from source files and a page has no file to copy: its output is the rendered document plan 3.2 produces. Until then a page is classified, read, and checked, and not written, which is a dark seam inside a package no site builds on yet. Rejected: writing a page's body unrendered, which the spec's rationale for the missing-template error names as never what an author means. Rejected: an `Output` that carries contents instead of a source path, which is plan 3.2's to shape with the rendered document in hand.

7. **Frontmatter is parsed by `parseFrontmatter(text: string)` in a new `src/templates/parse-frontmatter.ts`, returning the frontmatter keys, the `template` directive, and the body. It splits the block by hand and parses the block with `js-yaml` under `CORE_SCHEMA.withTags(timestampTag)`.** The block opens when the file's first line is `---` and closes at the next line that is `---`, either with a trailing carriage return, and the body is everything after the closing line. A file whose first line is anything else has no keys and its whole contents as its body. Four cases are errors, and Phase 3 amends the spec to commit to them: a block that opens and never closes, because a page whose frontmatter silently became its body is the misfire the spec's own rationale names; a block whose YAML is not a mapping; a `template` value that is not a string; and YAML the parser rejects, reported with the parser's reason and the line's number in the file, which is the mark's zero-based line plus one for the delimiter and one for the count. A block that is empty or holds only comments has no keys: the block is parsed with `loadAll`, which returns no document for such input where `load` throws, and the first document is the mapping. A key starting with an underscore is the error the spec already states. The `template` key is removed from the keys and returned on its own, so a page's `template` never reaches the merged variables. The module works on values and names no file: the reader adds the file (see: Decision 8). The parser is js-yaml because the two candidates answered every case alike once given the timestamp tag, and js-yaml is the more downloaded. The core schema with timestamps is the reading of the spec that makes an unquoted date a date value without the 1.1 schema turning a key spelled `on` into `true`. Rejected: `gray-matter`, which parses the block for us but brings excerpts, a second delimiter syntax, and a fraction of the downloads, for a split that is a few lines. Rejected: `yaml`, fewer downloads and no other difference this plan can see. Rejected: parsing the YAML 1.1 way, which the spec's date rule might be read to want, because it changes a key's spelling. *(deviation: the mapping check tests that the document's prototype is `Object.prototype`, because under the timestamp schema a bare date scalar parses to a `Date`, which a plain-object check accepts as a mapping.)*

8. **`readSite(source, sourceFiles): Promise<Site>` in a new `src/build/read-site.ts` reads every page and template with `readFile`, parses its frontmatter, and returns a `Site` with `pages: Page[]`, `templates: Template[]`, and the static files as they were. A `Page` is a `PageFile` with `frontmatter`, `template`, and `body`, and a `Template` a `TemplateFile` with the same three. An error from the parser is rethrown with the file's path under the source root ahead of the message and the original as the cause.** The build's first phase classifies and parses frontmatter, and this is the parse: after it, nothing reads a page's or template's source again. Splitting the read from classification keeps classification on values and puts the disk behind one function with one fixture. The spec has every frontmatter error name the file, and the reader is where the file is known. The reads run through `runUnits`, as every unit does, and each unit writes its result into a slot preallocated at its file's index, so the pages and templates come back in classification's order whichever read settles first, which is what keeps scheduling out of the output. The principle's sentence that classification alone makes the value is amended in Phase 3 to name the read too. Rejected: reading inside `classifySource`, which is proven on values today and would need a fixture per rule.

9. **The fixture renderer is `fixtureRenderer(): Plugin` in `test/fixtures/pages/fixture-renderer.ts`, a plugin local to that site, named `fixture` and registering the extension `tpl` with a renderer that returns the body unchanged. The site's configuration imports it as `./fixture-renderer.ts`, and a test that needs a plugin value imports it from the fixture by relative path.** *(deviation: at the gate the user ruled that a test never imports a file from a fixture it does not exercise, so the pages configuration is the plugin's one importer and the bad-frontmatter build test writes its renderer as a literal.)* A site may keep a plugin of its own beside its configuration, so the file is written as a site writes one, and a copy of the fixture carries it, which is what lets the compiled command build the copy. The extension is one no existing fixture uses, so every file in `defaults` and `excluding` stays static. A factory returning the plugin type mirrors the shape the toolchain convention gives every real plugin. The renderer's body is plan 3.2's to write, when the context carries variables to substitute. Rejected: registering `html` or `txt`, which turns files in existing fixtures into pages. Rejected: a helper under `test/helpers/`, which a configuration imports by a path that leaves the fixture directory, so a copy of the site cannot load it.

10. **Two fixtures. `test/fixtures/pages/` *(deviation: renamed `test/fixtures/templated/` at the gate, naming the case it holds, a site with templates, in the pattern of the other fixtures rather than one feature of it)* is a site whose configuration lists the fixture renderer, holding pages, templates, and static files in the shapes the source tree spec distinguishes. `test/fixtures/bad-frontmatter/` holds a source tree alone, with one page whose frontmatter has an underscore-prefixed key.** The site is read in place by the reader's tests and copied by the build's, and it is the whole-site fixture plan 3.2 renders. The error fixture exists because the reader touches the disk and its one error path needs a file. It needs no configuration, because the reader takes the classified files as a value and the build's test resolves a configuration value holding the fixture renderer against the fixture directory. Every other frontmatter rule is a value test.

11. **Delivery is a single PR.** The change is three new modules with their tests, five changed modules with their tests, one dependency, two fixtures, and four doc edits, which one review holds. No phase would ship on its own: the setting without classification accepts a list the build ignores, and classification without the read leaves frontmatter errors uncaught.
