# Globals and data files

## Goal

Deliver checklist plan 3.3: the `globals` setting, the `_data` directory, the first layer of the variable merge, and the collision errors. After this plan a site defines variables once, in its configuration or in a data file, and every page and template reads them beneath its own frontmatter. Step 3 of the checklist is then complete.

## Context

### What the specs commit to

- The configuration may define globals, an object whose keys become variables in every page and template. A global whose name starts with an underscore is an error. A global that a data file also defines is an error naming both (see: docs/specs/configuration.md, Globals).
- A setting the configuration does not know is an error naming the setting, before any work starts (see: docs/specs/configuration.md, The configuration file).
- A file in `_data` at the source root defines one global named after the file, with its parsed contents as the value. A subdirectory defines an object holding its files. A file and a directory with one name at one level are an error naming both. A JavaScript module's default export is the value. A data file whose name starts with an underscore is an error, because the variable it would define is reserved (see: docs/specs/templates.md, Data files).
- The merged variables are built from the globals first, then each template's frontmatter from the root down, then the page's, each layer overriding the keys before it (see: docs/specs/templates.md, Variables).
- A file the configuration excludes is treated as absent (see: docs/specs/configuration.md, Excluded files).
- Phase 1 of a build classifies every file, parses every frontmatter block, and parses the data files. The name collisions among globals are caught once every global is defined (see: docs/specs/build.md, Order of work).

## Decisions

1. **The `globals` setting.** `Configuration` gains `globals?: Record<string, unknown>`, `ResolvedConfiguration` gains `globals: Record<string, unknown>`, the default is an empty object, and `settingNames` gains the key. `checkSettings` fails a `globals` value that is not a plain object with `The globals setting must be an object.`, and a key starting with an underscore with `The global ${name} starts with an underscore, which is reserved.`. The resolver is where every other setting is checked before any work starts, and the spec puts the underscore rule on the configuration, so a site learns of it from the command before a walk. `isObject` is the check the resolver already uses for the configuration itself. Rejected: checking the underscore rule where the globals meet the data files, which would let a walk and a read run before a configuration error that needs neither.

2. **The data reader.** A new `src/templates/read-data.ts`, headed with a marker naming `docs/specs/templates.md`, Data files, declares `interface DataVariable { name: string; sourcePath: string; value: unknown }` and exports `readData(source: string, sourcePaths: string[]): Promise<DataVariable[]>`. It takes every path the build kept after exclusion, selects those under `_data/`, and returns one variable per top-level name in the order the names were first defined: the name, the path of the file that defines it or of the directory that does, and the value. The module sits in `src/templates/` because the Data files section is the templates spec's (see: docs/conventions/structure.md, Directories). It takes the already-walked paths because the walk lists every file and the exclusion has run, so a `.DS_Store` under `_data` is absent to it as it is to classification, and the structure rules run on paths as values. It returns the defining path with each variable because the collision with a configuration global is caught only once every global is defined, after this read (see: docs/specs/build.md, Order of work), and the error names both. Rejected: a separate walk of `_data`, which repeats the walk and the exclusion. Rejected: reading data files inside `readSite`, which would make the build's read of pages and templates carry a second spec's rules. Rejected: taking the configuration's globals and checking the collision here, which would catch it in the build's first phase, where the spec catches it only once every global is defined (see: docs/specs/build.md, Order of work).

3. **Which files are data.** The spec names JSON, YAML, and a JavaScript module. The configuration runs as a `.ts` file on type stripping. The sites built on Underdot keep no YAML data, per the user's ruling in planning.

   **Data files are `.json`, `.js`, and `.ts`. Any other file under `_data` is a build error naming it. The spec's Data files section is amended to say so, with YAML dropped and TypeScript modules added.** A `.ts` data module is what a site that writes its configuration in TypeScript expects to write, and the runtime that loads the one loads the other. YAML goes because a commitment with no site behind it is machinery every build carries for nobody, and the frontmatter parser stays the one place a site writes YAML. An unrecognized file fails on the configuration spec's own reasoning for unknown settings: a file placed to define a variable that silently defines nothing is indistinguishable from one that had no effect. Rejected: keeping YAML because its parser is already a dependency, which argues from cost and not from need. Rejected: ignoring an unrecognized file, which lets `team.jsn` define nothing without a word.

4. **Reading, then assembling.** Every data file reads in its own unit through `mapUnits`, so the results keep the walk's sorted order, and the results then fold in that order into one tree of variables. A file's variable path is a list of segments, its directories under `_data/` and then its file name with the extension removed, so `_data/team/leads.json` defines `team.leads`. A segment is a name as written, so a dot inside a file name stays in the variable's name and never nests. Errors print the path joined by dots. Two rules are properties of the path alone, and a unit applies them before it touches the disk:
   - An extension other than `json`, `js`, or `ts` fails with `The data file ${sourcePath} must be a .json, .js, or .ts file.`.
   - A segment starting with an underscore, a directory's as much as a file's, fails with `The data variable ${variable} from ${sourcePath} starts with an underscore, which is reserved.`, where `${variable}` is the path up to that segment and the message's tail is the one the configuration's and the frontmatter's reserved-name errors already use. A directory under `_data` defines a variable too, so the reserved class covers it.

   Every collision is caught where the fold places a value. The fold keeps, for each node, the file or the directory that defined it, because a file's object value and a directory's object cannot be told apart once they are values:
   - A full path a file already holds fails with `Both ${first} and ${second} define ${variable}.`. Two data files with one name and different extensions are the case, and the spec amendment adds it beside the file-and-directory rule, with the rationale that the build has no rule to pick by, as it has none for two templates with one name (see: docs/specs/templates.md, Template resolution). Rejected: the last file in sorted order wins, which is deterministic and loses one file's contents without a report.
   - A directory prefix a file already holds, or a full path a directory already holds, fails with `Both ${filePath} and the directory ${directoryPath} define ${variable}.`, naming the file and the directory whichever came first. The directory is named by its path under the source root.

   The fold runs in sorted order after every read, so a collision names its two sources the same way on every machine. Which of two independent failures a site sees first, a malformed file or a collision, is no commitment: the build stops at the first unit that fails (see: docs/specs/build.md, Errors), and `readSite` already lets two frontmatter errors race the same way. Rejected: checking the layout over the paths before any read, which builds the table of definers a second time, ahead of the fold that hits the collision on its own.

5. **Parsing.** A `.json` file is read with `readFile` and parsed with `JSON.parse`. A parse error is rethrown as `${sourcePath}: ${describeError(error)}` with the original as its cause, the way a frontmatter error is wrapped, because `JSON.parse`'s message names no file. A `.js` or `.ts` file is imported by `pathToFileURL(join(source, sourcePath)).href`, as the configuration is, and its default export is the value. *(deviation: the import idiom and the error wrapping were each a second copy of code another spec directory already held, so the final review moved them to `src/shared/import-default.ts` and `src/shared/attribute-error.ts`, so the configuration loader imports `importDefault`, the site reader imports `attributeError`, and the data reader imports both.)* A module whose default export is `undefined` fails with `The data file ${sourcePath} has no default export.`, because a data value may be anything, so no later check can tell a missing export from a value, where a configuration's missing export fails its object check. A module that throws propagates its own error, as a throwing configuration does. The spec amendment names JavaScript and TypeScript modules so the `.ts` case is a commitment and not an accident of the runtime. Rejected: wrapping a module's throw with the path, which the throwing configuration does not get and whose branch no test can reach without a third fixture.

6. **Defining the globals.** The build spec catches a global name defined twice only once every global is defined, in the phase after every frontmatter block and data file is parsed (see: Decision 2). The templates spec states the same collision from the data file's side (see: docs/specs/templates.md, Data files). A new `src/templates/define-globals.ts`, headed with a marker naming `docs/specs/templates.md`, Data files, so the marker names its directory's spec (see: docs/conventions/structure.md, Directories), exports `defineGlobals(globals: Record<string, unknown>, dataVariables: DataVariable[]): Record<string, unknown>`, a function on values that returns the configuration's globals with each data variable added under its name, and fails a name both define with `Both the globals setting and ${sourcePath} define ${name}.`, where the path is the variable's defining file or directory. The build calls it after the site read, which is where the spec's third phase sits while no handler or hook exists, so a site with a bad frontmatter block and a colliding global sees the frontmatter error first, as the spec's order says. Checklist step 6 adds the globals that hooks define to this function's input, which is why the check has a function of its own rather than a line in the build. Rejected: checking the collision inside the data reader, which runs in the first phase (see: Decision 2). Rejected: amending the build spec's third phase to say the check runs as soon as the data is read, which would move a commitment to fit the code and move it back when hooks arrive.

7. **The first layer of the merge.** `renderPages(pageChains: PageChain[], globals: Variables)` takes the globals, typed with the alias the module already declares, and `mergeVariables` starts from a copy of them before folding the chain. A key overrides the whole value under it, so a page's `team` replaces the data `team` rather than merging into it, which is what the spec's layered override says and what every other layer already does. Rejected: deep-merging objects across layers, which the spec does not commit to and which would make a page unable to replace a list.

8. **Wiring.** `build` in `src/build/build.ts` destructures `globals` from the resolved configuration, calls `readData` after classification, then `readSite`, then `defineGlobals` with the configuration's globals and the data variables, and passes the result to `renderPages`. The two reads are the build spec's first phase, and the definition is its third, with nothing yet between them. Rejected: one call that reads and defines, which puts a third-phase check inside a first-phase read.

9. **The fixture proves the layer.** The templated fixture's configuration gains `globals: { siteName: 'Templated', title: 'Global' }`. Its source gains `_data/site.json` holding `{ "year": 2024 }`, `_data/team/leads.json` holding a list of two names, `_data/team/size.js` exporting `3`, and `_data/team/motto.ts` exporting a string. The root template reads `siteName` and `site.year` beside what it reads today, and `about/team.tpl` reads `team.leads`, `team.size`, and `team.motto`. The root template's `title: Site` stays, so `about/index.html` still prints `Site` and proves that a template's frontmatter overrides a global. The four files cover a top-level JSON file, a nested JSON file, and a module in each extension, and the fixture already reads every variable through one renderer, so the expected output proves the layer's position and the nesting from one build. The lint override for a fixture's default export is widened to `test/fixtures/**/source/_data/**/*.{ts,js}`, with its comment saying a data module's default export is its value. Rejected: a second whole-site fixture for globals, which would repeat the templates to prove one more layer of the merge they already prove.

10. **Fixtures for the disk.** Four new fixtures hold the errors that need a file read, one per filesystem case (see: docs/conventions/testing.md, Fixtures): `test/fixtures/bad-data/source/_data/site.json` holds malformed JSON, `test/fixtures/data-without-default/source/_data/site.ts` exports a named value and no default, `test/fixtures/duplicate-data/source/_data/` holds `team.json` beside `team.ts`, and `test/fixtures/data-file-and-directory/source/_data/` holds `team.json` beside `team/leads.json`. None needs a configuration, because the reader is called with the source path. The extension and reserved-name rules fail before a read and get value tests with a source path nothing reads.

11. **Delivery is a single PR.** The change is two new modules with their tests, a setting with its checks, a parameter on the renderer, two pipeline lines, fixture files with a regenerated expected output, and doc amendments. One review holds it, and plan 3.2's PR was larger.

## Out of scope

- **A helper's name colliding with a global or a frontmatter key.** Deferred to checklist step 5, which registers the first helper.
- **Globals defined by page hooks.** Deferred to checklist step 6, which adds them to `defineGlobals`'s input.
- **Watching `_data` and reloading a changed data module.** Deferred to checklist step 8. A module import is cached by URL, so a session that reruns a build in one process needs a way past the cache, which the session owns.
- **Tracking which globals a render read.** Deferred to checklist step 7.
- **A site-facing convention for data modules.** Declined. Every rule this plan decides about a site's data files is a spec rule.
- **A migration guide entry.** Declined. The guide already carries the move of data files into `_data` and the merge order.
