# The EJS plugin

## Goal

Deliver checklist plan 4.2: the first workspace package, `underdot-ejs`, with a renderer for `.ejs` files, the unset-variable rule, includes resolved through the render context, the configured `views` directories, the plugin's spec, and its site-facing conventions. After this plan a site renders its pages and templates with EJS through the build alone, which closes checklist step 4 and gives step 5's helpers a real engine to be called from.

## Context

### What a renderer owes the build and what it gets back

- A plugin registers a renderer for a file extension. The renderer turns a body and the variables into a string, receives the render context, and resolves any include or relative reference through it. A renderer lets a template read a variable no file set without raising an error, and documents what the read yields (see: docs/specs/plugins.md, Renderers).
- The render context carries the file's path under the source root, the merged variables with the built-ins among them, and the build's read operations. A read of a file resolves a relative path against the file's directory and an absolute path against the source root, yields no value at a path where no file is, treats an excluded file as absent, and fails for a path above the source root (see: docs/specs/plugins.md, Render context). A plugin reads source files through the context, never through the filesystem (see: docs/specs/plugins.md, Reading and writing).
- A relative path resolves against the directory of the file being rendered when the path is used. A renderer may also search directories its plugin is configured with, after the file's own directory, so an include can name a shared partial without a path (see: docs/specs/templates.md, Relative paths).
- `_content` is the rendered output of the file below in the chain, and `_url` and `_chain` are the other built-ins (see: docs/specs/templates.md, Built-in variables).
- A page is a file whose extension has a registered renderer, so which extensions make a page is the site's choice (see: docs/specs/source-tree.md, Classification).
- A plugin reports a failure by throwing. An error thrown while a plugin is set up fails the run before any unit starts (see: docs/specs/plugins.md, Errors). A site lists its plugins in the configuration (see: docs/specs/configuration.md, Plugins).
- `src/plugins/register-plugins.ts:6` is `Renderer`, a function of a body and a `RenderContext` returning a string or a promise of one, and lines 8-12 are `Plugin`, a `name` and a `renderers` map keyed by extension without its dot.
- `src/plugins/bind-render-context.ts:11-19` is `RenderContext`: `sourcePath`, `variables`, `readFile(reference): string | undefined`, and `readBody(url): string`. Lines 32-46 are `readFile`, which joins a reference starting with a slash onto the source root and any other onto the directory of `sourcePath`, fails for a result above the root, returns `undefined` for a path the walk did not see, and reads synchronously.
- `src/templates/render-pages.ts:34` and `:46` build a fresh variables object for every file rendered, so nothing a render writes into its variables reaches another file.
- `src/index.ts:9` exports the types `Configuration`, `Plugin`, `RenderContext`, and `Renderer`, which is everything a plugin imports from `underdot`.

### Where a second package plugs into the repo

- `package.json:21-23` declares `workspaces: ["plugins/*"]`, and no directory matches it yet. Lines 31-35 are the core's `exports` map with its `development` condition first. Line 43 is the core's `prepack`, which runs the build.
- `tsconfig.json:6` includes `plugins/*/src` in the type check. `tsconfig.solution.json:4` references the core's build config alone. `tsconfig.base.json` carries the compiler options every build config extends, `customConditions: ["development"]` among them.
- `vitest.config.ts:5` runs `plugins/*/src/**/*.test.ts`, and line 9 counts `plugins/*/src/**` toward coverage, with every column held at 100 (see: docs/conventions/testing.md, Coverage).
- `eslint.config.js:46` lists the `development` condition for the `n` plugin's resolver, so an import of `underdot` from a plugin resolves to `src/`. Line 106 sorts an import of `underdot` as external through a `pathGroups` entry, because the resolver finds it inside the repo.
- `.gitignore:5-6` ignores `dist/` and `*.tsbuildinfo` at any depth.
- Every plugin's manifest declares the same `engines` as the root, and every package's `exports` map carries a `development` condition before `types` (see: docs/conventions/toolchain.md, Node floor) (see: docs/conventions/toolchain.md, Modules).

### How the proof must be shaped

- A fixture is a project directory holding what its case needs, written exactly as a site writes it, read in place and copied by a test that builds, and a test that builds a site with pages holds the destination to the fixture's `expected/` directory (see: docs/conventions/testing.md, Fixtures).
- A test sits in the file of the module whose code does the work, a module that delegates gets tests for what it adds and one that reaches the delegate end to end, and a whole-site test belongs to the module that runs the pipeline (see: docs/conventions/testing.md, Placement).

## Decisions

1. **The package.** The core sits at the repository root with plugins as workspaces under `plugins/`, each published as `underdot-<name>` (see: Where a second package plugs into the repo). `npm pack --workspace <name>` runs that workspace's `prepack` with the root's `node_modules/.bin` on the path, and `npm install` in a workspace declaring `underdot` at `file:../..` links `node_modules/underdot` to the repository root. Both verified 2026-10-03 in scratch workspaces.

   **`plugins/ejs/` is the package `underdot-ejs` at version `2.0.0-alpha.0`, an ES module with the root's `engines`, `files: ["dist"]`, an `exports` map of `development: ./src/index.ts`, `types: ./dist/index.d.ts`, and `default: ./dist/index.js`, a `prepack` script running `tsc -b tsconfig.build.json`, `ejs` at `^6.0.1` as its one dependency, `underdot` at `^2.0.0-alpha.0` as a peer dependency, and `@types/ejs` at `^3.1.5` and `underdot` at `file:../..` as dev dependencies. Its `tsconfig.build.json` extends `../../tsconfig.base.json` with `composite`, `rootDir: src`, `outDir: dist`, includes `src`, excludes tests, and references the core's build config. The root solution file gains a reference to it.** The version matches the core's so the peer range names a release that exists, and the caret admits every later prerelease and the 2.x line. The `file:` dev dependency is what links the core into the workspace so the plugin's tests and type check reach the core's source through the condition. `prepack` on the plugin is what lets `npm pack --workspace underdot-ejs` build it, and the reference builds the core first. Rejected: `@types/ejs` at the root, which puts a plugin's types where no plugin file is checked against the root manifest.

2. **The import of EJS.** `ejs` is at 6.0.1, released 2026-05-26, with 52.5 million downloads in the week ending 2026-10-01, and it ships no types. `@types/ejs` is at 3.1.5, written for the 3.1 line. The package ships an ES module build under the `import` condition with a default export and no named exports, so `import { compile } from 'ejs'` type-checks against `@types/ejs` and fails at runtime with `does not provide an export named 'compile'`, while `import ejs from 'ejs'` type-checks and runs. A `.d.ts` file under `plugins/*/src/` is not emitted by a composite build and does not count toward coverage. Verified 2026-10-03 on the registry, in the tarball, in a scratch type check, and by placing one under a throwaway workspace and running the suite.

   **The plugin imports EJS as `import ejs from 'ejs'` and calls `ejs.compile`. A file `plugins/ejs/src/ejs-options.d.ts` augments `@types/ejs`'s `Options` with `unsafePrototypeLocals?: boolean` and `legacyInclude?: boolean`, the two options EJS 6 added, with a comment stating that the types are written for EJS 3 and lack them.** A default import is the one form that both type-checks and runs. The augmentation is the smallest patch over types the registry has not caught up with, and the comment keeps the next reader from deleting a file the compiler would not miss until the next edit. Rejected: a local declaration of the whole `ejs` module, which rewrites types the registry already carries. Rejected: `@ts-expect-error` at the compile call, which hides every other error on that line.

3. **The factory.** The toolchain convention has every plugin's factory take a typed options object and return the core plugin type (see: docs/conventions/toolchain.md, TypeScript). The user chose `views` as the one option.

   **`plugins/ejs/src/index.ts` exports `interface EjsOptions { views?: string[] }` and `ejs(options: EjsOptions = {}): Plugin`. The plugin is named `ejs` and registers one renderer, for the `ejs` extension, that calls `renderEjs` with the body, the context, and the views. `views` defaults to an empty list. A `views` entry is a directory path under the source root, written without a leading slash, as `_includes`. A `views` value that is not an array throws `The views option must be an array.`, and an entry that is not a string, is empty, or starts with a slash throws `Each views entry must be a directory path under the source root, written without a leading slash.`.** A site writes `import { ejs } from 'underdot-ejs'` and `plugins: [ejs({ views: ['_includes'] })]`, so the factory's name is the engine's. The shape checks exist for a JavaScript site the type cannot protect, and they run when the configuration module evaluates, which is before any work. A leading slash is rejected rather than tolerated because an entry is joined under the source root and a slash would read as the filesystem root. An entry with a `..` segment is left to the context, which fails a read above the source root. Rejected: an `ext` option, which v1 had, because the extension that makes a page is the site's choice through the files it writes and nothing the user's sites need. Rejected: passing other keys through to EJS, which v1 did, because an option the plugin does not understand is one the spec cannot commit to.

4. **The module layout.** The structure convention names a module after its one function, groups the core's modules under the directory of the spec each enforces, and keeps the core's entries at the root as thin calls into the modules that do the work (see: docs/conventions/structure.md, Names) (see: docs/conventions/structure.md, Directories). It says nothing about a plugin package.

   **A plugin package's `src/index.ts` is its entry, exporting the factory and the options type in the signature the plugin's spec names, and the renderer lives in `plugins/ejs/src/render-ejs.ts` as `renderEjs(body, context, views)`. Both carry a spec marker naming `docs/specs/ejs.md`. The structure convention's Directories section gains the ruling: a plugin package under `plugins/<name>/` enforces `docs/specs/<name>.md`, its `src/index.ts` exports the factory and the options type a site imports, and the modules doing the work sit beside the entry, each named after its one function with its test beside it, with no spec directories because the package enforces one spec.** The entry is thin for the reason the core's is: the renderer's own signature takes the views, which the registered renderer closes over, where the registered signature is the spec's body and context. The options type sits in the entry because the site imports it from there and the entry is where the factory consumes it. Rejected: one module holding the factory and the renderer, which gives the entry work to do that the convention keeps out of it. Rejected: `src/ejs/` directories inside the plugin, which group one spec's modules under a name that repeats the package's.

5. **Includes.** The spec resolves a relative path against the directory of the file being rendered when the path is used, lets a renderer search its plugin's configured directories after the file's own, and has every read go through the context (see: What a renderer owes the build and what it gets back). EJS's own `include(path, data)` copies the locals into a bare object before rendering the partial, and its resolution probes the disk with `existsSync`, relative to the `filename` option and then each `views` directory. EJS's `legacyInclude` option defaults to true and makes `<% include name %>` read the named file from the disk at compile time, and with it false the directive is ordinary JavaScript and a syntax error. Verified 2026-10-03 in the `ejs@6.0.1` source and in a scratch probe run on Node 24.19.0 and 22.18.0.

   **The renderer supplies its own `include(reference, data)` function to every file it renders and compiles every file with `legacyInclude: false`. A reference with no extension gets `.ejs`. A reference starting with a slash is read through the context as it is. Any other reference is tried as a path under the including file's directory and then under each `views` entry in order, each candidate read through the context as an absolute path. The first read that yields text is rendered through the same function as the including file, with the partial's own path as its file and the including file's variables with `data` merged over them, so a nested include resolves against the partial and the partial renders under the same rules as the file that included it. A relative reference no candidate satisfies throws `No include ${reference} is in ${directory} or in the views directories.`, with `the source root` in place of an empty directory. An absolute one throws `No include ${reference} is under the source root.`.** Supplying `include` is what lets the plugin hand a partial the same variables object the including file renders with, and reading through the context is what records the read as an input once step 7 tracks inputs and what keeps an excluded or above-root partial absent or failing by the context's rules. The `.ejs` default is EJS's own, so `include('header')` reads as every EJS author expects. An absolute reference searches no `views` directory because it names its directory. The missing-include error names the directory searched rather than the including file, because the build attributes the file in step 6 and a partial's own name is already in the reference. `legacyInclude: false` turns the one EJS form that reads the disk behind the build into a syntax error. The templates spec's Relative paths section gains one sentence: a partial an include renders is the file being rendered while it renders, so a relative path inside it resolves against the partial's directory. Rejected: EJS's `includer` hook, which runs after EJS has probed the disk and still hands the partial a bare copy of the locals. Rejected: resolving a top-level relative reference by handing it to `readFile` unjoined, which splits the resolution between the plugin and the context for the first level only.

6. **The unset-variable rule.** The spec has the renderer let a template read a variable no file set and document what the read yields (see: What a renderer owes the build and what it gets back). `ejs.compile(text, options)` returns a function of a data object, and before the generated code runs, the function copies the data into a bare object unless `unsafePrototypeLocals: true` is set, which passes the data object through untouched. The generated code wraps the template in `with (locals || {})` and inside that block reaches five names of its own: `__append`, `__line`, `escapeFn`, `include`, and `locals`. Every other name a template reads resolves through the data object first and then the enclosing scopes, so a Proxy whose `has` trap answers for a name decides what the name reads, and `with` hands the trap string keys only. `<%= %>` escapes its value and `<%- %>` prints it raw, and both print nothing for `undefined` and `null`. A `const`, `let`, or `var` declared inside a scriptlet works with a Proxy as the locals, and a `var` assignment lands on the Proxy's target. Verified 2026-10-03 in the source and in the same probe run.

   **The renderer compiles every file with `unsafePrototypeLocals: true` and renders it with a Proxy over a copy of the file's variables. The Proxy's `has` trap answers true for a key that is an own property of the copy, for `include`, and for any other key that is neither a property of `globalThis` nor one of `__append`, `__line`, `escapeFn`, and `locals`. Its `get` trap returns the include function of Decision 5 for `include` and the copy's property otherwise. The four EJS names are a module constant typed as a set of property keys, so the trap needs no check of the key's type, under a comment stating that they are the names EJS's generated code reaches from inside its `with` block.** *(deviation: the four names fall through whether or not the copy has an own property of that name, because an own `locals` or `escapeFn` answered by the trap stood in for EJS's own and broke the file that set it. Such a variable is reachable through `locals` alone, which the spec's Variables section states.)* A name no file set is answered by the Proxy and read as `undefined`, which the output tags print as nothing, so `title` works wherever `locals.title` did and `locals.title` keeps working because `locals` falls through to EJS's own parameter, which is the Proxy. A runtime global falls through so `JSON`, `Math`, `Date`, and `encodeURIComponent` keep working, and a variable that shares a global's name shadows it because an own property always answers. The four EJS names fall through so `__line` keeps counting lines and `escapeFn` keeps escaping. `include` always answers with the plugin's function, so a variable of that name is unreachable from an EJS file. The copy is what keeps a `var` assignment inside a scriptlet off the caller's object. The names couple the plugin to EJS's generated code, and the renderer's tests prove each of the four still falls through, so a change in EJS surfaces as a failing test rather than a broken site. Rejected: `destructuredLocals` with the names a scan of the template finds, which is what the migration guide's wording describes, because a `const` the template declares collides with the `var` EJS emits for the same name. Rejected: `strict` mode, which makes `title` a reference error and keeps only `locals.title`. Rejected: `Symbol.unscopables` on the data object, which enumerates the same four names behind a second mechanism.

7. **Rendering and errors.** A helper returns synchronously and an engine's include hook is synchronous, which is why a read through the context returns synchronously (see: docs/specs/plugins.md, Render context). A plugin never writes its own name or the file it was working on into the message, and a renderer's syntax error carries the line and column the engine reports (see: docs/specs/plugins.md, Errors). With EJS's `filename` option set, a runtime error's message opens with `<filename>:<line>`, the surrounding source lines with the failing one marked, and the error's own message, and a syntax error's message is the engine's followed by ` in <filename> while compiling ejs` and advice naming EJS-Lint, with no line or column. Verified 2026-10-03 in the same probe run. The user chose to pass the file.

   **The renderer compiles synchronously, with `filename` set to the file's path under the source root, the partial's path inside a partial, and returns the compiled function's string. Every error EJS throws propagates as it is. The plugins spec's Errors section is amended so that what the engine a plugin wraps reports passes through as it is, the file and line of a failure included, while the plugin's own messages still never name the plugin or the file.** A template cannot `await`, and nothing it can call is asynchronous. The file in EJS's context is the one fact the build cannot supply for a failing partial, since the build knows the template and not the partial it included. The amendment records that the engine's report is the engine's and not a message the plugin wrote. Rejected: EJS's `async` option, which would let a template await a read the context cannot perform asynchronously. Rejected: a compile cache keyed by path, which no measurement has asked for.

8. **The spec.** Every statement in a spec is a commitment, with rationale inline where a decision would otherwise be reopened (see: @lab43/q conventions/specs.md, What a spec holds). The README has each plugin's spec written inside the plan that builds it.

   **A new `docs/specs/ejs.md`, indexed in the agent briefing's Specs group, commits to the plugin's behavior in four sections. Rendering: the plugin registers a renderer for the `ejs` extension, a file renders with EJS's syntax, rendering is synchronous, the legacy include directive is a syntax error, and a render error carries the file and line the engine reports. Variables: every merged variable and built-in is reachable by its name, a name no file set reads as `undefined`, `locals` holds the same variables, a runtime global is reachable unless a variable shares its name, and `include` is the plugin's function in every file, so a variable of that name is unreachable. Includes: the signature, the resolution order, the `.ejs` default, nested includes against the partial, data merged over the variables, reads through the context, and the two errors. Options: `views`, what an entry is, and the two shape errors. Each commitment carries the rationale Decisions 3, 5, 6, and 7 give it.** The spec is what the structure convention's ruling and the plugin's markers name, and what a later change to the plugin is held to. Rejected: a section of the plugins spec, which is the contract every plugin honors and not the behavior of one.

9. **Tests on values.** A function from a value to a value is tested on object literals, and a fixture exists only where the code touches the disk or a whole site proves an integrated build (see: How the proof must be shaped). The renderer takes the context's `readFile` and never touches the disk itself.

   **`plugins/ejs/src/render-ejs.test.ts` tests the renderer with a stub context whose `readFile` looks an absolute reference up in a map of source paths to text and whose `readBody` returns an empty string, and it asserts through a spy that every read the renderer makes is an absolute reference. `plugins/ejs/src/index.test.ts` tests the factory's shape, its defaults, its option errors, and one render through a registered renderer that reaches a partial through `views`.** The stub is the context as the spec defines it to a renderer, so the tests prove the renderer against the contract and not against the core's implementation. The spy is what holds the renderer to resolving every reference itself before the read. Rejected: importing `bindRenderContext` from the core into the plugin's tests, which proves the core again through a plugin.

11. **How the fixture declares the plugin.** A whole-site test belongs to the module that runs the pipeline (see: How the proof must be shaped). `eslint-plugin-n`'s extraneous-import check, read at `node_modules/eslint-plugin-n/lib/util/check-extraneous.js:180-260`, allows an import of the nearest manifest's own name and its declared dependencies, and for a file inside a workspace member also the root manifest's dependencies, so a file under the root importing a workspace package by name is extraneous unless the nearest manifest declares it. 12. **The docs beyond the spec.** The payload carries rules for writing a site, addressed to its authors only (see: @lab43/q conventions/extensions.md, Which rules ship). The migration guide names what a v1 site changes, each entry pointing at the spec section that decided it, and the driving manual records how to bring Underdot up by hand. `docs/guides/migrating-from-v1.md:33` says an include that names a partial without a path, resolved through the EJS plugin's `views` directories, keeps working unchanged, and line 45 says the EJS plugin supplies every referenced name, which describes a mechanism Decision 6 rejected. The v1 plugin, as the user supplied it, is a function of a config object returning an installer. It took `ext`, defaulting to `ejs`, `views`, defaulting to an empty list, and passed every other key through to EJS as an option, setting `root` to the source directory and appending the rendering file's directory to `views` at each render. A v1 site therefore passed `views` entries as paths from the project directory, and may have passed `ext` or any EJS option.

    **Three docs change. A new `q-extension/conventions/ejs.md`, indexed in the briefing's `underdot` group, carries two rules with their rationale inline: print `_content` with `<%- %>`, never `<%= %>`, because it is rendered HTML and the escaping tag would show its markup as text; and include a shared partial by name through `views` rather than by path, because a relative path resolves against the file rendering it, so a partial included from templates at several depths needs a path per depth where a name reads the same everywhere *(deviation: the rule forbids a relative path, not every path, because its rationale does not reach an absolute path, which reads the same from every depth, and the fixture's root template includes one)*. The migration guide gains a section, The EJS plugin, with four entries: the import and the call become `import { ejs } from 'underdot-ejs'` and `ejs({ views: [...] })` in the plugin list; `views` entries are directories under the source root, such as `_includes`, where v1 took paths from the project directory, the rendering file's own directory is searched without being listed, and a partial anywhere under the source root is named with a leading slash; `ext` is gone, so a site that registered another extension renames those files to `.ejs`; and other EJS options no longer pass through, so a site that set `delimiter`, `rmWhitespace`, or `root` drops them, `root` being the source root in both versions. Line 33 of the guide is reworded so an include by name keeps working once `views` is written relative to the source root, and line 45 so the plugin resolves every name a template reads rather than supplying it. The driving manual gains a section, A site on the published packages: pack the core and the plugin into a scratch directory, copy the `ejs` fixture beside them, install both tarballs in the copy, run `npx underdot build` there, and diff the build against the fixture's `expected/`, which is the one run that proves the plugin's `dist`, its `exports` map without the `development` condition, and its peer dependency.** The two conventions are the rules a site author can get wrong without the build catching it, which is what a convention is for, and everything else the plugin decides is a spec rule. The guide's entries follow from the v1 surface and the options Decision 3 keeps, and line 33 is reworded because the entry on `views` falsifies it as written. The manual's section exists because the compiled command cannot resolve `underdot-ejs` from a scratch copy that installs nothing, and a real install is the proof a consumer gets. Rejected: a convention on reading `title` over `locals.title`, which is style with nothing the build or a reader loses either way. Rejected: a README for the plugin package, which publishing, out of scope since the scaffolding plan, will need and this plan does not.

13. **Delivery is a single PR in two phases.** The package with its tests and spec is one seam, and the fixture with the docs around it is the other. The package alone proves the renderer against the contract and leaves the repo green, and the fixture then proves it through the build. Neither ships alone: the package without the fixture is a plugin no site in the repo uses, and the fixture without the package does not build. The change is one small package, one fixture with three expected files, and the doc edits, which one review holds. Rejected: stacked PRs, which would put a package and its first use under separate reviews for mechanics that return nothing.

- **Attributing a render error to the plugin and the file in the chain.** Deferred to step 6. This plan's errors are EJS's own and the include error names the directory searched.
