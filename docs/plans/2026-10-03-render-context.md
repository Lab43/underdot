# The render context

## Goal

Deliver checklist plan 4.1: the render context with the file being rendered, a read of a file under the source root that resolves relative paths against that file and absolute paths against the source root, a read of another page's rendered body by its URL with the page-body error, and the logger, proven with the fixture renderer. After this plan a renderer resolves an include through the build rather than the filesystem, a template composes other pages' bodies, and a plugin warns without failing anything, which is the surface plan 4.2's EJS plugin renders against.

## Context

### What the specs commit to

- The render context carries the file being rendered, its path under the source root and so its directory, the merged variables with the built-ins and `_chain` among them, the build's read operations, the emit operation, and a logger. Reading another page's rendered body is available while a template renders and never while a page's body renders. A page body that reads another page's body is a build error naming both pages (see: docs/specs/plugins.md, Render context).
- A relative path resolves against the directory of the file being rendered when the path is used, so a template's include resolves the same way whichever page is rendering it. An absolute path resolves against the source root. A renderer may also search directories its plugin is configured with, after the file's own directory (see: docs/specs/templates.md, Relative paths).
- A plugin reads source files through the context and never through the filesystem directly, because a read the build cannot see is a dependency it cannot track (see: docs/specs/plugins.md, Reading and writing). Renderers and plugins may read any file under the source directory, underscore-prefixed or not, including files inside underscore-prefixed directories (see: docs/specs/source-tree.md, Underscore prefix).
- Helpers return their value synchronously, and all file handling completes before any page renders because helpers read handled output synchronously (see: docs/specs/plugins.md, Template helpers) (see: docs/specs/plugins.md, File handlers).
- A file the configuration excludes is treated as absent: not classified, not handled, and not written (see: docs/specs/configuration.md, Excluded files).
- A plugin warns through the context's logger, and a warning fails nothing. A plugin never writes its own name or the file it was working on into a message, because only the build knows which unit was running (see: docs/specs/plugins.md, Errors).
- Every page's body renders in the build's fourth phase and every chain in the fifth, so a template reads a body that exists (see: docs/specs/build.md, Order of work).
- The URL identifies a page everywhere: as `_url`, in helpers, and in the page tree plugins see (see: docs/specs/source-tree.md, URLs).

## Decisions

1. **The context module.** The structure convention groups a module under the directory of the spec it enforces and declares a type in the module whose function produces its values (see: docs/conventions/structure.md, Directories) (see: docs/conventions/structure.md, Types). The render context is the plugins spec's section, and `src/plugins/register-plugins.ts` declares it today because nothing produced one.

   **A new `src/plugins/bind-render-context.ts`, headed with a marker naming `docs/specs/plugins.md`, Render context, declares `RenderContext` and exports `bindRenderContext(source: string, sourcePaths: ReadonlySet<string>, warn: WarningSink): MakeRenderContext`. `RenderContext` keeps `sourcePath` and `variables` and gains `readFile: (path: string) => string | undefined`, `readBody: (url: string) => string`, and `logger: { warn: (message: string) => void }`. `MakeRenderContext` is `(file: { sourcePath: string; variables: Record<string, unknown> }, bodies: ReadonlyMap<string, string> | undefined) => RenderContext`, and `WarningSink` is `(line: string) => void`. `register-plugins.ts` imports the context type for `Renderer`, and `src/index.ts` re-exports it from the new module.** The three operations close over what the build lends every render, the source root, the walked file set, and the warning sink, and over what each render has of its own, the file and the bodies rendered so far. Binding the build's part once and making a context per file is what keeps `renderPages` a function on values that takes the maker as a parameter (see: Decision 5). The context stays flat, with the file's path alone, because a read resolves a relative path itself (see: Decision 2), so no plugin computes the directory. The checklist's "and its directory" is the spec's own wording, the path and so its directory, and the directory is carried as the path's, which the read resolves against. Rejected: a `directory` field beside `sourcePath`, which plan 3.1 cut as derivable and which a read that resolves for the caller leaves no plugin needing. Rejected: `makeRenderContext(source, sourcePaths, warn, file, bodies)` with the build binding the first three at the call, which puts a five-parameter call behind an arrow in the pipeline where one bound function reads. Rejected: keeping the type in `register-plugins.ts`, which would declare a value's type away from the function that now makes the value.

2. **Reading a file.** `readFile` resolves its argument to a path under the source root with `node:path/posix`'s `join`: an argument starting with a slash joins onto `.`, and any other joins onto the directory of `sourcePath`, which `dirname` gives with `.` read as the root. A resolved path that is `..` or starts with `../` is a build error: `${sourcePath} reads ${path}, which is above the source root.`. A resolved path not in `sourcePaths` returns `undefined`. Otherwise the file is read with `readFileSync` from `node:fs` as UTF-8 and returned. The resolver carries a marker naming `docs/specs/templates.md`, Relative paths, and the set check carries one naming `docs/specs/configuration.md`, Excluded files, since that check is what keeps an excluded file absent to a read.

   The read is synchronous because helpers return synchronously and read handled output synchronously, and an engine's include hook is synchronous, so an asynchronous read would be unusable by the two callers the spec names. The lookup is against the walked set rather than the disk, so an excluded file is absent to a read exactly as it is to classification, a directory is not a file, and nothing outside the walk is readable. An absent file reads as no value rather than failing, so a renderer can try the file's own directory and then each configured directory with plain reads, which is the search the templates spec allows, and it matches how an unset variable reads. A path above the root is an error because no site means it, and a read outside the source is the read the plugin contract forbids. The build has `paths` in hand, so the set costs one construction. Text alone because the EJS plugin is the consumer this plan serves and it reads text (see: Out of scope). Phase 1 amends the plugins spec's Render context section with three commitments, that reads are synchronous, that a read of a path at which no file is yields no value, and that a path above the source root is a build error naming the file, and amends the configuration spec's Excluded files section so an excluded file is absent to a read. Rejected: an `exists` operation beside the read, which the undefined read already answers. Rejected: probing the disk and mapping `ENOENT` and `EISDIR` to `undefined`, which reads excluded files and files the walk never saw. Rejected: clamping a path above the root to the root, which `posix.normalize` does for an absolute argument and which silently reads the wrong file.

3. **Reading a body.** `readBody` takes a URL. When `bodies` is `undefined`, a page's body is rendering, and the read is a build error naming the reading page and the URL: `${sourcePath} reads the body of ${url} while its own body renders, which only a template can do.`. Otherwise it returns the body at the URL in `bodies`, and a URL the map lacks is a build error: `${sourcePath} reads the body of ${url}, but no page has that URL.`.

   `undefined` for the bodies is the body pass's mark because the first pass has no bodies to offer and the error is the only thing the read can do there. The URL names the other page, since the URL is the page's identity everywhere, so the error names both pages as the spec requires. An unknown URL fails where an unknown file reads as absent because nothing searches for pages the way a renderer searches for an include, and a listing that names a page the site lacks is an author error worth stopping for. Phase 1 amends the Render context section with a fourth commitment, that reading the body of a URL no page has is a build error naming the file and the URL. Two pages with one URL reach the map, and the second overwrites the first in the pages' order, which is deterministic, and the build then fails at the write with the uniqueness error it raises today, so the map checks nothing. Rejected: returning `undefined` for an unknown URL, which turns a misspelled URL into an empty listing. Rejected: naming the other page's source path, which the body pass would have to look up for an error that fires before the lookup matters.

4. **The logger and its sink.** `logger.warn(message)` calls the sink with `${sourcePath}: ${message}`. `build` in `src/build/build.ts` gains a second parameter, `warn: WarningSink`, defaulting to a function that writes `warning: ${line}\n` to `process.stderr`, and binds it into the context maker. `src/index.ts` and the command pass nothing.

   The line names the file because that is what the context knows and what an author needs to find the warning, and the spec forbids the plugin from naming it. Naming the plugin waits for step 6, which attributes errors to the plugin and the unit, so that the one attribution covers both. The sink is a parameter of the internal build rather than of the configuration because the configuration is data, and a parameter is what lets the dev server supply a sink that reaches the browser in step 8 without a setting. The default sits on the internal build so neither caller changes, and the `warning:` prefix is the sink's because a line on stderr beside error reports needs the word and a browser panel for warnings does not. Rejected: a logger object as the parameter, which is one method behind an object for a build that has one thing to say. Rejected: a sink parameter on the exported `build`, which no script needs yet.

5. **Wiring the passes.** `renderPages(pageChains: PageChain[], globals: Variables, makeContext: MakeRenderContext)` makes each context through the maker. `renderBody` calls `makeContext({ sourcePath, variables }, undefined)`. `renderPages` builds `bodies` as a `Map` from each rendered body's `page.url` to its `body` once the first pass settles, and `renderChain` takes it and calls `makeContext({ sourcePath, variables }, bodies)` for each template. `build` calls `renderPages` with `bindRenderContext(source, new Set(paths), warn)`, and the set's construction carries a marker naming `docs/specs/source-tree.md`, Underscore prefix, because seeding the set from the walk rather than from classification is what lets a read reach a file inside a private directory.

   The maker is a parameter so the render passes stay a function on values, proven with a stub maker, and the module that touches the disk is proven on the fixture. The map is built between the passes, which is exactly the boundary the spec puts between bodies and chains. The render tests that assert the exact context switch to `expect.objectContaining` on `sourcePath` and `variables`, and two tests assert the maker's calls: every body call gets `undefined`, and every chain call gets a map holding every page's body under its URL. Rejected: having `renderPages` take the source root, the set, and the sink and bind the maker itself, which puts the disk behind the render tests.

6. **The fixture proves the reads.** The fixture renderer gains two forms beside `{{ path }}`: `{{> path }}` substitutes the context's `readFile(path)`, shown as an absent value when `undefined`, and `{{@ url }}` substitutes `readBody(url)`. A third form, `{{! message }}`, calls `logger.warn(message)` and substitutes nothing. The templated fixture changes so one build proves every rule:

   - `_.tpl` at the root gains a line including `{{> _partial.txt }}`. Every page renders through it, and `blog/hello.tpl` and `about/team.tpl` belong to directories that hold no `_partial.txt`, so the partial's text appearing on their pages proves the relative path resolved against the template's directory and not the page's.
   - `blog/_post.tpl` gains `{{> ../_partial.txt }}`, a relative path climbing a directory.
   - `blog/_.tpl` gains `{{> /_includes/header.tpl }}`, an absolute path into a private directory.
   - `about.tpl` gains `{{> missing.txt }}`, a read of a file the site lacks, which shows as nothing, from a page body, which proves a page body may read files.
   - A new `blog/_archive.tpl` with the body `The archive template: hello {{@ /blog/hello/ }}` followed by `{{ _content }}`, and a new `blog/index.tpl` with `template: archive` and the body `The blog index.`. The archive's output shows the hello post's rendered body, unwrapped, which proves a template reads another page's body as the first pass rendered it.
   - `index.tpl` gains `{{! The home page warns. }}`, which the build test proves reaches the sink as `index.tpl: The home page warns.` by passing a spy as `build`'s second parameter.

   The forms are the least syntax that exercises each operation, and the sigils keep the existing form untouched. The page-body error and the unknown-URL error are value tests of the context module, since a renderer in a value test is a function that calls the read. The driving manual's description of the templated fixture gains the includes and the body read, and its claim that a successful build prints nothing becomes that a successful build prints nothing but warnings, with the templated fixture's one warning line as the example, since the fixture it recommends now prints one. Rejected: a second whole-site fixture for the reads, when the existing one already holds the include and the partial plan 3.1 placed for this step.

7. **The guide.** The migration guide describes v2 as the specs commit to it, ahead of the code: its entries on page hooks, emit, and the dev server describe surfaces no code has yet, each pointing at the spec section that decided it. Its two render context entries, at lines 36 and 44, name a directory field and a page URL that the spec's Render context section does not list, since the section carries the file's path and so its directory, and the URL reaches a render as `_url`.

   **The two entries are rewritten to the spec's context: a helper hands a relative path to the context's read, which resolves it against the file being rendered, and the context carries the file's path, the merged variables with `_url` among them, the build's read and emit operations, and a logger.** Emit stays in the entry because the spec's section lists it and the guide's emit entry already describes it, and a migrating author reads the guide against the spec, not against a release. Rejected: cutting emit from the entry until step 5 ships it, which would make one entry track the code while every other entry tracks the spec.

8. **Delivery is a single PR, in one phase.** The change is one new module with its tests, edits to the render passes, the build, their tests, and the fixture with its expected output, two spec amendments, and two guide entries. It has no seam at which the repo is green: the widened context type is required wherever a context literal is built, the passes are the only place one is, the default sink is a branch only a warning reaches, and the fixture is where the first warning comes from. Rejected: a phase for the module and the passes ahead of the fixture, which leaves the sink's default uncovered and the suite red.

## Out of scope

- **Recording each read as an input of the render.** Deferred to checklist step 7, which plan 3.3 also deferred the tracking of global reads to. Every read goes through the closures the build makes, so step 7 wraps them without changing the plugin surface.
- **Reading handled output, and emit.** Deferred to checklist step 5, which adds file handlers and the first emitted file.
- **A read that returns bytes.** Deferred to the first plugin that needs them, the images plugin of checklist step 9. The EJS plugin reads text.
- **Naming the plugin in a warning, and attributing errors to the plugin and the unit.** Deferred to checklist step 6.
- **Caching a file's contents across the renders of one build.** Declined. A synchronous read of a small include per render is cheap, and a cache is an optimization no measurement has asked for.
- **A site-facing convention.** Declined. Everything this plan decides about a site's files is a spec rule.
