# The bust plugin

## Goal

Deliver checklist plan 5.2: the second workspace package, `underdot-bust`, whose one helper gives a link to a static file a query string that changes when the file's served bytes change. It is the first plugin to consume a helper registration and a read of handled output, so it proves the mechanisms of plan 5.1 through a published package and a real engine. The plan also closes two caveats plan 5.1 shipped with, by holding what a file handler returns to a shape the build can write and read back.

## Context

### What the helper may rely on, and what it owes the build

- A helper is reachable by its name among the file's variables in every engine, bound to the render context of the file being rendered, receives that context ahead of the arguments written in the template, and returns synchronously (see: docs/specs/plugins.md, Template helpers). `src/plugins/register-plugins.ts:21` is `Helper = (context: RenderContext, ...args: unknown[]) => unknown`, and `src/plugins/bind-render-context.ts:115-120` copies the variables and sets each helper under its name, bound to the context.
- A read of handled output takes a reference resolved as a file read is and yields the output as the build writes it: the file as it sits in source when no handler matched it, a private output that is never written, and no value for a path no static file's output has, a page's path included. Every read through the context returns synchronously, and a path above the source root is a build error (see: docs/specs/plugins.md, Render context). `src/plugins/bind-render-context.ts:70-76` resolves a reference by joining a slash-prefixed one under `.` and any other under the file's directory with `node:path/posix`'s `join`, then fails above the source root, and lines 88-94 are `readOutput`, which looks the resolved path up in the outputs by output path and reads a copy from disk.
- A relative path resolves against the directory of the file being rendered, the template's directory when a template is rendering, and this binds every helper that takes a path (see: docs/specs/templates.md, Relative paths).
- An output path with a segment starting with an underscore is never written (see: docs/specs/source-tree.md, Underscore prefix), which `src/build/write-destination.ts:72-73` enforces by splitting the path on slashes.
- All file handling completes before any page renders (see: docs/specs/plugins.md, File handlers). Plugin order decides the sequence file handlers run in and the sequence page hooks run in, and nothing else about a plugin depends on its position (see: docs/specs/plugins.md, Plugin identity and order).
- A plugin reads source files through the context, never through the filesystem (see: docs/specs/plugins.md, Reading and writing). A plugin that keeps state between a file handler and a helper, such as a table of hashes, keeps it through the context's reads instead (see: docs/specs/plugins.md, Dependencies).
- A plugin reports a failure by throwing, and never writes its own name or the file it was working on into the message (see: docs/specs/plugins.md, Errors).
- The same source, configuration, and plugins produce a byte-identical destination on every run and every machine (see: docs/specs/build.md, Determinism).

## Decisions

1. **A handler's return is checked before the build takes it.** An output is written under the destination at its path and read back through the context by that exact string (see: What the helper may rely on, and what it owes the build). `src/plugins/run-handlers.ts:27-47` runs one file through the handlers under the file's head marker naming the File handlers section. Lines 37-39 fail a handler whose return is not an array, naming the plugin and the glob. Lines 40-42 push each returned file with `Buffer.from(contents)`, and nothing checks the returned `outputPath` or `contents` first. PR #46's body records the two consequences as caveats: a returned path such as `../x`, `/x`, or `a/./b` reaches the write as given, and a returned file with no `contents` fails inside `Buffer.from` with an error naming no plugin. This plan's helper is the first reader of output paths, so the check lands here.

   **`runHandlers` checks each returned file after the array check. An `outputPath` that is not a string, or whose slash-separated segments include an empty one, `.`, or `..`, fails with `The handler ${pluginName} registers for ${glob} returned a file at ${JSON.stringify(outputPath)}, which is not a plain path under the destination.`. A `contents` that is neither a string nor a `Uint8Array` fails with `The handler ${pluginName} registers for ${glob} returned ${outputPath} with contents that are neither text nor bytes.`. The plugins spec's File handlers section gains one commitment: a returned file whose output path is not a string, or has a leading slash or an empty, `.`, or `..` segment, or whose contents are neither text nor bytes, is the same error naming the plugin and the glob, because an output is written under the destination at its path and read back by that exact string, so a path that escapes the destination or spells one location two ways can be neither written nor found.** The segment rule is one predicate that rejects every shape the caveat lists: an empty segment covers a leading slash, a doubled slash, a trailing slash, and the empty string, and the two dot segments cover climbing and the unnormalized spelling. `JSON.stringify` quotes the path, so an empty string reads as `""` rather than as nothing. A `Buffer` is a `Uint8Array`, so a handler passing bytes through passes the check. The checks sit under the file's existing marker, since they enforce the section it names. The messages carry the plugin and the glob because the build writes them, as the array message does, and step 6's attribution only adds the unit. Rejected: normalizing the returned path for the handler, which would let `a/./b` and `a/b` from two handlers reach the uniqueness check as one path with no author having written it twice. Rejected: deferring the check to the write, where the path has lost the handler that returned it.

Every plugin's factory takes a typed options object and returns the core plugin type (see: docs/conventions/toolchain.md, TypeScript). `plugins/ejs/` is the one workspace package: `package.json` with the root's `engines`, `files: ["dist"]`, an `exports` map of `development`, `types`, and `default`, a `prepack` running `tsc -b tsconfig.build.json`, `underdot` as a peer dependency at `^2.0.0-alpha.0` and a dev dependency at `file:../..`; `tsconfig.build.json` extending the base with `composite`, `rootDir: src`, `outDir: dist`, and a reference to the core's build config. `tsconfig.solution.json:5` references it, and `plugins/ejs/src/index.ts:14-27` is its factory. `tsconfig.json:6` type-checks `plugins/*/src`, `vitest.config.ts:5` and `:9` run and cover `plugins/*/src`, `eslint.config.js:106` sorts `underdot-*` as external, `package.json` lists `plugins/*` as workspaces, and `.gitignore` ignores `dist/` and `*.tsbuildinfo` at any depth, so a second package under `plugins/` needs no change to any of them. `src/index.ts:10` exports `Helper`, `Plugin`, and `RenderContext` among the types a plugin imports. The user chose the name `bust` for the package suffix, the plugin, the factory, and the helper.

   **`plugins/bust/` is the package `underdot-bust` at `2.0.0-alpha.0`: an ES module with the root's `engines`, `files: ["dist"]`, an `exports` map of `development: ./src/index.ts`, `types: ./dist/index.d.ts`, and `default: ./dist/index.js`, a `prepack` of `tsc -b tsconfig.build.json`, no dependencies, `underdot` at `^2.0.0-alpha.0` as a peer dependency and at `file:../..` as a dev dependency, and a `tsconfig.build.json` identical in shape to the EJS package's. `tsconfig.solution.json` gains a reference to it. `plugins/bust/src/index.ts` exports `bust(): Plugin`, which returns `{ name: 'bust', helpers: { bust: bustReference } }`. The helper lives in `plugins/bust/src/bust-reference.ts` as `bustReference(context: RenderContext, reference: unknown): string`. Both files carry a marker naming `docs/specs/bust.md`.** The factory takes no parameter because it has no option to type, and the toolchain rule exists so a site's options are checked, which a factory with none satisfies with nothing. An empty options interface is what the lint's empty-object rule forbids. The helper's module is named for what the function does, since `bust` is the factory's name in the same package and a module exporting one function is named after it. 3. **The helper.** The read of handled output, the relative-path rule, and the underscore rule bind the helper (see: What the helper may rely on, and what it owes the build). A browser resolves a relative link against the page's URL and not against the template that wrote it, so a relative reference returned as written would name one place to the build and another to the browser, and the two agree only for a page in its own directory. `node:crypto` exports `hash(algorithm, data, encoding)`, a one-shot digest, as a named export. It exists on Node 22.18.0, the floor, `eslint-plugin-n` 18.3.0 lists it as supported from 20.12.0 and 21.7.0, and `@types/node` 22.20.4 declares it at `crypto.d.ts:3407`. Its first eight hex characters for `body { margin: 0; }\n` are `eac0e790`, for `body {\n  margin: 0;\n}\n` are `25e8ca12`, and for `export const site = 'bust';\n` are `2aab4262`, and `createHash('sha256')` agrees. `node:path/posix`'s `join` normalizes as it joins: `join('.', '/a/./b')` is `a/b`, `join('.', '/_x/../a')` is `a`, `join('blog', '../styles/site.css')` is `styles/site.css`, and `join('.', '../x')` is `../x`. All run on Node 24.19.0 and 22.18.0 on 2026-10-04. The user chose the query-string form when planning 5.1.

   **`bustReference` fails a reference that is not a string with `A reference must be a string, and ${String(reference)} is not.`. It resolves the reference as the context does, `join(reference.startsWith('/') ? '.' : dirname(context.sourcePath), reference)` with `join` and `dirname` from `node:path/posix`, which also normalizes it. It reads `context.readOutput(reference)`, so the error the context throws for a reference above the source root propagates as it is, and fails no value with `No static file's output is at ${reference}.`. It then fails a resolved path any of whose segments starts with an underscore with `${reference} is private, so it is never written and cannot be linked.`. Otherwise it returns `/${outputPath}?v=${hash('sha256', output, 'hex').slice(0, 8)}` with `hash` from `node:crypto`, the output's absolute URL and never the reference as written.** Hashing the output rather than the source is the whole point: a stylesheet a handler compiles or minifies busts when its compiled form changes and not otherwise, and reading through the context is what will make the page depend on the file once step 7 records reads. The hash is a function of the bytes alone, so every machine produces the same link. Eight hex characters distinguish every revision one file will have, and a longer string buys a link nothing. The query string leaves the path alone, so nothing else that names the file changes and no handler runs. Returning the absolute URL is what lets a relative reference resolve per the templates rule and still mean the same place to the browser. The plugin repeats the context's one-line join because the context exposes no resolver and both are bound to the same spec rule, and the read still goes through the context by the reference as written so the context's own above-root check runs. The private check mirrors the write's rule on segments, on the resolved path so `/_x/../a` is judged by where it lands, and runs after the read so the above-root error is the context's. An absent output is an error rather than the reference returned bare, because a link no file answers is an author error that an unbusted link would hide until the page was served. The one-shot `hash` is the runtime's own and on the floor. The messages name neither the plugin nor the file, which the build attributes. Rejected: failing every relative reference, which contradicts the templates rule binding every path-taking helper, for a case the resolution answers correctly. Rejected: returning the reference as written, which for a relative one yields a link the browser resolves against a different directory than the build read. Rejected: a per-build cache of hashes inside the plugin, which is the table of hashes the plugin contract names as state a plugin keeps through the context's reads instead, and which would hide the file from the dependency tracking step 7 adds.

- **Two outputs where one is a file and the other a directory beneath it**, `a` and `a/b`, which PR #46's third caveat records as failing with the filesystem's error. Deferred. It predates plan 5.1, applies to pages too, and belongs to the uniqueness rule rather than to handlers.
- **Recording each read as an input of the render.** Deferred to checklist step 7. The helper reads through the context, so step 7 wraps it without changing the plugin.
- **Attributing the helper's error to the plugin, the template, and the line.** Deferred to checklist step 6. The helper's messages name neither, as the plugin contract requires.
- **Options on the factory.** Declined (see: Decision 2).
- **Publishing, and a README for the package.** Deferred to publishing, which no checklist step performs (see: Decision 7).
