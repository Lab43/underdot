# File handlers and template helpers

## Goal

Deliver checklist plan 5.1: file handlers that transform, rename, split, and drop static files in plugin order, template helpers a page or template calls with the render context bound in, and a read of handled output through the context, proven with fixture plugins. After this plan every static file passes through the handlers whose globs match it before any page renders, a template calls a helper under its own name in any engine, a helper reads a file as it will be served, and the cache-busting plugin of plan 5.2 has every mechanism it consumes.

## Context

### What a plugin may do to a build, and what it owes back

- A plugin registers a file handler with a glob. Every static file whose path matches passes through the handler, underscore-prefixed files included. The handler receives the file's path and contents and returns zero or more files, each a path and contents. Handlers run in plugin order. What one returns is what the next matching handler receives, and what the last returns is what the build writes, subject to the underscore and uniqueness rules. All file handling completes before any page renders (see: docs/specs/plugins.md, File handlers).
- A plugin registers a helper by name. A helper receives the render context ahead of the arguments written in the template and returns synchronously. Two plugins registering one helper name is a build error naming both. A helper name starting with an underscore is a build error. A frontmatter key or global that shares a name with a registered helper is a build error naming the file (see: docs/specs/plugins.md, Template helpers). A global whose name a registered helper carries is an error naming both (see: docs/specs/configuration.md, Globals).
- The render context carries the file being rendered, the merged variables, and the build's read operations, the handled output of a static file by its output path among them. A read returns synchronously. A read of a file resolves its path per the templates spec, yields no value where no file is, and fails above the source root (see: docs/specs/plugins.md, Render context).
- A plugin that keeps state across units, such as a table of hashes a handler fills and a helper reads, keeps it through the context's reads instead (see: docs/specs/plugins.md, Dependencies).
- A relative path resolves against the directory of the file being rendered when the path is used, and this binds every helper that takes a path. A partial an include renders is the file being rendered while it renders, so a relative path inside it resolves against the partial's directory (see: docs/specs/templates.md, Relative paths).
- File handlers run in the build's second phase, after classification and before page hooks, bodies, and chains. Within a phase, units run in no defined order, and scheduling never affects the output (see: docs/specs/build.md, Order of work) (see: docs/specs/build.md, Determinism).
- A file or directory whose name starts with an underscore is never written, and an underscore-prefixed static file still passes through file handlers so that a plugin can inline an SVG or import a Sass partial kept under the prefix. Files inside an underscore-prefixed directory are not classified at all, neither pages, templates, nor static files, so no handler reaches `_icons/mail.svg`, the layout a directory of inlined icons takes (see: docs/specs/source-tree.md, Underscore prefix). Renderers and plugins may read any file under the source root, those inside underscore-prefixed directories included. Two sources that would write one destination path are a build error naming both, a static file colliding with a handler's renamed output included (see: docs/specs/source-tree.md, Output paths are unique).
- A plugin reports a failure by throwing, and the build attributes it. Attribution to the plugin and the unit is step 6's (see: docs/specs/plugins.md, Errors).
- The EJS plugin includes a partial by reading it through the context, with the partial's own path as the file being rendered and the including file's variables with the include's data merged over them (see: docs/specs/ejs.md, Includes). Every merged variable is reachable by its name, and `include` is the plugin's function in every file (see: docs/specs/ejs.md, Variables).

## Decisions

1. **Helpers are variables.** A helper is a function a page or template calls, and a frontmatter key or global sharing its name is an error, so the spec already treats helper names and variable names as one namespace (see: What a plugin may do to a build, and what it owes back). The EJS Proxy answers every own property of the variables (see: Where the pipeline stops short of that contract). Under `strict`, a function typed `(context, reference: string) => string` is not assignable to `(context, ...args: unknown[]) => unknown`, while `(context, reference: unknown) => string` is. Checked with `tsc` 6.0 on 2026-10-04.

   **`Plugin` gains `helpers?: Record<string, Helper>`, with `Helper = (context: RenderContext, ...args: unknown[]) => unknown`. `registerPlugins` collects them into `Registry.helpers: Map<string, RegisteredHelper>` with `RegisteredHelper { pluginName: string; helper: Helper }`, in plugin order, and fails on four conditions: a `helpers` value that is not an object, `The helpers of ${pluginName} must be an object.`; a value that is not a function, `The helper ${name} of ${pluginName} is not a function.`; a name starting with an underscore, `The helper ${name} of ${pluginName} starts with an underscore, which is reserved.`; a name another plugin registered, `Both ${other} and ${pluginName} register a helper named ${name}.`. Each registration in `registerPlugins` sits under its own `if (plugin.<field> !== undefined)` in place of the early `continue`, so a plugin with helpers and no renderers registers them. `bindRenderContext` takes the helpers map and the context maker binds each helper to the context it makes, as `(...args) => helper(context, ...args)`, and sets the bound function under the helper's name on a copy of the variables it was handed, which becomes the context's `variables`.** Binding in the maker is what puts a helper into every renderer's variables with no renderer doing anything, which is the strongest rung for a rule every engine must honor. A helper receives the very context the renderer renders with, as the spec gives one context to both. The arguments are `unknown` because a template passes whatever it writes, and a typed parameter does not assign under strict function types, so a helper narrows its arguments the way the EJS factory checks its options for a JavaScript site. The helper's `context.variables` is the same object the renderer reads, so a helper reads `_url` and any other variable from it. A helper's name always wins over a variable handed to the maker, which is what the collision rule promises, so a value a renderer merges over the variables under a helper's name, as an include's data could, is replaced by the helper. The plugins spec's Template helpers section is amended: a helper is reachable in a page or template by its name among the variables, bound to the render context of the file being rendered. Rejected: a `helpers` field on the context that each renderer merges, which puts the one rule into every engine and leaves a renderer free to forget it. Rejected: `any` for the arguments, which the lint forbids and which hides the narrowing a helper owes a JavaScript site. Rejected: a namespace object such as `_helpers` holding every helper, which would put a prefix on every helper call in every template to avoid a collision the build reports loudly with a one-line fix, and would make the underscore class's first member that is not a fact about the page.

2. **The collisions are caught where each name is defined.** A frontmatter key or global sharing a helper's name is a build error, and the spec places the catch where every global is defined (see: What a plugin may do to a build, and what it owes back). Page hooks, which define globals in the third phase, arrive with checklist step 6, so today every global is defined once the data files are read in the first phase. `defineGlobals` already fails a name the configuration and a data file both define, and `readSite` already attributes a frontmatter error to its file (see: Where the pipeline stops short of that contract).

   **`defineGlobals(globals, dataVariables, helpers)` fails a configuration global whose name is a helper's with `Both the globals setting and the plugin ${pluginName} define ${name}.` and a data variable whose name is a helper's with `Both ${sourcePath} and the plugin ${pluginName} define ${name}.`. `readSite(source, pageFiles, templateFiles, helpers)` fails a page or template whose frontmatter has a helper's name as a key, after the parse and outside its attribution, with `Both ${sourcePath} and the plugin ${pluginName} define ${key}.`. Each check carries a marker naming `docs/specs/plugins.md`, Template helpers.** A data file's directory defines a variable too, and `DataVariable` already carries the directory's path as its `sourcePath`, so one check covers both. The frontmatter check sits in `readSite` because that is where every frontmatter is parsed and attributed. Both checks run in the first phase, before any render, which is as early as the names exist. The build spec's Order of work places the catch after page hooks because that is where the last global is defined, and it needs no amendment: a collision among names that exist in the first phase is caught there, and step 6 checks the globals its hooks define when they exist. The `template` directive is not a variable and is not checked. Rejected: a check inside `parseFrontmatter`, which is a function of text alone and whose errors are the templates spec's.

3. **A renderer enters a partial through the context.** A relative path inside a partial resolves against the partial's directory, and this binds every helper that takes a path (see: What a plugin may do to a build, and what it owes back). A helper is bound to the context the build made, for the file the build knows is rendering (see: Decision 1), so a helper called inside a partial would resolve against the including file unless the renderer can make the partial the file being rendered.

   **`RenderContext` gains `enterFile(reference: string, variables: Record<string, unknown>): RenderContext`. It resolves the reference as `readFile` does, fails above the source root with the same error, fails a path the walk did not see with `${sourcePath} enters ${reference}, but no file is there.`, and returns the context the maker makes for the resolved path with the given variables, the same bodies, and the helpers bound to the new context. `renderEjs`'s inner `render` takes the text and a context in place of the path and variables, reads `sourcePath` and `variables` from it, and renders a partial by calling `render(partial, context.enterFile(candidate, { ...context.variables, ...data }))`.** The entered context re-binds every helper, so a helper inside a partial resolves against the partial, and the partial's variables are what the renderer supplies, which keeps the include's data rule the EJS plugin's own. A missing file is an error rather than no value because a renderer enters a file it has already read, so an absent one is a plugin defect and never a search. The plugins spec's Render context section gains the operation and its rationale, and the EJS spec's Includes section says the partial renders as the file being rendered through the context. Rejected: binding helpers to the including file and carving an exception into the templates spec, which trades a one-operation surface for a rule with a hole in it. Rejected: taking a resolved source path in place of a reference, which gives the one operation a path form the reads do not take.

4. **A file handler is keyed by its glob and receives the file as it stands.** The configuration's one pattern syntax is the glob, in minimatch's dialect, and the build matches a dotfile like any other name (see: What a plugin may do to a build, and what it owes back) (see: Where the pipeline stops short of that contract). A stylesheet compiler and an SVG optimizer return text, and a handler that keeps a file it does not change returns the bytes it was given. A planned plugin reading other files from a handler, as a Sass compiler follows imports, arrives with checklist step 11. minimatch 10.2.6 with `dot: true` matches `.well-known/x.css` against `**/*.css`, matches `styles/_vars.scss` against `**/*.scss`, matches `site.css` at the root against `**/*.css`, matches `_partial.text` against `**/*.{text,css}`, and does not match `styles/site.css.map` against `**/*.css`. Run on Node 24.19.0 on 2026-10-04.

   **`Plugin` gains `handlers?: Record<string, FileHandler>`, keyed by glob, with `FileHandler = (file: HandledFile) => HandlerOutput[] | Promise<HandlerOutput[]>`, `HandledFile { outputPath: string; contents: Buffer }`, and `HandlerOutput { outputPath: string; contents: string | Uint8Array }`. `registerPlugins` collects them into `Registry.handlers: RegisteredHandler[]`, `RegisteredHandler { pluginName: string; glob: string; handle: FileHandler }`, in plugin order and in key order within a plugin, failing a `handlers` value that is not an object with `The handlers of ${pluginName} must be an object.` and a value that is not a function with `The handler ${pluginName} registers for ${glob} is not a function.`. A new `src/plugins/run-handlers.ts` declares `HandledFile` and `HandlerOutput` and exports `runHandlers(file: HandledFile, handlers: RegisteredHandler[]): Promise<HandledFile[]>`: starting from the one file, for each handler in order, each file whose `outputPath` matches the handler's glob in dot mode is replaced by what the handler returns, each output's contents made a `Buffer`, and each file that does not match passes through unchanged. A handler that returns anything but an array fails with `The handler ${pluginName} registers for ${glob} must return an array of files.`. A handler's throw propagates as it is.** The glob keys mirror `renderers`' extension keys, so a plugin reads the same way for both registrations, and the key order within a plugin is the author's order. The handler receives the path as the previous handler left it, which is what lets a later CSS handler pick up a Sass output named `.css`, and matching on that path at each stage is what re-matching means. A handler keeps a file it does not want to change by returning it, and drops one by returning nothing, so a return that is neither is a defect rather than a third meaning, and the check is what tells a JavaScript site's author about a forgotten `return` instead of passing every file through in silence. Text is accepted because every planned text handler would otherwise call `Buffer.from` on its result, and bytes because a handler passing a file through returns what it received. Errors propagate raw as a renderer's do, and step 6 attributes them. `run-handlers.ts` declares the two types because its function produces their values, and `register-plugins.ts` imports them for `FileHandler` while `run-handlers.ts` imports `RegisteredHandler` back, a type-only cycle of the kind `bind-render-context.ts` and `register-plugins.ts` already form and nothing lints. The plugins spec's File handlers section is amended: the handler receives the output path as the handlers before it left it and the contents, returns files whose contents are text or bytes, may return asynchronously, and is matched against the path each handler returned. Rejected: a list of `{ glob, handle }` objects, which spells one registration two ways. Rejected: a `sourcePath` on the handler's input, which no planned handler reads and which a file produced from no source, as step 9's derivatives are, would have none of. Rejected: a context for the handler, which step 11's Sass plugin is the first to need and which is additive to the handler's signature.

5. **Files inside a private directory are private static files, handled outputs are held in memory, and untouched files are copied.** All file handling completes before any page renders because helpers read handled output synchronously, and the one layout the spec's own rationale for handling private files describes, a directory of SVGs a plugin inlines, is unreachable to a handler as the spec stands (see: What a plugin may do to a build, and what it owes back). A site's images are its largest static files, and an image no handler matches has nothing to hold.

   **`classifySource` classifies a file inside an underscore-prefixed directory as a static file whatever its extension, so `_includes/header.tpl` is neither a page nor a template and `_icons/mail.svg` reaches a handler. Data files under `_data` are static files too, read by the data reader on their own. The source-tree spec's Underscore prefix section is amended: a file inside an underscore-prefixed directory is a static file, so it passes through file handlers and is never written, and the extension that would make it a page or a template elsewhere makes nothing of it there. A new `src/plugins/handle-files.ts` declares `Output { sourcePath: string; outputPath: string; contents: Buffer | undefined }`, where no contents means the file is copied from `sourcePath`, and exports `handleFiles(source, staticFiles: StaticFile[], handlers: RegisteredHandler[]): Promise<Output[]>`. For each static file, in order through `mapUnits`: a file no handler's glob matches yields one output at its own path with no contents, and a file some glob matches is read from disk as bytes, run through `runHandlers`, and yields one output per returned file, each carrying the static file's `sourcePath`. `build` calls it after `readSite` and before the context is bound, and passes the outputs to the context and to `writeDestination`. `StaticFile` loses `private`, and `writeDestination(source, destination, outputs: Output[], pages)` drops every output whose path has a segment starting with an underscore, under a marker naming `docs/specs/source-tree.md`, Underscore prefix, collects the rest with the pages into the sorted uniqueness check, copies an output with no contents from source, and writes one with contents. The uniqueness error for two outputs of one source reads `${sourcePath} would be written to ${outputPath} twice.`.** The first match on the source path decides whether a file is read at all, which is correct because a chain starts only where a handler matches. Privacy moves to the output path because a handler may rename a private file into a public one or a public one into a private directory, and the output path is what the rule's rationale is about. The flag on `StaticFile` then has no reader. Classifying a private directory's files as static files costs a copy entry per file that is never written, and a data file a glob matches is read once more than before, which is nothing against a directory of icons each needing its own underscore. The same-source message exists because a split that names one path twice would otherwise name the file twice as if it were two. Rejected: reading every static file into memory, which holds a site's images for nothing. Rejected: a second list for handled files beside the static files, which gives `writeDestination` two shapes for one thing. Rejected: keeping `_data` out of the static files, a carve-out for a second read nothing suffers from, and the one way a handler could publish site data, renaming its output into a public directory, is the author's deliberate act for any private file.

6. **Reading handled output.** A cache-busting helper needs the hash of the CSS as it will be served, and a plugin keeps state between a handler and a helper through the context's reads (see: What a plugin may do to a build, and what it owes back). A helper that answers whether a file exists must not read a whole image to say so.

   **`bindRenderContext(source, sourcePaths, helpers, outputs: Output[])` indexes the outputs by output path, and `RenderContext` gains `readOutput(reference: string): Buffer | undefined`, which resolves the reference as `readFile` does, fails above the source root the same way, returns no value for a path no output has, and otherwise returns the output's contents, read from the source file with `readFileSync` when the output is a copy. The three resolutions share one local function inside the maker. The returned `Buffer` is the one the build holds and writes, read-only by contract, and its JSDoc says so. The index keeps the last output of a path, which only matters for a path two outputs claim, and the build fails that path at the write.** Handled contents are already in memory after the second phase, so a read of them costs nothing, and a copy reads the way `readFile` does today. An existence check is `readOutput(reference) !== undefined`, which for a handled file touches no disk, so no separate operation is needed. A page has no output when a render runs, so a read of its path yields no value. A helper can read an output and never change one, because every output is final before the first render so that every page reads the same bytes whatever order the renders run in. The plugins spec's Render context section is amended: the read of handled output takes a reference resolved as a file read is, yields the file as it sits in source when no handler matched it, and yields no value for a path no static file's output has. Rejected: an `exists` operation, which the read answers at the same cost. Rejected: copying the buffer on every read, which doubles an image's memory for a mutation no helper has reason to make. Rejected: text from `readOutput`, since an image's bytes are what a hash and a resize need and a string is one call away.

8. **The EJS plugin's proof.** A function from a value to a value is tested on object literals, and the renderer's tests use a stub context (see: Where the pipeline stops short of that contract).

9. **Delivery is a single PR in three phases.** Helpers with the entered partial are one seam. The cutover of the write path from static files to outputs, with the private-directory classification, is the second, kept to itself so the one change that reshapes what reaches the destination is reviewable and revertable alone and lands with the destination byte-identical to before. Handlers with the read of their output are the third. Each phase leaves the repo green, and the first and third change the templated fixture's expected output. The phases change the same context module, the same stub contexts, and the same fixture's expected files, so stacked PRs would each rewrite what the one below just wrote and a reviewer would read three diffs of one file, which is why one review of the whole holds better than three of its parts. Rejected: stacked PRs, for that reason. Rejected: the cutover inside the handler phase, which buries the write path's reshaping in a machinery diff.

## Out of scope

- **Emitted files.** Deferred to checklist step 9, the srcset plugin, which is the first plugin to emit. The cache-busting plugin returns a reference with a query string and emits nothing, the SVGO plugin reads handled output and emits nothing, and the template helpers never did, so a mechanism built here would sit dark for three steps and be grounded against code that had moved on. The checklist's entries for plans 5.1, 5.2, and step 9 are corrected with this plan's docs. One ruling on the spec is recorded now rather than left for step 9 to rediscover: emitting while a plugin is set up has no consumer in the checklist, and the spec's Emitted files section is amended with this plan's docs so emitting is available from helpers during a render.
- **Recording each read as an input of a unit.** Deferred to checklist step 7. Every read goes through the context, so step 7 wraps them without changing the plugin surface.
- **A context for a file handler, and declaring the files a wrapped tool read.** Deferred to checklist step 11, the Sass plugin, which is the first handler that reads other files. Adding a parameter to `FileHandler` is additive.
- **Attributing a handler's or helper's error to the plugin and the unit.** Deferred to checklist step 6. Errors propagate as thrown.
- **Registering the EJS plugin's `include` as a helper.** Declined. The include renders a partial with the plugin's own per-file machinery, and registering it would make a frontmatter key named `include` an error where the EJS spec makes it unreachable. A helper another plugin registers under that name is a variable of that name to the EJS plugin, and so unreachable from an EJS file by the EJS spec's Variables section, while every other renderer reaches it. The EJS plan's deferral closes here.
- **Bytes from `readFile`.** Deferred to checklist step 9, as the render context plan deferred it. `readOutput` returns bytes because handled output is bytes.
- **Page hooks.** Deferred to checklist step 6.
