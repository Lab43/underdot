# The helpers plugin

## Goal

Deliver checklist plan 5.3: the third workspace package, `underdot-helpers`, with the three helpers a site calls from its templates: `activeLink` for a navigation link that knows when it points at the current page or at an ancestor of it, `formatDate` for a date printed the same on every machine, and `fileExists` for a template that includes a file only when the build will serve it. After this plan a site that used v1's `underdot-template-helpers` builds on v2 with the edits the migration guide names.

## Context

### What a helper may rely on, and what it owes the build

- A helper is reachable by its name among the file's variables in every engine, bound to the render context of the file being rendered, receives that context ahead of the arguments written in the template, and returns synchronously (see: docs/specs/plugins.md, Template helpers). `src/plugins/register-plugins.ts:21` is `Helper = (context: RenderContext, ...args: unknown[]) => unknown`, so a helper narrows its own arguments, and `src/plugins/bind-render-context.ts:115-120` sets each helper under its name, bound to the context.
- A frontmatter key or global that shares a name with a registered helper is a build error naming the file (see: docs/specs/plugins.md, Template helpers). `date` is the key a post sets, so no helper carries that name.
- The context carries the variables the file renders with, the built-ins among them (see: docs/specs/plugins.md, Render context). `_url` is the page's URL in every file of the chain (see: docs/specs/templates.md, Built-in variables). `src/templates/render-pages.ts:28` sets it for the page's render and line 46 spreads the same variables into each template's.
- A read of handled output takes a reference resolved as a file read is, a relative one against the directory of the file being rendered and a slash-prefixed one from the source root. It yields the output as the build writes it, a private output included, no value for a path no static file's output has, a page's path included, and a build error for a path above the source root (see: docs/specs/plugins.md, Render context) (see: docs/specs/templates.md, Relative paths). `src/plugins/bind-render-context.ts:88-94` is `readOutput`, which returns the handled contents from memory and reads a copy from disk.
- A plugin reports a failure by throwing, and never writes its own name or the file into the message, which the build attributes (see: docs/specs/plugins.md, Errors).
- The same source, configuration, and plugins produce a byte-identical destination on every machine, and nothing in the output depends on the time (see: docs/specs/build.md, Determinism).

### How a date reaches a template

- An unquoted YAML date keeps the type YAML gives it, a date value and not a string (see: docs/specs/templates.md, Frontmatter). `src/templates/parse-frontmatter.ts:12` parses with the core schema plus the timestamp tag. Under it `date: 2024-01-02` is the `Date` at `2024-01-02T00:00:00.000Z`, `date: 2024-01-02 18:00:00` is the `Date` at `2024-01-02T18:00:00.000Z`, and `date: 2024-01-02T18:00:00-06:00` is the `Date` at `2024-01-03T00:00:00.000Z`. A quoted date is a string. Run against the repo's js-yaml 5.4.2 on 2026-10-04.
- A JSON data file has no date type, so a date in one is a string (see: docs/specs/templates.md, Data files). `new Date('2024-01-02')` is UTC midnight, and `new Date('2024-01-02T18:00')`, with no zone, is the machine's local time. Run on Node 24.19.0 on 2026-10-04.
- A `Date`'s local-time methods read the machine's zone. On a machine in `America/Los_Angeles`, `getDate()` of the `Date` at `2024-01-02T00:00:00.000Z` is `1` and `toLocaleDateString('en-US')` is `1/1/2024`. A runtime global such as `Date` is reachable from an EJS file (see: docs/specs/ejs.md, Variables). Assigning `process.env.TZ` at runtime changes the zone the process formats in, on Node 24.19.0 and 22.18.0, run on 2026-10-04.

### The surface a v1 site migrates from

The v1 plugin is `underdot-template-helpers` 1.0.0, read from its repository on 2026-10-04 at the user's direction, for its surface alone. It depended on `date-fns` 2 and registered three helpers:

- `activeLink(metadata, href, title, attributes = {}, wrapper)`. It appended `active` to the attributes' `class` when `'/' + slug` equalled `href`, and `parent` when `'/' + slug` started with `href`, so an exact match got both classes and a `href` of `/` got `parent` on every page. It mutated the attributes object given. It rendered `<a href="…" …attributes>title</a>`, or with `wrapper` given `<wrapper …attributes><a href="…">title</a></wrapper>`, with every value interpolated as written.
- `formatDate(metadata, date, dateFormat, options = {})`, which returned `format(date, dateFormat, options)` from date-fns 2, formatting in the machine's zone.
- `fileExists(metadata, filename)`, which returned `existsSync(join(source, filename))`, so every path was taken from the source root, a leading slash or none.

### The date library

- `date-fns` 4.4.0 and `@date-fns/tz` 1.5.0 are the latest, each with no dependencies, each shipping its own types, read from the registry on 2026-10-04.

## Decisions

1. **The package.** The naming rules and the model package are given (see: What is already in place for a third package). The user chose `underdot-helpers` over v1's `underdot-template-helpers`.

   **`plugins/helpers/` is the package `underdot-helpers` at `2.0.0-alpha.0`, described as `Template helpers for Underdot`, in the shape of `plugins/bust/package.json` with `repository.directory` of `plugins/helpers`, `date-fns` at `^4.4.0` and `@date-fns/tz` at `^1.5.0` as its dependencies, and a `tsconfig.build.json` identical in shape to the bust package's. `tsconfig.solution.json` gains a reference to it. `plugins/helpers/src/index.ts` exports `helpers(): Plugin`, which returns `{ name: 'helpers', helpers: { activeLink: renderActiveLink, formatDate, fileExists } }`. The three helpers live in `plugins/helpers/src/render-active-link.ts`, `format-date.ts`, and `file-exists.ts`, each exporting the one function its name states, each taking the context first and the template's arguments as `unknown`. Every module carries a marker naming `docs/specs/helpers.md`.** The helper names are v1's, so a migrating site changes nothing in its templates for the names. `renderActiveLink` is the function's name because a function is named as a verb phrase, and `activeLink` is the name the spec commits to for the template. `formatDate` is already a verb phrase and `fileExists` a question. The factory takes no parameter, for the reason the bust plugin's takes none: it has no option to type, and an empty options interface is what the lint's empty-object rule forbids. Rejected: `underdot-template-helpers`, the v1 name, which the user ruled against. Rejected: one module holding the three helpers, which gives a reader of one helper the other two to read past.

2. **`activeLink` marks the current page and its ancestors.** The helper reads `_url` from the context's variables (see: What a helper may rely on, and what it owes the build). v1 gave an exact match both classes and made `/` everyone's parent (see: The surface a v1 site migrates from). Every page URL ends in a slash except `/404.html`, so a link to a section is written `/blog/` (see: docs/specs/source-tree.md, URLs). The user ruled that both quirks are fixed.

   **`renderActiveLink(context, href, title, attributes = {}, wrapper)` fails a `href` or `title` that is not a string with `The href must be a string, and ${String(href)} is not.` and `The title must be a string, and ${String(title)} is not.`, an empty `href` with `The href must not be empty.`, `attributes` that are `null`, an array, or not an object with `The attributes must be an object, and ${String(attributes)} is not.`, attributes holding a key named `href` with `The attributes must not carry href, which the link already has.`, an attribute whose value is not a string with `The attribute ${name} must be a string, and ${String(value)} is not.`, a `wrapper` that is given and not a string with `The wrapper must be a string, and ${String(wrapper)} is not.`, and an empty `wrapper` with `The wrapper must not be empty.`. With `url` as `String(context.variables._url)`, the link's class is `active` when `url === href`, `parent` when `href !== '/' && url !== href && url.startsWith(href)`, and nothing otherwise. The rendered attributes are a copy of those given, in the order given, with the class appended to an existing `class` value after a space, set as the value when the existing one is empty, or added as a last attribute named `class` when none was given. Every attribute value is escaped, the `href` included, `&` to `&amp;`, `"` to `&quot;`, `<` to `&lt;`, and `>` to `&gt;`, by a local function inside the helper. Attribute names, the wrapper, and the title are printed as given. The result is `<a href="${href}"${attributes}>${title}</a>`, or with a wrapper `<${wrapper}${attributes}><a href="${href}">${title}</a></${wrapper}>`, where `${attributes}` is each rendered attribute as ` ${name}="${value}"`.** A page is `active` for its own link alone, because `parent` means an ancestor and a page is not its own ancestor. `/` is never a parent because every URL starts with it, and a home link marked on every page marks nothing. The check is a plain prefix with no directory test, because a section's URL ends in a slash, so a link written as the URL is matches the section's pages and not a sibling whose name shares a prefix. An empty `href` fails because every URL starts with it, which would mark every page `parent` as `/` did in v1, and a link to nowhere is an author error. `null` and arrays fail the attributes check because `typeof` calls both objects, and rendering either would fail inside the loop with a message naming nothing. The copy keeps the caller's object as it was, where v1's mutation made an attributes object shared between two calls accumulate the first call's class. Attribute values are escaped, the `href` among them, because a value with a quote or an ampersand in it otherwise ends or corrupts the attribute, and the comparison against `url` uses the `href` as written so the escaping changes nothing about which class applies. The title, the wrapper, and the attribute names are printed raw because they are the author's own markup, an icon in a title as often as text. Attribute values are strings only so a value that is not one fails rather than printing `[object Object]`. An attribute named `href` fails because the anchor already carries one, and two of one attribute is markup no author means. An empty wrapper fails because `<></>` is not an element. The messages name neither the plugin nor the file, which the build attributes. Rejected: a boolean `isActive` helper in place of the markup, which would have every migrating site rewrite its navigation. Rejected: keeping v1's two quirks, which the user ruled against. Rejected: a directory-boundary test on the prefix, which a trailing-slash URL already gives for a href written as the URL is.

3. **`formatDate` formats in UTC with date-fns.** A date reaches a template as a `Date` from YAML or a string from JSON, a `Date`'s local methods read the machine's zone, and the destination must not depend on the machine (see: How a date reaches a template) (see: What a helper may rely on, and what it owes the build). v1 passed a third argument through to date-fns (see: The surface a v1 site migrates from). Weekly downloads for the week ending 2026-10-03, read from the npm downloads API on 2026-10-04: `date-fns` 121.9M, `dayjs` 88.6M, `luxon` 49.8M, `@date-fns/tz` 45.4M, `moment` 43.1M, `date-fns-tz` 13.1M. The following was run against the latest date-fns and `@date-fns/tz` (see: The date library) installed in a scratch directory on Node 24.19.0 and 22.18.0 with `TZ=America/Los_Angeles` on 2026-10-04. `format(date, formatStr, options)` takes a `Date`, a number, or a string, and its options are a locale, week settings, additional-token switches, and `in`, a context. With `{ in: tz('UTC') }`, `format` of the `Date` at `2024-01-02T00:00:00.000Z` with `MMMM d, yyyy` is `January 2, 2024`, and without it is `January 1, 2024`. The string `2024-01-02` and the number of milliseconds format the same. The `Date` at `2024-01-02T18:00:00.000Z` with `MMMM d, yyyy 'at' h:mm a` is `January 2, 2024 at 6:00 PM`. `do MMMM yyyy` is `2nd January 2024`. A format of `YYYY` throws a `RangeError` whose message starts with ``Use `yyyy` instead of `YYYY` ``, and `DD` one starting with ``Use `dd` instead of `DD` ``. The string `nope`, `undefined`, an object, and an invalid `Date` each throw `RangeError: Invalid time value`. `null` and `true` format as 1970 without throwing. An unknown zone name throws `RangeError: Invalid time value`. A helper in this shape typechecks under the repo's compiler options, run with the repo's `tsc` on 2026-10-04. The user ruled that the third argument is cut and that the zone is UTC with no option.

   **`formatDate(context, date, dateFormat, ...rest)` fails a `date` that is not a `Date`, a string, or a number with `The date must be a Date, a string, or a number, and ${String(date)} is not.`, a `dateFormat` that is not a string with `The format must be a string, and ${String(dateFormat)} is not.`, and any further argument with `formatDate takes a date and a format and nothing else.`. It returns `format(date, dateFormat, { in: utc })` with `format` from `date-fns` and `utc` as `tz('UTC')` from `@date-fns/tz`, made once at module level. What date-fns throws passes through as it is.** Pinning the zone is what makes a date-only value print as written on every machine, where v1 printed the local date and moved a post a day earlier west of Greenwich. date-fns over the runtime's `Intl` because a token string such as `MMMM d, yyyy` is what a template author writes and what v1's templates hold, and date-fns's output is a function of the value and the tokens alone. date-fns over dayjs and luxon by downloads. The value check exists because date-fns formats `null` and `true` as 1970 in silence, and a template printing 1970 for a post whose date key was misspelled is the failure the build should stop for. A string is parsed as the runtime parses it, so a date alone or one with a zone is the same on every machine, and a string holding a time with no zone is the machine's local time, which no code in the build can tell from a zoned one. date-fns's own errors pass through because a `YYYY` token's message already says what to write instead. The third argument fails rather than being ignored so a site that passed options learns it at the first build. Rejected: a `timeZone` option on the factory, which no site has asked for and which would make a committed destination depend on a setting rather than on the source alone. Rejected: a `locale` option, which no template can reach a date-fns locale object from. Rejected: `Intl.DateTimeFormat`, whose options express a style and not a layout, so `2nd January 2024` has no spelling. Rejected: passing `rest` through under the UTC pin, which keeps an argument that can override the pin or do nothing.

4. **`fileExists` asks for the handled output.** The read of handled output answers whether the build will serve a file at a path, private outputs included, and resolves a reference as every path does (see: What a helper may rely on, and what it owes the build). v1 probed the source root from any depth (see: The surface a v1 site migrates from). The user ruled that the helper reads handled output.

   **`fileExists(context, reference)` fails a `reference` that is not a string with `The reference must be a string, and ${String(reference)} is not.`, and returns `context.readOutput(reference) !== undefined`. The context's error for a reference above the source root propagates as it is.** The served output is what a template asks about before it links to or inlines a file, and a stylesheet a handler compiled from `site.scss` is found by the name it will be served under and not by the name it has in source. A private output reads as present because the file a template inlines from `_icons/` is the ordinary case for that question, and a link to one is the bust helper's error and not this helper's. A page's path reads as absent because no static file's output is there. The relative-path rule binds this helper as it binds every helper that takes a path, so a reference inside a template resolves against the template. Rejected: `readFile`, which sees pages and templates, whose existence a template has no use for, and misses a handler's renamed output. Rejected: resolving every reference from the source root as v1 did, which the templates spec forbids for a helper that takes a path.

5. **The spec.** Every statement in a spec is a commitment, with rationale inline where a decision would be reopened (see: @lab43/q conventions/specs.md, What a spec holds). Each plugin's spec is written inside the plan that builds it.

   **A new `docs/specs/helpers.md`, indexed in the agent briefing's Specs group, commits to the plugin in four sections. The plugin: the name, the three helpers, and the optionless factory of Decision 1, with its rationale. `activeLink`: the arguments, the classes and when each applies, that the parent check is a plain prefix so a section link is written as the section's URL is, trailing slash included, the copy of the attributes in their order with the class appended, the escaping of attribute values with the `href` among them and not of the title, the wrapper, or the names, the two markup shapes, and the errors, with Decision 2's rationale. `formatDate`: a `Date`, a string, or a number formatted with date-fns tokens in UTC, how a string is parsed, which errors are the helper's and which pass through from date-fns, and that there is no third argument, with Decision 3's rationale. `fileExists`: true when a static file's output is at the resolved reference, a private one included, false for a page's path, the error for a reference that is not a string, and the context's error for a reference above the source root, with Decision 4's rationale.** The spec is what the package's markers name and what a later change to the plugin is held to. Rejected: one section of the plugins spec, which is every plugin's contract and not one plugin's behavior.

6. **The site conventions.** The payload carries rules for writing a site that the build cannot catch (see: @lab43/q conventions/extensions.md, Which rules ship). `q-extension/conventions/ejs.md` has a rule, Print `_content` with the raw tag, whose rationale is that `_content` is rendered HTML, and no other doc cites that heading, checked by grep on 2026-10-04. A template can reach a `Date`'s local methods (see: How a date reaches a template), and a string with a time and no zone parses in the machine's zone where a YAML timestamp does not (see: Decision 3).

   **The EJS rule is rewritten in place as Print HTML with the raw tag: print `_content`, and what a helper that returns markup such as `activeLink` returns, with `<%- %>` and never `<%= %>`, with the rule's existing rationale. A new `q-extension/conventions/templates.md`, indexed in the briefing's `underdot` group, carries rules for writing a site's pages and templates in any engine, with one rule: never print a date through the runtime's local-time or locale methods, `toString`, `toLocaleDateString`, `getDate`, and their kin. Format it through a helper that formats in a fixed zone, such as `formatDate` from `underdot-helpers`. Write a date that is a string, as one in a JSON data file is, as a date alone or with its offset, never as a time with no zone. Rationale: the build commits to the same destination on every machine, and a date printed through the machine's zone, or a string parsed in it, breaks that commitment on the first build west of Greenwich, which the build cannot detect. A YAML date needs no offset, because YAML reads a time with none as UTC.** The EJS rule is refined rather than given a sibling because `activeLink`'s output is rendered HTML for the same reason `_content` is, and two rules with one rationale are one rule. The date rule is a convention because the build cannot tell a `toLocaleDateString` in a template from any other expression, and its audience is every site, not only one that installs the helpers plugin, which is why it names the plugin as an example. Rejected: a rule telling a site to list the helpers plugin anywhere in particular, since plugin order sequences handlers and hooks alone.

The zone stub is what turns the suite into proof of the one thing the helper exists for. Rejected: importing `bindRenderContext` into the plugin's tests, which proves the core again through a plugin.

## Out of scope

- **Recording each read as an input of the render.** Deferred to checklist step 7. `fileExists` reads through the context, so step 7 wraps it without changing the plugin.
- **Attributing a helper's error to the plugin, the template, and the line.** Deferred to checklist step 6. The helpers' messages name neither, as the plugin contract requires.
- **An existence check that reads nothing.** Deferred. `readOutput` reads a copied file from disk to answer, so `fileExists` of a large image reads the image. The render context plan and the bust plan each declined an `exists` operation because the read answers at the same cost, which holds for a handled file and not for a copy. Raise it with a measurement from a real site rather than on the cost's shape.
- **Options on the factory, a time zone, and a locale.** Declined (see: Decision 3).
