# The collections plugin

## Goal

Deliver checklist plan 6.2, the last of step 6: the fifth workspace package, `underdot-collections`, whose page hook defines a global per collection, the list of the pages under a directory, and whose helper reads a page's rendered body into a template. It is the first plugin to register a page hook, so one package proves the mechanism plan 6.1 shipped working through a real site: an archive page lists every post from a global the hook defined and embeds each post's body through the render context. After this plan a site that used v1's collection plugin builds on v2 with the edits the migration guide names, and step 6 is complete.

## Context

### What a hook and a helper may rely on, and what they owe the build

- A plugin registers at most one page hook. Hooks run in plugin order after every page is classified and before any page renders. A hook sees every page's URL, output path, source path, and frontmatter as written, the `template` directive apart, never rendered content, and changes nothing it sees. It returns the globals it defines as an object. A global a hook defines follows the rules for globals: the underscore class is reserved, and a name the configuration, a data file, another hook, or a helper already carries is a build error naming both. A listing that shows each page's content gets it at render time, through the render context (see: docs/specs/plugins.md, Page hooks). `src/plugins/register-plugins.ts:29` is `PageHook = (pages: readonly HookPage[]) => Record<string, unknown> | Promise<Record<string, unknown>>`, and `src/plugins/run-page-hooks.ts:11-16` declare `HookPage` with `sourcePath`, `outputPath`, `url`, and `frontmatter: Readonly<Record<string, unknown>>`. `src/plugins/run-page-hooks.ts:46-48` fail a returned key starting with an underscore, and `src/templates/define-globals.ts:26-41` catch every collision a hook global can have.
- `src/source-tree/walk-source.ts:46` sorts the walked paths by code unit, `src/source-tree/classify-source.ts:68-86` classify them in that order, `src/build/read-site.ts:62-72` keep that order whichever read settles first, and `src/plugins/run-page-hooks.ts:32` maps the pages in it. So the page list a hook receives is in source-path order, the same on every machine, which the plugins spec does not commit to.
- Every page has a URL: its output path with a leading slash and a trailing `index.html` removed, so `about/index.html` has `/about/` and the home page has `/`. A page `about.ejs` and a directory `about/` coexist: the page is the index of that URL space and the pages inside `about/` are its children. A directory's own page is written either as `about.ejs` beside it or as `about/index.ejs` inside it, and both have the URL `/about/` (see: docs/specs/source-tree.md, URLs) (see: docs/specs/source-tree.md, A page and a directory may share a name). `src/source-tree/classify-source.ts:61` derives the URL so.
- A helper is reachable by its name among the file's variables in every engine, bound to the render context of the file being rendered, receives that context ahead of the arguments written in the template, and returns synchronously (see: docs/specs/plugins.md, Template helpers). `src/plugins/register-plugins.ts:22` is `Helper = (context: RenderContext, ...args: unknown[]) => unknown`, so a helper narrows its own arguments.
- Reading another page's rendered body is available while a template renders, never while a page's body renders. A page body that reads another page's body is a build error naming both pages, and reading the body of a URL no page has is a build error naming the file and the URL (see: docs/specs/plugins.md, Render context). `src/plugins/bind-render-context.ts:50` is `readBody: (url: string) => string` on the context, and lines 110-119 raise the two errors, `${sourcePath} reads the body of ${url} while its own body renders, which only a template can do.` and `${sourcePath} reads the body of ${url}, but no page has that URL.`. The body a template reads is the page's own rendered body, before any template of its chain wrapped it (see: docs/specs/templates.md, Rendering the chain).
- A helper's throw is tagged with the helper's plugin where the build binds it, and a render's failure names the file that was rendering and the tagged plugin, with the engine's file and line prefixed to the message (see: docs/specs/plugins.md, Errors). `src/plugins/bind-render-context.ts:135-143` wrap each bound helper, and `src/templates/render-pages.ts:36-43` attribute the render.
- A plugin reports a failure by throwing and never writes its own name or the file into the message. An error thrown while a plugin is set up fails the run before any unit starts (see: docs/specs/plugins.md, Errors). `src/configuration/run-command.test.ts:57-58` show the command printing a configuration module's throw as its message alone, with nothing prefixed.
- The same source, configuration, and plugins produce a byte-identical destination on every run and every machine, and nothing in the output depends on how the work was scheduled. Chains render in no defined order (see: docs/specs/build.md, Determinism) (see: docs/specs/build.md, Order of work).

### What the one v1 site wrote and expects

Surveyed from the site's templates on 2026-10-05 at the user's direction, for the use case alone. The user ruled that v1's option shape binds nothing. The site configured one collection as `{ name: 'posts', directory: 'posts' }`, the pages under `source/posts/`. Each post's frontmatter holds `title`, `link`, `type`, and `date`, a YAML date, and its body is HTML. One template reads the collection: the home page's archive template, which sorts the global in place by date descending and renders a partial per post, spreading the item into the partial's data. The partial reads the frontmatter keys, `content`, the post's full body, and `slug`, `posts/welding-table`, for a sibling image at `/${slug}.jpg`. Nothing links to a post's own page, and no pagination, feed, next or previous link, or tag page exists.

### What the runtime does with a frozen collection

Run on Node 24.19.0 and on the floor, 22.18.0, on 2026-10-05. On a frozen array of two frozen objects, `sort` throws a `TypeError` whose message is `Cannot assign to read only property '0' of object '[object Array]'` on both, `toSorted` returns a new ordinary array, and spreading a frozen item into an object literal gives an ordinary object. An assignment onto a frozen item outside strict mode is ignored in silence, and EJS renders outside strict mode: on ejs 6.0.1, a template that assigns onto a frozen item's key prints the item unchanged and raises nothing.

## Decisions

1. **The package.** The naming rules, the model package, and the two-name precedent for a helper are given (see: What is already in place for a fifth package). The user ruled the helper's template-facing name `pageBody`.

   **`plugins/collections/` is the package `underdot-collections` at `2.0.0-alpha.0`, described as `Page collections for Underdot`, in the shape of `plugins/svgo/package.json` with `repository.directory` of `plugins/collections` and no `dependencies`, and a `tsconfig.build.json` identical in shape to the svgo package's. `tsconfig.solution.json` gains a reference to it. `plugins/collections/src/index.ts` exports `CollectionsOptions` and `collections(directories?: CollectionsOptions): Plugin`, which returns `{ name: 'collections', pageHook, helpers: { pageBody: readPageBody } }`. The hook's work lives in `plugins/collections/src/collect-pages.ts` as `collectPages(pages: readonly HookPage[], directories: Readonly<Record<string, string>>): Record<string, readonly CollectionItem[]>`, and the helper in `plugins/collections/src/read-page-body.ts` as `readPageBody(context: RenderContext, url: unknown): string`. Every module carries a marker naming `docs/specs/collections.md`.** The package, the factory, and the plugin take the checklist's name for the mechanism, as the other plugins take theirs. The helper is `pageBody` in a template because that is what a template author reads at the call site, and the function is `readPageBody` because a function is named for what it does, the two kept apart as `activeLink` and `renderActiveLink` are. Rejected: `readBody` for the helper, the context operation's name, which the user ruled against. Rejected: one module holding the hook and the helper, which gives a reader of one the other to read past.

2. **A collection is the pages below a directory's URL, the directory's own page excluded.** The URL rules and the two spellings of a directory's own page are given (see: What a hook and a helper may rely on, and what they owe the build). The v1 site named its collection's directory (see: What the one v1 site wrote and expects).

   **For a collection named `name` with directory `directory`, `collectPages` takes the prefix `/${directory}/` and selects every page whose `url` starts with the prefix and is not the prefix itself, at any depth below it.** Membership is by URL rather than by the page's source directory because the directory's own page can be written as `posts.ejs` beside the directory or `posts/index.ejs` inside it, and by source directory the second would be a member of its own listing while the first would not. The URL names both the same way. The directory's own page is excluded because it is the index of the URL space and not one of its children, which is what a section's listing page is. Every depth is included because a directory is a directory, and a site that nests its posts by year has nested its posts. Rejected: membership by a glob over URLs, which a trailing slash defeats, since `/posts/*` does not match `/posts/welding-table/` in minimatch's dialect, and which no site has asked for. Rejected: the direct children only, a rule a site with nested posts would have to work around and no site has asked for.

3. **The helper reads the body through the context and nothing else.** The context's `readBody`, its two errors, the body it returns, and the tagging of a helper's throw are given (see: What a hook and a helper may rely on, and what they owe the build). `fileExists` is the model of a helper over one operation (see: What is already in place for a fifth package).

   **`readPageBody(context, url)` fails a `url` that is not a string with `The URL must be a string, and ${String(url)} is not.`, and otherwise returns `context.readBody(url)`.** The context already raises the two errors a body read can fail with, naming the file and the URL, so the helper adds the one check the context's type cannot make for a JavaScript template. The helper takes the URL rather than the item because `_url` is right there on the item and a URL from anywhere else, a link in a data file say, reads the same way. Rejected: accepting an item or a URL, two shapes for one argument.

4. **An item is the page's frontmatter plus `_url`, in a frozen list of frozen items, in source-path order.** The frontmatter a hook sees, the hook order the build already produces, the URL as the page's identity, the determinism commitment, and the render order are given (see: What a hook and a helper may rely on, and what they owe the build). What the runtime does with a frozen collection is given (see: What the runtime does with a frozen collection). The v1 site's items carried `content` and `slug`, and its archive sorted the global in place (see: What the one v1 site wrote and expects). The user ruled that the collection is frozen.

   **Each item is `Object.freeze({ ...frontmatter, _url: url })`, and each collection is `Object.freeze` of the list of its items in the order the hook received the pages. `CollectionItem` is declared in `collect-pages.ts` as a readonly object with `_url: string` and any other key `unknown`. The hook returns one key per collection, the collection's name, with the empty list for a directory under which no page is. The Page hooks section of `docs/specs/plugins.md` gains, after `A hook sees every page's URL, output path, source path, and frontmatter as written.`, the sentence `The pages come in the order of their source paths, so a global built from them is the same on every machine.`** The frontmatter is the item because it is what a listing prints, and `_url` joins it under the name every template already knows the page by, with no collision possible since no frontmatter key starts with an underscore. `slug` is not carried because `_url` is the identity and the migration guide already says how a sibling path is built from it. `content` is not carried because a hook never sees rendered content, and the body is read at render time through the helper of Decision 3. The list is frozen because a collection is one global shared by every render, chains render in no defined order, and a template that sorted it in place would reorder it for every template rendered after, which no two runs need agree on. Frozen, the in-place sort fails at the template's line with the engine's report, while `toSorted` and spreading an item keep working. The items are frozen for the same reason, since an assignment onto one would reach every later render. The freeze is shallow: a nested value, a date or a list in the frontmatter, stays what YAML made it, so the spec promises the list and each item's own keys and nothing below them. Whether an engine reports the attempt is the engine's affair: EJS renders outside strict mode, so it ignores the assignment, and the freeze still keeps the change from reaching another render, which is the commitment. The order is the hook's page order, committed in the plugins spec rather than re-sorted here, because the build already sorts the pages and every hook benefits from the commitment. `src/source-tree/walk-source.test.ts` holds the sort and `src/plugins/run-page-hooks.test.ts` holds that a hook receives the pages in the order given, so the sentence commits to what two tested units already do. An empty collection is a list and not an error because the hook sees pages and nothing else, so it cannot tell a misspelled directory from a section with no pages yet, and a site before its first post has nothing to fix. Rejected: sorting the collection by URL inside the plugin, which repeats a sort the build did. Rejected: sorting by `date`, a frontmatter key no spec names. Rejected: a `sort` option, which no site has asked for and `toSorted` covers.

5. **The options are the map, checked at setup.** The factory's duty to a JavaScript site and the svgo factory's checks are given (see: What is already in place for a fifth package). The user ruled the shape: `collections({ posts: 'posts' })`.

   **`CollectionsOptions` is `Record<string, string>`, each key a collection's name, the global it defines, and each value a directory under the source root written without a leading or trailing slash, with JSDoc saying so. `collections(directories: CollectionsOptions = {})` fails a value that is not an object, `null` and an array included, with `The collections must be an object of names to directories.`, and a directory that is not a string, is empty, or starts or ends with a slash with `The directory of ${name} must be a path under the source root, written without a leading or trailing slash.`. It returns the plugin with `pageHook: (pages) => collectPages(pages, directories)`.** The map is the whole options object because a collection is a name and a directory and nothing else, and a site reads `{ posts: 'posts' }` at a glance. `collections()` is valid and defines nothing, since a site may want `pageBody` alone. The slash checks exist because the prefix is built from the directory, and a leading or trailing slash would produce a prefix no URL has. A name starting with an underscore is caught by the build, naming the plugin's page hook, so the factory does not repeat it. Rejected: the map under a named option, `{ directories }`, leaving room for options no site has asked for. Rejected: a list of names with the directory implied, under which a `blog/` directory cannot define `posts`. Rejected: v1's `{ name, directory }` object, which the user ruled binds nothing.

## Out of scope

- **Recording the helper's read as an input of the render.** Deferred to checklist step 7. The helper reads through the context, so step 7 wraps it without changing the plugin.
- **Pagination, feeds, next and previous links, and tag pages.** Declined. No site has asked for them, and a generated page is out of scope for the page type (see: docs/conventions/principles.md, A page is not its source file).
- **A sort option, or items sorted by a frontmatter key.** Declined (see: Decision 4).
