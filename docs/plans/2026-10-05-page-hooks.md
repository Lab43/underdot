# Page hooks and error attribution

## Goal

Deliver checklist plan 6.1, the first of step 6: page hooks, the mechanism a plugin defines globals with from the page list, and error attribution, the report that names the plugin, the unit, and the file when a plugin throws. Both are proven in the core with fixture plugins. After this plan a plugin registers a page hook that sees every page and returns the globals it defines, those globals reach every render under the rules every global follows, and a failure in a handler, a hook, a renderer, or a helper reports which plugin failed doing what to which file. The collections plugin of plan 6.2 is grounded in the code this plan ships.

## Context

### What the build owes a plugin that throws

- The build catches a plugin's throw and attributes it to the plugin, the unit, and the file, passing the engine's message through as it is, and a render names the file in the chain that was rendering (see: docs/specs/plugins.md, Errors). The units are handling one static file, running one page hook, rendering one page, and producing one emitted file (see: docs/specs/plugins.md, Dependencies). Run on its own, the build prints the report and exits non-zero (see: docs/specs/build.md, Errors). `src/configuration/run-command.ts:18` prints the error's message through `describeError`, `src/shared/describe-error.ts:4`, which is an Error's message and anything else as a string.

### What a hook may rely on, and what the build owes it

- A hook runs in plugin order after classification and before any render, sees every page's URL, output path, source path, and frontmatter as written, and defines globals under the rules every global follows, with a collision naming both sides (see: docs/specs/plugins.md, Page hooks) (see: docs/specs/plugins.md, Plugin identity and order). Hooks are the third phase of a build, where a name defined twice or shared with a helper is caught (see: docs/specs/build.md, Order of work) (see: docs/specs/plugins.md, Template helpers). An underscore name is reserved for a configuration global and a data variable alike (see: docs/specs/configuration.md, Globals) (see: docs/specs/templates.md, Data files).

### What the proof and the verification rest on

- The templated fixture is a site of four plugins of its own, a renderer, two with file handlers, and one with helpers, listed at `test/fixtures/templated/underdot.config.ts:7`. Its renderer prints a string as it is and any other value as JSON (`test/fixtures/templated/fixture-renderer.ts:18`). Its pages in classification order are `404.tpl`, `about.tpl`, `about/team.tpl`, `blog/hello.tpl`, `blog/index.tpl`, and `index.tpl`, which `src/build/read-site.test.ts:21` asserts. Of those only `blog/hello.tpl` and `index.tpl` set a `title` in their own frontmatter, `Hello` and `Home`, while every page renders with `title` merged from the root template's `Site` (`test/fixtures/templated/expected/about/index.html:1`). A page at the root renders through `_.tpl` alone, whose output is the four lines `test/fixtures/templated/expected/404.html:1-4` show ahead of the page's body. `about.tpl:1` is the one page body that calls the `here` helper, and `_.tpl:1` calls it too. Bodies and chains render in no defined order, and `src/build/run-units.ts:15-34` throws the first failure after starting nothing further.
- The bust fixture is a site on `underdot-ejs` and `underdot-bust`, driven on the packed packages per the driving manual's section A site on the published packages, and its templates call `bust` from `_.ejs`.

## Decisions

1. **One function attributes a plugin's throw to its unit and its plugin.** The report names the plugin, the unit, and the file, with the plugin's own message passed through as it is (see: What the build owes a plugin that throws). `src/shared/attribute-error.ts:6-7` is `attributeError(sourcePath, error)`, an error reading `${sourcePath}: ${message}` with the original as its cause, which `src/build/read-site.ts:31-38` uses for a frontmatter error and `src/templates/read-data.ts:32-37` for a JSON error. Neither is a plugin's unit.

   **A new `src/plugins/attribute-plugin-error.ts`, headed with a marker naming `docs/specs/plugins.md`, Errors, exports `attributePluginError(unit: string, pluginName: string, error: unknown): Error`, which returns `new Error(`${unit} failed in ${pluginName}: ${describeError(error)}`, { cause: error })`. The unit is a phrase the caller writes: `Handling ${sourcePath}`, `Running the page hook`, or `Rendering ${sourcePath}`, so a report reads `Handling images/logo.svg failed in svgo: …`, `Running the page hook failed in collections: …`, or `Rendering blog/_post.ejs failed in bust: …`.** The unit leads because the author reads what the build was doing before who did it, and the file sits inside the unit phrase because the hook's unit has no file. `describeError` keeps the engine's message as it is, line and context included, and the cause keeps the original for a caller that wants its stack. `attributeError` stays as it is for the build's own errors. Rejected: the plugin leading the message, which puts the actor before the act the author is looking for. Rejected: a file-prefixed shape with the plugin and unit in a parenthetical, matching the frontmatter errors, which has no file to prefix for a hook. Rejected: an error class carrying the plugin, the unit, and the file as fields for the report, which the dev server of step 8 would read into its browser report. The message is what the server shows, and the fields can be added when a reader needs them. The `PluginError` of Decision 2 is not that class: it is a tag naming the plugin alone, raised inside a render and consumed by this function, never the report itself.

2. **The build tags a helper's throw with the helper's plugin where it binds the helper.** A helper called from a template fails on the template's line, and the engine passes the error through with the line added (see: What the build owes a plugin that throws). `src/plugins/bind-render-context.ts:115-121` binds each registered helper to the context as `(...args) => helper(context, ...args)` under its name, and holds the helper's `pluginName` in the same loop. The context's own operations throw plain errors naming the file: lines 72-74 for a path above the source root, 97-103 for a body read a page makes or a URL no page has, 109-111 for an entered file that is absent. EJS adds the file and line to an error thrown while a template renders by assigning to the thrown object's `message` and `path` and rethrowing the same object, so an `Error` subclass keeps its class and its own properties through the engine, and a thrown value that is not an object loses its message entirely. Verified on ejs 6.0.1 on 2026-10-05 by compiling a template whose helper throws an `Error` subclass carrying a `pluginName` property: the caught error was the same instance, with the property intact and the message prefixed by the file, the line, and the surrounding source. The same template with a helper throwing a string surfaced an empty object.

   **`src/plugins/bind-render-context.ts` declares and exports `class PluginError extends Error`, with a `readonly pluginName: string` and a constructor `(pluginName: string, cause: unknown)` that calls `super(describeError(cause), { cause })`. The bound helper at line 119 becomes a function that calls `helper(context, ...args)` inside a `try` whose catch rethrows the error as it is when it is already a `PluginError` and otherwise throws `new PluginError(pluginName, error)`.** The build is the only party that knows which plugin a helper belongs to, and the binding is the one place its call is wrapped. The engine mutates the thrown object's message and rethrows the same object, so the tag survives into the render's catch with the engine's file and line prefixed to the message, and a thrown value that is not an object would lose its message in the engine, so wrapping it in an `Error` first keeps it. An error already tagged passes through so that the innermost plugin is named when one plugin's function reaches another's. The catch takes a synchronous throw only, because a helper returns synchronously (see: docs/specs/plugins.md, Template helpers), so a helper that returns a rejected promise is a plugin defect the renderer meets as a value. A context operation that throws inside a helper, a read above the source root say, is tagged with the helper's plugin, because that helper's call is what failed and the message already names the file. An engine that wraps a helper's throw in a fresh error drops the tag and names its own plugin, which is that engine's plugin's affair. The class lives in `bind-render-context.ts` because that module produces its values. Rejected: a `WeakMap` from error to plugin name, which hides the tag from a reader of the error and adds a module for a lookup the class does by `instanceof`. Rejected: tagging the context's own throws as the build's so a render could report no plugin, since every such throw is reached through a plugin's function, the renderer's include or a helper's read, and that plugin is the right name.

3. **A handler's throw names the static file's source path.** The unit is handling one static file, and the handler receives the output path as the handlers before it left it (see: What the build owes a plugin that throws). `src/plugins/run-handlers.ts:27-54` is `runHandlers(file, handlers)`. Line 36 awaits each matching handler with nothing around it, so a handler's throw propagates as thrown, and lines 37-47 check what the handler returned and fail naming the plugin and the glob. `src/plugins/handle-files.ts:33` calls it with the file's output path and contents, and holds the static file's `sourcePath` at line 27.

   **`runHandlers(sourcePath: string, file: HandledFile, handlers: RegisteredHandler[])` takes the source path first. The `await handle(current)` sits in a `try` whose catch throws `attributePluginError(`Handling ${sourcePath}`, pluginName, error)`. The checks on what the handler returned stay outside the `try`, since they are the build's errors and already name the plugin and the glob. `handleFiles` passes the file's `sourcePath` through.** The source path is the file the author edits, and a handler that failed on a path an earlier handler renamed still failed handling that source file. The engine's message names the renamed path where the plugin handed it over, as the SVGO plugin does, so both names reach the author. Rejected: tagging the error inside `runHandlers` and composing the message in `handleFiles`, two steps for what one parameter does.

4. **A render names the file in the chain that was rendering, and the plugin whose function threw.** For a render the report names the file that was rendering when the throw happened (see: What the build owes a plugin that throws). `src/templates/render-pages.ts:34` awaits `page.render` and line 46 awaits `template.render`, each with nothing around it. `src/source-tree/classify-source.ts:6-25` give `PageFile` and `TemplateFile` a `render: Renderer`, set at line 78 from the registry's entry, and line 66 types the renderer map as `ReadonlyMap<string, { render: Renderer }>`, so a page carries the function and not the plugin that registered it. `src/plugins/register-plugins.ts:40-43` is `RegisteredRenderer { pluginName, render }`, what the registry holds per extension. `test/helpers/make-page.ts` and `test/helpers/make-template.ts` build test values with `render: renderBody`, and `src/source-tree/classify-source.test.ts:7-8`, `src/build/read-site.test.ts:12`, and `src/plugins/handle-files.test.ts:14` build four renderer maps of `{ render: renderBody }`, the empty one at `classify-source.test.ts:8` typed `{ render: typeof renderBody }`. `src/templates/render-pages.test.ts` passes `render` to `makePage` and `makeTemplate` at fifteen sites, twelve as `render:` overrides at lines 90, 91, 113-115, 138-140, 148-150, and 158 and three as the shorthand `render` at lines 129-131, and `src/source-tree/classify-source.test.ts` asserts `render: renderBody` on classified files at five, lines 57, 65, 71, 79, and 80. A step with one caller stays inline and a helper is extracted only for a second caller, and a function enforcing a section of a second spec inside its file carries that section's marker at its head (see: docs/conventions/principles.md, Linear functions). `src/templates/render-pages.test.ts:156-161` is the test "a renderer's throw rejects with that error", which asserts that the thrown error comes out by identity.

   **`PageFile` and `TemplateFile` carry `renderer: RegisteredRenderer` in place of `render: Renderer`, set at classification from the registry's entry, and `classifySource` types its map as `ReadonlyMap<string, RegisteredRenderer>`. `renderPages` gains a local `render(file: Page | Template, context: RenderContext): Promise<string>` that awaits `file.renderer.render(file.body, context)` inside a `try` whose catch throws `attributePluginError(`Rendering ${file.sourcePath}`, pluginName, error)`, where `pluginName` is `error.pluginName` when the error is a `PluginError` and `file.renderer.pluginName` otherwise. `renderBody` and `renderChain` call it in place of their direct awaits, so a body's failure names the page and a template's names that template. The function carries a marker naming `docs/specs/plugins.md`, Errors. `test/helpers/make-page.ts` and `make-template.ts` default `renderer` to `{ pluginName: 'fixture', render: renderBody }`, every `render` passed in `render-pages.test.ts` becomes `renderer: { pluginName: 'fixture', render }`, the four renderer maps become maps of `RegisteredRenderer` values with `pluginName: 'fixture'`, the empty one typed so, and the classify expectations assert `renderer` as the map's entry.** One field carrying the registration as the registry made it keeps the name with the function, so nothing pairs them again downstream. The local function exists because two call sites would otherwise repeat the catch. A renderer's own throw, EJS's syntax error say, carries no tag and names the renderer's plugin, which is the plugin whose code was running. Rejected: a `pluginName` field beside `render` on the page, two fields for one registration.

5. **A plugin registers one hook under `pageHook`, a function the build calls with the list of every page, whose returned object's keys become globals.** A plugin registers a page hook, hooks run in plugin order, and a hook defines globals (see: What a hook may rely on, and what the build owes it). `src/plugins/register-plugins.ts:23-38` is `Plugin`, with `name`, `renderers`, `helpers`, and `handlers`, each registered under a key: the extension, the name, or the glob. Lines 60-64 are `Registry`, and lines 69-125 are `registerPlugins`, which checks each registration's shape, so a helper that is not a function fails with `The helper ${name} of ${pluginName} is not a function.`. `src/build/read-site.ts:14-27` declare `Page` as `PageFile` plus `frontmatter`, `template`, and `body`, where `frontmatter` holds the keys that become variables and `template` holds the directive apart (`src/templates/parse-frontmatter.ts:53-62`). A type is declared in the module whose function produces its values, as `src/plugins/register-plugins.ts:5` imports `HandledFile` from `src/plugins/run-handlers.ts`, which produces them (see: docs/conventions/structure.md, Types), and `src/index.ts:10` re-exports the types a site imports.

   **`Plugin` gains `pageHook?: PageHook`, with `PageHook = (pages: readonly HookPage[]) => Record<string, unknown> | Promise<Record<string, unknown>>` declared in `src/plugins/register-plugins.ts` beside the other registration types. `HookPage { sourcePath: string; outputPath: string; url: string; frontmatter: Readonly<Record<string, unknown>> }` is declared in `src/plugins/run-page-hooks.ts`, which produces its values, and imported into `register-plugins.ts` as `HandledFile` is. `registerPlugins` collects hooks into `Registry.hooks: RegisteredHook[]` with `RegisteredHook { pluginName: string; hook: PageHook }`, in plugin order, under its own `if (plugin.pageHook !== undefined)`, and fails a value that is not a function with `The page hook of ${pluginName} is not a function.`. `src/index.ts` re-exports `PageHook` and `HookPage`.** A hook has no key to register under, and one hook per plugin makes plugin order the whole order, with nothing to decide inside a plugin. A plugin with two things to compute computes both in one function. Returning an object is pure data out, which is what step 7 caches by the hook's inputs, and a return the build checks catches a forgotten `return` the way a handler's array check does. `frontmatter` is the page's variable keys, the `template` directive apart, because the directive names a file and not a value, and the collections plugin selects by URL. Rejected: a `defineGlobal` callback handed to the hook, under which a hook that defines nothing is silent and the result is a side effect rather than a value. Rejected: a `hooks` list per plugin, which adds an order inside a plugin that nothing needs.

6. **Hooks run one after another in plugin order, over one page list, and their globals come back as values.** Hooks run in plugin order, between file handling and body rendering (see: What a hook may rely on, and what the build owes it). Nothing in the output depends on the order files were read or how the work was scheduled (see: docs/specs/build.md, Determinism). `src/source-tree/walk-source.ts:44` sorts the walked paths by code unit, and `src/source-tree/classify-source.ts:68-86` classifies them in that order, so the page list is the same on every machine. `src/build/build.ts:20-32` is the pipeline: the registry at line 21, `readSite` at line 25, `handleFiles` at line 26, and `renderPages` at line 30 with `defineGlobals(globals, dataVariables, helpers)` inline in its arguments. `src/shared/is-object.ts:4` is `isObject`, true for a plain object and false for an array. `src/templates/read-data.ts:51-56` reject a data variable whose name starts with an underscore in the module that reads it, and `src/configuration/resolve-configuration.ts:93-98` reject a configuration global's the same way.

   **A new `src/plugins/run-page-hooks.ts`, headed with a marker naming `docs/specs/plugins.md`, Page hooks, exports `runPageHooks(pages: readonly HookPage[], hooks: RegisteredHook[]): Promise<HookGlobal[]>` and declares `HookGlobal { name: string; pluginName: string; value: unknown }`. It maps the pages once to `HookPage` values carrying each page's `sourcePath`, `outputPath`, `url`, and `frontmatter` object and nothing else, then awaits each hook in turn with that one list. The build's `Page` values satisfy the parameter's type as they are, so the module imports nothing from `src/build/`. A hook's throw is caught and rethrown through `attributePluginError('Running the page hook', pluginName, error)`. A result that is not an object by `isObject` fails with `The page hook of ${pluginName} must return an object of globals.`. A key starting with an underscore fails with `The global ${name} from the page hook of ${pluginName} starts with an underscore, which is reserved.`. Every other own entry becomes a `HookGlobal` with the plugin's name, in the order the hooks ran and the keys were defined. `src/build/build.ts` takes `hooks` from the registry, calls `runPageHooks(site.pages, hooks)` after `handleFiles` and before `renderPages`, holds the result as `hookGlobals`, and hands it to `defineGlobals`.** A hook reads memory and nothing else, so running two at once saves nothing, and awaiting each in turn is the order the spec promises. The unit the spec names is running one page hook, so the catch sits around the one call. The underscore check sits here because the module that defines a global checks its name, while every collision waits for `defineGlobals`, the one place every global is known. The page objects are the build's own, typed read-only, because a hook sees pages and never changes them, and copying every frontmatter per hook would buy a mutating plugin nothing the type does not already refuse. Rejected: running hooks through `mapUnits`, which runs them at once and gives up the order the spec promises for no gain.

7. **Hook globals join `defineGlobals`, which catches every collision.** Every global is defined once hooks have run, and a name a hook defines that the configuration, a data file, another hook, or a helper already carries is an error naming both (see: What a hook may rely on, and what the build owes it). `src/templates/define-globals.ts:9-33` is `defineGlobals(globals, dataVariables, helpers)`. It copies the configuration's globals, adds each data variable under its name failing a collision with `Both the globals setting and ${sourcePath} define ${name}.`, then fails a helper name the globals or a data variable carry with `Both the globals setting and the plugin ${pluginName} define ${name}.` and `Both ${sourcePath} and the plugin ${pluginName} define ${name}.`.

   **`defineGlobals(globals, dataVariables, hookGlobals, helpers)` takes the hook globals third. After the data variables it adds each hook global under its name, failing with `Both the globals setting and the page hook of ${pluginName} define ${name}.` when the configuration carries the name, `Both ${sourcePath} and the page hook of ${pluginName} define ${name}.` when a data variable does, and `Both the page hooks of ${other} and ${pluginName} define ${name}.` when an earlier hook global does. The helper loop then also fails a helper name a hook global carries with `Both the page hook of ${pluginName} and the plugin ${helperPluginName} define ${name}.`.** The messages name both sides in the shape the existing ones do, with the hook's side spelled as the plugin's page hook so a plugin with a helper and a hook of one name reads as two things. Rejected: catching hook collisions in `runPageHooks`, which would have to be handed the configuration's globals and the data variables that `defineGlobals` already holds.

## Out of scope

- **Recording a hook's inputs and rerunning it only when a page was added, removed, or changed.** Deferred to checklist step 7. The hook receives values and returns values, so step 7 wraps the call without changing the plugin surface.
- **The collections plugin.** Deferred to plan 6.2, grounded in the hook this plan ships.
- **Emitted files and the producer unit's attribution.** Deferred to checklist step 9, the first plugin that emits.
- **Fields on the attributed error for the dev server's browser report.** Deferred to checklist step 8, which is the first reader of anything but the message (see: Decision 1).
- **Naming a line in a helper's failure beyond what the engine reports.** Declined. The engine's rewrite carries the template's line, and the build knows no line of its own.
