# The SVGO plugin

## Goal

Deliver checklist plan 5.4, the last of step 5: the fourth workspace package, `underdot-svgo`, whose file handler optimizes every SVG under the source root with svgo and whose helper inlines an optimized SVG into a page. It is the first plugin to register both a handler and a helper, so one package proves the two mechanisms working together: the handler's output is what the helper reads, and a private icon is optimized, inlined, and never written. After this plan a site that used v1's `underdot-svgo` builds on v2 with the edits the migration guide names.

## Context

### What a handler and a helper may rely on, and what they owe the build

- A plugin registers a file handler with a glob. Every static file whose path matches passes through it, underscore-prefixed files and files inside underscore-prefixed directories included. The handler receives the file's output path as the handlers before it left it and its contents as bytes, returns zero or more files with contents as text or bytes, and may return asynchronously. What the last handler returns is what the build writes, subject to the underscore rule, and all file handling completes before any page renders (see: docs/specs/plugins.md, File handlers) (see: docs/specs/source-tree.md, Underscore prefix). `src/plugins/register-plugins.ts:14` is `FileHandler = (file: HandledFile) => HandlerOutput[] | Promise<HandlerOutput[]>`, `src/plugins/run-handlers.ts:10-21` declare `HandledFile` with `contents: Buffer` and `HandlerOutput` with `contents: string | Uint8Array`, and `src/plugins/handle-files.ts:33` reads a matched file from disk as bytes before the handlers run.
- A helper is reachable by its name among the file's variables in every engine, bound to the render context of the file being rendered, receives that context ahead of the arguments written in the template, and returns synchronously (see: docs/specs/plugins.md, Template helpers). `src/plugins/register-plugins.ts:21` is `Helper = (context: RenderContext, ...args: unknown[]) => unknown`, so a helper narrows its own arguments.
- A read of handled output takes a reference resolved as a file read is, a relative one against the directory of the file being rendered and a slash-prefixed one from the source root. It yields the output as the build writes it, a private output included, no value for a path no static file's output has, a page's path included, and a build error for a path above the source root (see: docs/specs/plugins.md, Render context) (see: docs/specs/templates.md, Relative paths). `src/plugins/bind-render-context.ts:88-94` is `readOutput`, which returns handled contents from memory.
- A plugin keeps state between a handler and a helper through the context's reads, never in memory (see: docs/specs/plugins.md, Dependencies).
- A plugin reports a failure by throwing and never writes its own name or the file into the message. What the engine a plugin wraps reports passes through as it is, the file and line of a failure included. An error thrown while a plugin is set up fails the run before any unit starts (see: docs/specs/plugins.md, Errors). `plugins/ejs/src/render-ejs.ts:47` hands EJS the file's path as `filename`, so the engine's report names the file.
- The same source, configuration, and plugins produce a byte-identical destination on every run and every machine (see: docs/specs/build.md, Determinism).

### What a v1 site wrote and expects

The v1 plugin is `underdot-svgo` 1.0.1, read from its repository on 2026-10-05 at the user's direction, for its surface alone. It depended on `svgo` 1 and took `{ rule = '**/*.svg', ...config }`, handing `config` to svgo's constructor, so a site wrote svgo 1's options, such as `plugins: [{ removeViewBox: false }]`, beside `rule`. It registered a file handler on `rule` that optimized the file with its path, stored the result in a table keyed by the path, and returned the file at the same path. It registered a helper `svgo(src)` that resolved a relative `src` against the page's directory and an absolute one from the source root, and returned the table's entry, `undefined` when there was none.

### What svgo makes of a file and a configuration

The following was read from the registry and run against svgo installed in a scratch directory on Node 24.19.0 and 22.18.0 on 2026-10-05.

- `svgo` 4.1.0 is the latest, an ES module with `engines` of Node 16 and seven dependencies. Weekly downloads for the week ending 2026-10-04: 46.9M. It ships its own types, and its `exports` map resolves them under the repo's compiler options: a file importing `optimize` and the types `Config` and `PluginConfig` from `svgo` typechecks with the repo's `tsc` under `tsconfig.base.json`.
- `optimize(input: string, config?: Config): { data: string }` is synchronous. `Config` carries `path`, `multipass`, `floatPrecision`, `plugins: PluginConfig[]`, `js2svg`, and `datauri`. A `PluginConfig` is a builtin plugin's name, an object with a `name` and optional `params`, or a custom plugin object.
- With no `plugins`, svgo runs `preset-default`, which in version 4 keeps `viewBox` and `<title>` and removes the XML declaration, comments, `<desc>`, editor metadata, and empty groups. The output has no trailing newline, and svgo's own command writes none either.
- The icon: `<?xml version="1.0" encoding="UTF-8"?>`, `<!-- Generator: Sketch 3.0 -->`, `<svg xmlns="http://www.w3.org/2000/svg" width="24px" height="24px" viewBox="0 0 24 24" version="1.1">`, `  <title>Mail</title>`, `  <desc>Created with Sketch.</desc>`, `  <g id="icon" stroke="none" fill="#000000">`, `    <path d="M2,4 L22,4 L22,20 L2,20 Z" id="envelope"></path>`, `  </g>`, `</svg>`, each line followed by a newline, optimizes to `<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24"><title>Mail</title><path d="M2 4h20v16H2Z"/></svg>`, the same on both Node versions, on two runs, with and without `multipass`, and unchanged when optimized again. With `plugins: ['preset-default', 'removeDimensions']` the `width` and `height` go. With `plugins: []` nothing but the serialization changes.
- The logo: `<?xml version="1.0" encoding="UTF-8"?>`, `<svg xmlns="http://www.w3.org/2000/svg" width="100" height="40" viewBox="0 0 100 40">`, `  <!-- The wordmark -->`, `  <rect x="0" y="0" width="100" height="40" fill="#FF0000"/>`, `</svg>`, each line followed by a newline, optimizes to `<svg xmlns="http://www.w3.org/2000/svg" width="100" height="40" viewBox="0 0 100 40"><path fill="red" d="M0 0h100v40H0z"/></svg>`.
- A file svgo cannot parse throws a `SvgoParserError`, an `Error`, whose message is `<input>:1:49: Unexpected close tag` for `<svg xmlns="http://www.w3.org/2000/svg"><g></svg>`, and `_icons/broken.svg:1:49: Unexpected close tag` when `path` is `_icons/broken.svg`.
- `svgo` 1.3.2, v1's library, removes `viewBox` and `<title>` by default, and keeps one with `plugins: [{ removeViewBox: false }]`, a per-plugin object with a boolean, the shape svgo 4 no longer takes.
- A `plugins` value that is not an array throws `malformed config, \`plugins\` property must be an array.`. An unknown name, as a string or in an object, throws `Unknown builtin plugin "nope" specified.`, and an object with no name throws `Plugin name must be specified`. An entry of `42` throws `Cannot read properties of null (reading 'params')`, and an entry of `null` prints a warning to stderr and is ignored. Each is raised by `optimize`, so a wrong configuration is found by the first optimization and not by the call that made it.

## Decisions

1. **The package.** The naming rules and the model package are given (see: What is already in place for a fourth package). The v1 package, plugin, and helper were all `svgo` (see: What a v1 site wrote and expects).

   **`plugins/svgo/` is the package `underdot-svgo` at `2.0.0-alpha.0`, described as `SVG optimization for Underdot`, in the shape of `plugins/helpers/package.json` with `repository.directory` of `plugins/svgo` and `svgo` at `^4.1.0` as its one dependency, and a `tsconfig.build.json` identical in shape to the helpers package's. `tsconfig.solution.json` gains a reference to it. `plugins/svgo/src/index.ts` exports `SvgoOptions` and `svgo(options?: SvgoOptions): Plugin`, which returns `{ name: 'svgo', handlers: { '**/*.svg': handler }, helpers: { inlineSvg } }`. The handler lives in `plugins/svgo/src/optimize-svg.ts` as `optimizeSvg(file: HandledFile, config: Config): HandlerOutput[]` and the helper in `plugins/svgo/src/inline-svg.ts` as `inlineSvg(context: RenderContext, reference: unknown): string`. Every module carries a marker naming `docs/specs/svgo.md`.** The helper is `inlineSvg` rather than v1's `svgo`, because a function is named for what it does, as a verb phrase, and the helper inlines an SVG the handler already optimized, so `svgo` at a call site reads as running the optimizer on the reference. The user ruled the rename worth one find-and-replace per migrating site, as the bust plugin's rename of `busted` was. The plugin and factory take the package's name, as the bust plugin's do, since the package is the optimizer. The two modules are named for what each function does. Rejected: `svgo` for the helper, which names the tool and not the action. Rejected: `svg`, a noun saying nothing of inlining, and `inline`, saying nothing of SVG. Rejected: one module holding the handler and the helper, which gives a reader of one the other to read past.

2. **The handler optimizes in place and hands svgo the path.** The handler contract, the pass-through of the engine's report, and the EJS plugin's handing of the path are given (see: What a handler and a helper may rely on, and what they owe the build), and so are svgo's synchronous, deterministic `optimize` and the error it raises with and without `path` (see: What svgo makes of a file and a configuration). The user ruled that the glob is fixed at `**/*.svg`, with no `rule` option.

   **`optimizeSvg` returns one file at the file's own `outputPath` whose contents are `optimize(file.contents.toString('utf8'), { ...config, path: file.outputPath }).data`, svgo's output as it is, with no newline appended. What svgo throws passes through as it is.** The output stays at the same path because an optimized SVG is the same file smaller, so every link and every helper reference keeps working. Handing svgo the path is what makes a parser error name the file and the line, which is the engine's report the plugin contract passes through, and it is what gives a path-keyed plugin a site adds, such as `prefixIds`, a prefix from the file's name alone, the same on every machine. The output is written as svgo gives it, newline and all, because a byte the optimizer did not produce is a byte the site did not ask for, and svgo's own command writes none. The glob is fixed because an SVG a site wants left unoptimized is a need no site has stated, and the bust plugin dropped its rule on the same ground. Rejected: a `rule` option, which the user ruled against. Rejected: a table of optimized SVGs for the helper to read, v1's design, which the plugin contract forbids because state the build cannot see hides the file from the dependency tracking step 7 adds.

3. **The option is svgo's plugin list, checked at setup.** An error thrown while a plugin is set up fails the run before any unit starts, and a factory checks its options for a JavaScript site (see: What a handler and a helper may rely on, and what they owe the build) (see: What is already in place for a fourth package). svgo raises every configuration error from `optimize`, and two ill-shaped entries get a message naming nothing or a warning (see: What svgo makes of a file and a configuration). v1 passed svgo 1's whole configuration through (see: What a v1 site wrote and expects). The user ruled that the factory takes `plugins` alone, defaulting to `preset-default`, and that `prefixIds` is not in the default list.

   **`SvgoOptions` is `{ plugins?: PluginConfig[] }` with `PluginConfig` imported as a type from `svgo`, and its JSDoc says the list replaces svgo's default of `['preset-default']`. `svgo({ plugins = ['preset-default'] }: SvgoOptions = {})` fails a `plugins` value that is not an array with `The plugins option must be an array.` and an entry that is neither a string nor an object whose `name` is a string with `Each plugins entry must be a plugin name or an object with a name.`. It then makes `config` as `{ multipass: true, plugins }` and calls `optimize('<svg xmlns="http://www.w3.org/2000/svg"/>', config)` once, so what svgo throws for a name it does not know fails the factory call. The handler is `(file) => optimizeSvg(file, config)`.** The plugin list is the one setting that changes what an SVG becomes, and a site that cannot change it cannot keep a `<desc>` the preset drops or add the `prefixIds` an inlined icon with a gradient needs, so it is the one option. It is typed as svgo's own `PluginConfig[]` so a site's configuration is checked against the names and parameters svgo accepts, in the editor, with the plugin declaring nothing svgo already declares. The shape check exists for a JavaScript site, because svgo answers a number with a message naming nothing and `null` with a warning the build never sees. The one optimization at setup is what moves svgo's own check of the names to the configuration load, where an unknown name fails once and before any file, rather than on the first SVG, which a site with none would never reach. `multipass` is on with no option because a second pass only finds what the first left, the output is still a function of the file and the list, and a site has no reason to ask for less. `preset-default` alone is the default because `prefixIds` prefixes class names as well as ids, which breaks an icon styled from the page's stylesheet, and v1 did not prefix. Rejected: passing svgo's whole `Config` through as v1 did, because `path` is the build's, `datauri` would make the handler's output something the helper cannot inline, and the spec would commit to whatever each remaining option means. Rejected: no options, as the EJS plugin has, which leaves a site whose icon the preset breaks with no lever. Rejected: `preset-default` followed by `prefixIds` as the default, which the user ruled against. *(deviation: at the local gate the user reversed that ruling on the evidence that every v1 site configures `inlineStyles: false`, `removeViewBox: false`, `prefixIds: true`, and `removeTitle: false`. The default is now `[{ name: 'preset-default', params: { overrides: { inlineStyles: false } } }, 'prefixIds']`. svgo 4's preset keeps `viewBox` and `<title>` on its own, so the other two settings need no counterpart. The spec's Options section, the factory, its tests, and the migration guide's entry carry the change.)*

4. **The helper inlines the handled output and fails for a missing file.** The read of handled output resolves a reference as every path does, yields a private output, and yields no value where no static file's output is (see: What a handler and a helper may rely on, and what they owe the build). v1 resolved against the page and returned `undefined` for a path it had not optimized (see: What a v1 site wrote and expects).

   **`inlineSvg(context, reference)` fails a `reference` that is not a string with `The reference must be a string, and ${String(reference)} is not.`, reads `context.readOutput(reference)`, so the context's error for a reference above the source root propagates as it is, fails no value with `No static file's output is at ${reference}.`, and otherwise returns the output as UTF-8 text.** The handled output is the optimized SVG, because the handler ran before any page rendered and left its output at the file's own path, so the helper reads through the context and keeps no table of its own. A private output is the ordinary case, since a site keeps its inlined icons under `_icons/` so the raw files are never written. A missing file is an error rather than nothing printed, because a page with a hole where an icon was is a failure the build should stop for, and v1's silence hid it until someone looked at the page. A relative reference resolves against the file being rendered, as every path-taking helper's does. The helper checks no extension and inlines whatever output the reference names, because the handler leaves every SVG at its own path, so an output at a `.svg` path is optimized, and a reference to anything else is the author's deliberate act. The string message is `fileExists`'s and the absent message is `bust`'s, each for the same condition. Rejected: returning an empty string for a missing file, which is v1's silence. Rejected: failing a reference whose path does not end in `.svg`, a check against a case no site has written.

The helper: `inlineSvg(reference)` returns the optimized SVG at the reference as text, resolved as a read through the context is, a private output included; a reference that is not a string, and one at which no static file's output is, a page's path included, are errors; a reference above the source root fails by the context's rule, with Decision 4's rationale. Options: the one option, `plugins`, svgo's plugin list defaulting to `preset-default`, replacing the default rather than extending it; a value that is not an array, an entry that is neither a name nor an object with a name, and a name svgo does not know are errors raised when the configuration loads, the last with svgo's own message; `multipass` is on; the factory takes no other option, with Decision 3's rationale.** The spec is what the package's markers name and what a later change to the plugin is held to. ## Out of scope

- **Recording each read as an input of the render.** Deferred to checklist step 7. The helper reads through the context, so step 7 wraps it without changing the plugin.
- **Attributing a handler's or helper's error to the plugin, the unit, and the file.** Deferred to checklist step 6. The helper's messages name neither, as the plugin contract requires, and the handler's error names the file only because svgo wrote it.
- **An attributes argument on the helper, merging a class or `aria-hidden` onto the inlined root.** Declined. v1 had none, and a site adds attributes by editing the icon.
- **`rule`, `multipass`, and svgo's other options.** Declined (see: Decisions 2 and 3).

## Phases
