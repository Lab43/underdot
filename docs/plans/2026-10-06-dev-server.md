# Dev server

## Goal

Deliver checklist step 8: `underdot dev`. The command builds the site, serves the destination on a local port, rebuilds when a source file changes, reloads the configuration when it changes, and shows every connected browser that a build is running, that it failed and why, or that it succeeded by reloading the page. After this plan a site's `dev` script is `underdot dev`, a script can run a session with the exported `dev` function, and the `rewrites` setting the configuration spec names is accepted and applied.

## Context

### The spec sections governing the territory

- `docs/specs/dev-server.md`, every section: one full build, then serving and watching until stopped, with the session as the scope of incremental builds. Serving whether or not the first build succeeded. Watching every file under the source root and the configuration file, with changes during a build held into one build. Rewrites first, then directory `index.html`, the slash redirect, `404.html` with a 404 status, headers forbidding caching, HTTPS from `localhost.pem` and `localhost-key.pem`, and port 3000 or the next free one. A script in every served HTML response that reloads on success and is never in the destination. Build status shown in the browser and the failure report in the browser and the terminal.
- `docs/specs/configuration.md`, Rewrites: pairs of a glob and the path to serve, applied by the dev server before looking for a file and ignored by a build. Commands: `underdot dev` takes a port and an HTTPS option, and both commands take a configuration path. Programmatic use: the session is exported as a function taking a configuration, doing what the command does, and several sessions may run at once on different ports. The configuration file: the configuration is data, so a session can reload it.
- `docs/specs/build.md`, Incremental builds: the first build of a session runs every unit, and a configuration change invalidates everything. Errors: a build run by a session reports its failure to the session, which builds again on the next change. Destination: a failed build leaves what it wrote.
- `docs/specs/source-tree.md`, Underscore prefix and Output paths: no output path has a segment starting with an underscore, and a page named `404` at the root is written to `404.html`.
- `docs/specs/plugins.md`, Errors: a plugin never terminates the process, so a thrown error reaches the session as a rejection.

### What every decision honors

- Coverage is held at 100% on every column on every run (source: docs/conventions/testing.md, Coverage), so a branch a decision adds has a test or a mock in the phase that adds it.
- A module enforcing a spec lives in the directory named after that spec and its marker names that spec (source: docs/conventions/structure.md, Directories).
- Every runtime fact below was verified on 2026-10-06 on Node 24.19.0 and on the floor, Node 22.18.0, on macOS, and where Linux is named, in Docker on the `node:22.18.0` and `node:24` images.

## Decisions

1. **`rewrites` is an object from glob to path, both written with a leading slash, matched in listed order.**

   The spec's Rewrites section states pairs and nothing about their shape or order. `Configuration` at `src/configuration/resolve-configuration.ts:7-13` has no `rewrites`. `settingNames` at `resolve-configuration.ts:26` is the one place a setting is declared known, and `checkSettings` at `resolve-configuration.ts:69-99` holds each setting's shape check with its own error. `matchGlob` at `src/shared/match-glob.ts:10` matches a path against a glob in minimatch's dialect, in dot mode. The collections plugin's options are an object from name to directory (source: docs/specs/collections.md, Options). A JavaScript object keeps its string keys in insertion order unless a key is a canonical array index, and a key starting with a slash never is.

   `Configuration` gains `rewrites?: Record<string, string>`, `ResolvedConfiguration` gains `rewrites: Record<string, string>` defaulting to `{}`, and `settingNames` gains `rewrites`. `checkSettings` rejects a `rewrites` that is not an object with `The rewrites setting must be an object.`, a value that is not a string with `The rewrite for ${glob} must be a string.`, and a glob or path that does not start with a slash with `The rewrite glob ${glob} must start with a slash.` or `The rewrite path ${path} for ${glob} must start with a slash.`. The dev server matches a request's path against each glob in the object's order with `matchGlob` and serves the first match's path in place of the request's. `docs/specs/configuration.md`, Rewrites, gains one sentence stating the shape, the leading slash on both sides, and that the first listed match wins. The site-facing conventions in `q-extension/conventions/configuration.md` rule on how a configuration is written, not on which settings exist, so they change nothing.

   An object reads as the pairs the spec names, and it is the shape a site already writes for a plugin's map. A request path starts with a slash, so a glob that lacks one matches nothing, and a path that lacks one has no meaning under the destination. Both are errors because a rewrite that silently never fires is the misfire the unknown-setting rule exists to prevent. First match wins because a site writes its specific rule before its general one, as a server's rules are read. Rejected: an array of two-element arrays, which is the literal reading of pairs and which no other setting looks like.

2. **`dev` is a second subcommand with two options of its own, and a build that is given them is a usage error.**

   `parseCommand` at `src/configuration/parse-command.ts:14-27` parses with `parseArgs` in strict mode, one option `config`, and accepts `build` alone. `runCommand` at `src/configuration/run-command.ts:27-36` prints a usage error with the usage line at `run-command.ts:9` and dispatches to `runBuildCommand` at `run-command.ts:13-21`. The shim `src/underdot.ts` assigns the returned status to `process.exitCode`. `parseArgs` with `port` as a string option and `https` as a boolean option, strict, with positionals allowed, parses `dev --port 4000 --https` as `{ port: '4000', https: true }`, parses `--port=abc` as the string `abc`, throws `ERR_PARSE_ARGS_INVALID_OPTION_VALUE` with `Option '--https' does not take an argument` for `--https=false`, and parses `build --https`, since the parser knows no subcommands.

   `Command` becomes a union: `{ name: 'build'; configurationPath: string | undefined }` and `{ name: 'dev'; configurationPath: string | undefined; port: number | undefined; https: boolean }`. `parseCommand` adds `port` as a string option and `https` as a boolean option to `parseArgs`. For `dev`, a `port` that is not a string of decimal digits naming an integer from 0 to 65535 throws `The port must be an integer from 0 to 65535, not ${value}.`. For `build`, either option present throws `The --${option} option belongs to dev.`. The usage line becomes two lines:

   ```
   Usage: underdot build [--config <path>]
          underdot dev [--config <path>] [--port <n>] [--https]
   ```

   `runCommand` dispatches on `name`. The migration guide already tells a site to run `underdot dev`, `--port <n>`, and `--https`, so it needs no entry.

   The parser knows no subcommands, so the command checks which options belong to which. Port 0 is accepted because it asks the operating system for a free port, which is what the tests use to run sessions in parallel without colliding, and it is a port given explicitly, so the spec's rule that an explicit port is taken or an error holds for it unchanged. Rejected: a parsing dependency, which buys a second vocabulary for two subcommands and three options the runtime's parser already handles.

3. **The configuration file is located once, and the loader takes the located file and a version.**

   `loadConfiguration(path?)` at `src/configuration/load-configuration.ts:46-49` finds the file in the working directory or checks the given path, through `findConfigurationFile` at `load-configuration.ts:20-36` and `checkConfigurationFile` at `load-configuration.ts:38-44`, then imports it through `importDefault` with no version. `importDefault` at `src/shared/import-default.ts:8-15` takes a version that goes on the file URL's query, and a URL with a new query loads the file as it stands, which `src/shared/import-default.test.ts` proves by rewriting a module and importing it again under a new version. The session watches the configuration file and reloads it, so the command must know which file was loaded.

   A new `src/configuration/locate-configuration.ts`, headed with a marker naming `docs/specs/configuration.md`, The configuration file, exports `locateConfiguration(path?: string): Promise<string>`, holding `findConfigurationFile` and `checkConfigurationFile` as they are. `loadConfiguration` becomes `loadConfiguration(file: string, version?: string)`, importing the file through `importDefault(file, version)` and resolving under `dirname(file)`. `runBuildCommand` calls `loadConfiguration(await locateConfiguration(configurationPath))`. The tests of the search move to `src/configuration/locate-configuration.test.ts`.

   Two callers need the located path, the build command and the dev command, so the search is extracted rather than copied. The version is the dev command's: each reload passes a new one so the module cache yields the file as it stands. Each version leaves its module in the cache for the life of the session, one small module per save, bounded by the saves a session makes.

4. **The server listens on the given port, or on 3000 and then the next free port, on every interface.**

   `http.createServer().listen(port)` on a port another server holds emits an error with `code: 'EADDRINUSE'`, and `listen(0)` binds an OS-chosen port that `server.address()` reports. A server that failed to listen can be told to listen again. Without a host, the runtime binds the unspecified address, every interface, and a server bound that way answers a request to the machine's own network address, verified on this machine. The spec's Serving section says the session serves locally on a local port. `networkInterfaces` from `node:os` lists each interface's addresses with `family` and `internal`.

   A new `src/dev-server/listen.ts`, headed with a marker naming `docs/specs/dev-server.md`, Serving, exports `listen(server: Server, port: number | undefined): Promise<number>`, where `Server` is `node:http`'s and `node:https`'s common type. Each attempt calls `server.listen(port)` inside a promise that attaches one `listening` listener and one `error` listener and removes both when either fires, so an attempt leaves no listener behind. Given a port it attempts once and resolves with the bound port from `server.address()`, or rejects with the error. Given none it tries 3000, and on an error whose `code` is `EADDRINUSE` tries the next number, until one binds. Any other error rejects. The session's URL is `http://localhost:${port}/`, or the `https` form.

   `server.listen(port)` is called with no host, so the session binds every interface. `docs/specs/dev-server.md`, Serving, is amended where it says the session serves on a local port: the session listens on every interface and prints two URLs, one naming `localhost` and one naming the machine's network address, so a phone on the same network can open the site.

   The URL names `localhost` because that is the name the certificate carries. A marketing site is checked on a phone, and a session only the machine can reach cannot be. The loop over ports has no cap because a port past 65535 is its own error from the runtime. Rejected: a port-finding dependency for one loop.

5. **HTTPS reads the pair from the project directory and names mkcert when either file is missing.**

   `mkcert localhost`, run in a scratch directory with mkcert installed locally, writes `localhost.pem` and `localhost-key.pem`. `createServer` from `node:https` takes `{ cert, key }` as the files' contents.

   When `https` is set, the session reads `localhost.pem` and `localhost-key.pem` from the loaded configuration's `projectDirectory`, and a read that fails with `ENOENT` rejects with `No ${name} in ${projectDirectory}. Run \`mkcert localhost\` there to generate localhost.pem and localhost-key.pem.`, naming the first missing file. The server is `createServer` from `node:https` with `{ cert, key }`, and `node:http`'s otherwise, both given the same request handler.

   The project directory is the one the spec names, and it comes from the configuration rather than from the working directory so a session started with `--config` reads beside the file. The message names the command because the spec says the session says how to generate them.

6. **The client script is a string inside `injectClientScript`, inserted before the closing body tag. It listens at `/_underdot/events` for three events.**

   No output path has a segment starting with an underscore (source: docs/specs/source-tree.md, Underscore prefix). `tsc` emits only what it compiles. `EventSource` is baseline in every browser, and the HTML standard has the browser reestablish a dropped connection on its own.

   A new `src/dev-server/inject-client-script.ts`, headed with a marker naming `docs/specs/dev-server.md`, Live reload, exports `injectClientScript(html: string): string`. It inserts `<script>` followed by the script and `</script>` before the last `</body>`, matched without regard to case, and appends it to the end when there is none. The script, held as a string constant in the module, opens `new EventSource('/_underdot/events')` and handles three events: `building` shows a fixed-position element in a corner reading `Building…`; `failed` replaces that element with a fixed-position overlay whose `<pre>` has the event's data as its `textContent`; `built` calls `location.reload()`. The elements are created once with inline styles and hidden until an event shows them. Nothing is written to the destination. `docs/specs/dev-server.md`, Live reload, gains the sentence that the connection is to a path under `/_underdot/`, which no site output can have because of the underscore rule (see: docs/specs/source-tree.md, Underscore prefix) and which rewrites never reach.

   A string constant is how a script reaches the compiled package without a second file to copy. `textContent` makes the report inert markup, so a failure message quoting a template's tags shows them as text. Inserting before `</body>` keeps the script after the page's own content in the common case, and appending covers a fragment a site serves as HTML without a body tag. The path's underscore segment is what guarantees no site file is shadowed. Rejected: a separate `.js` file published beside the module, which needs a copy step in the build.

7. **Requests are served by `serveRequest` over the current site, with the event stream answered before it.**

   `fetch` and the WHATWG URL parser collapse a dot segment, plain or percent-encoded, before a request is sent, so the one traversal that reaches the handler is an encoded slash: `/..%2Funderdot.config.ts` arrives as written, `decodeURIComponent` turns it into `/../underdot.config.ts`, and `join` of that onto the destination escapes it. `posix.normalize` of a rooted path drops a leading `..`. `new URL('//foo/bar', 'http://localhost')` reads `foo` as a host and `/bar` as the path. `response.setHeader` throws `ERR_INVALID_CHAR` for a value with a character outside Latin-1, and a request target arrives percent-encoded. A rejection from an `http` request listener is an unhandled rejection, which ends the process. `mime-types` 3.0.2, 340 million weekly downloads on 2026-10-06 against 188 million for `mime`, exports `contentType`, which given an extension such as `.css` returns `text/css; charset=utf-8`, appending the charset to every text type, and given an unknown extension or an empty string returns `false`. Given a path with a slash it returns the path unchanged, so it is called with `extname` of the path. Its types are `@types/mime-types` 3.0.1. It depends on `mime-db`.

   A new `src/dev-server/serve-request.ts`, headed with a marker naming `docs/specs/dev-server.md`, Serving, exports `serveRequest(site: Site, request: IncomingMessage, response: ServerResponse): Promise<void>`, with `Site { destination: string; rewrites: Record<string, string> }` declared beside it. In order:

   1. Take the request path as `request.url` up to its first `?`, decoded with `decodeURIComponent`. A path that fails to decode is answered as not found.
   2. Replace the path with the first rewrite whose glob matches it (see: Decision 1).
   3. Normalize the path with `posix.normalize`, which keeps it rooted so no `..` escapes the destination and collapses repeated slashes, and stat `join(destination, path)`.
   4. A directory, when the path ends with a slash, becomes the path with `index.html` appended, and is served as a file. A directory, when it does not, is a 302 redirect whose `Location` is the raw request path, `request.url` up to its first `?` as it arrived, with a slash appended and the query kept.
   5. A file is read whole and answered with status 200, `Content-Type` from `contentType(extname(path))` of `mime-types`, or `application/octet-stream` when that returns `false`, `Cache-Control: no-store`, and `Content-Length` from `Buffer.byteLength` of the body. A response whose type starts with `text/html` is read as UTF-8 text and passed through `injectClientScript` (see: Decision 6) before the length is taken.
   6. Anything else, a missing file or a stat error included, is answered with status 404 and the destination's `404.html` through the same file response when it exists, and with `Not found` as `text/plain` otherwise.
   7. Steps 2 through 6 run inside one `try`. A failure after the stat, such as a read that fails because a rebuild removed the file between the two calls, is answered with status 500 and the error's message as `text/plain` when no headers have been sent, so `serveRequest` never rejects.

   The session's request handler answers `/_underdot/events` itself and hands everything else to `serveRequest` with the current site. Every method is served alike.

   `mime-types` is the download-count pick, and its `contentType` carries the charset rule for text types, so no table lives here. The path is split by hand rather than parsed as a URL because a request target starting with two slashes would otherwise lose its first segment to a host. The redirect names the raw path because the decoded one may hold characters a header cannot carry, and because the raw path is what the browser asked for, so a rewrite stays the server's business. *(deviation: the raw path's leading slashes are collapsed to one in the `Location`, because `//about` otherwise redirected to `//about/`, which a browser reads as a protocol-relative URL to host `about`; review of Phase 2 caught it.)* The handler never rejects because a rebuild races requests exactly when the author is looking, and one lost race must not end the session. The file is read whole rather than streamed because the HTML response is rewritten and a dev server's files are small, and HTML is UTF-8 because that is what every renderer writes. A 302 rather than a 301 because a browser caches a 301 for the origin, and a directory that becomes a page later would keep redirecting. The event stream is matched before rewrites because a site's catch-all rewrite would otherwise swallow it. The `404.html` test is on every miss rather than only on pages so the author sees the page their visitors see. Rejected: streaming with `createReadStream`, which cannot inject into HTML without a transform. Rejected: `sirv` or `serve-static`, each a dependency carrying its own rewrite and caching rules the spec decides differently.

8. **Build status reaches the browser over Server-Sent Events, and a connecting client is told the current status.**

   Node's http documentation gives `server.requestTimeout` as the time to receive a request, 300 seconds, and `server.timeout` as 0, no socket timeout, so a response held open indefinitely is not cut. A browser holds at most six HTTP/1.1 connections to one origin across its tabs.

   The session keeps a set of open event responses and a status: idle, building, or failed with a report. A request for `/_underdot/events` is answered with status 200, `Content-Type: text/event-stream`, `Cache-Control: no-store`, and `Connection: keep-alive`, added to the set, and removed when the request's socket closes. On connect, a building status sends `building` and a failed status sends `failed` with the report. A broadcast writes `event: ${name}\n`, then one `data: ${line}\n` per line of the data, or `data:\n` when there is none, then a blank line, to every response in the set.

   Server-Sent Events need no dependency and no handshake: the response is a plain HTTP response held open, which the runtime's timeouts do not cut, and the browser reconnects on its own after a session restart. Sending the status on connect is what shows the report to a page opened, or reloaded by hand, while the build is broken. The six-connection limit per origin is reached by an author with seven tabs of one site, which the spec's one-tab author never meets. Rejected: `ws`, 342 million weekly downloads, for a WebSocket server, which escapes the limit at the cost of a dependency and a handshake.

9. **One build runs at a time. A change during a build sets a flag, and the loop runs one more build when the flag is set. Every build's outcome is printed and broadcast, and nothing is printed or broadcast once the session is closed.**

   `bindBuild` at `src/build/bind-build.ts:46` binds a resolved configuration and returns the function that runs one build, and every build it runs shares the memory of the ones before. A failed build rejects with the report as its message, printed as `describeError(error)` at `src/configuration/run-command.ts:18`. `runUnits` at `src/build/run-units.ts:30` awaits every worker, so a build that has settled has no unit still writing. The spec holds changes that arrive during a build into one build.

   The session keeps `pending: boolean`, `running: Promise<void> | undefined`, and `closed: boolean`. A change calls `scheduleBuild()`: when the session is closed it does nothing, and otherwise it sets `pending` and, when nothing is running, starts the loop. The loop, while `pending` is set and the session is not closed, clears `pending`, sets the status to building and broadcasts `building` (see: Decision 8), takes `performance.now()`, awaits the current bound build, and on success sets the status to idle, prints `Built in ${Math.round(elapsed)} ms\n` to `process.stdout`, and broadcasts `built`. On failure it sets the status to failed with `describeError(error)`, prints the report with a trailing newline to `process.stderr`, and broadcasts `failed` with the report. A build that settles after the session closed sets nothing, prints nothing, and broadcasts nothing. When the loop ends it clears `running`. The first build is the loop's first run.

   The flag is the whole of the held-changes rule: a burst of saves sets a flag that is already set, and the one build after the current one sees every file as it stands. No timer precedes a build, because the build's own stat-and-hash pass decides what reruns, so an event that changed nothing costs a walk and a stat per file and nothing else, and a timer would delay every real save by its length. A build that changed nothing still reloads every browser, as the spec says. The terminal gets a success line because the author's eye returns to it after a failure, and a report that stays on screen after the fix has gone reads as the fix failing. The closed flag keeps a build that outlives its session from printing into a test's output, and awaiting the settled build keeps its last write ahead of a directory's removal. Rejected: a debounce before the first build, which trades latency on every save for fewer no-op builds on a burst that the flag already collapses to one.

10. **The source root is watched with Node's own recursive `watch`, and any event schedules a build.**

    `watch` from `node:fs` with `recursive: true` reports a change under a nested directory, a file created by writing a temporary name and renaming it over the target, a file inside a directory created after the watch started, a dotfile, and an underscore-prefixed file, on macOS and on Linux. The filename is the path relative to the watched directory with forward slashes. macOS reports every event as `rename`, and Linux reports `rename` and `change`, with a write reported more than once. On macOS a watch started on a directory created moments before reports events for that creation, which Linux does not. A watch on a directory that does not exist throws `ENOENT` synchronously from the call. *(deviation: on the Linux CI runners a recursive watch on a missing directory starts and reports the error later, so the session stats the source root before watching and the stat's `ENOENT` is the start failure on both platforms.)* Node's fs documentation dates recursive support on Linux to v19.1.0, below the floor, says the filename is not guaranteed on every event, and has the watcher emit `error` after it starts. The build reruns a unit only when an input's hash changed, so which file an event names does not matter. `walkSource` at `src/source-tree/walk-source.ts:17` reports a missing source root as `The source root ${root} does not exist.`

    The session calls `watch(source, { recursive: true }, () => { scheduleBuild(); })` from `node:fs` (see: Decision 9), with an `error` listener that prints the error's message to `process.stderr`, and keeps the watcher to close. The filename argument is ignored.

    Recursive watching is in the runtime at the floor on every platform CI runs, verified, so a watcher dependency buys nothing here. A missing source root fails synchronously, which is the one failure the session wants at start, and the walk reports the same root on the first build when the root goes missing later. Rejected: `chokidar`, 262 million weekly downloads, which wraps the same runtime facility on these platforms. Rejected: feeding the watcher's filenames to the build, which the incremental plan rejected for making the destination only as correct as the event stream.

11. **The configuration file is watched through its directory. A reload loads through the loader, replaces the site and the bound build on success, and when it fails its report stands until a reload succeeds.**

    The spec reloads the configuration on a change to it and starts a full build. A fresh `bindBuild` has an empty memory, so its first build runs every unit. An editor that saves by writing a temporary file and renaming it over the original replaces the inode a watch on the file would hold, and the probe of Decision 10 shows the rename arriving with the target's name. The destination lives in the same directory and changes on every build.

    When the session is given a configuration file it calls `watch(dirname(configurationFile))` without recursion, whose listener calls `scheduleReload()` when the event's filename equals `basename(configurationFile)` and otherwise does nothing, a `null` filename included. Both watchers are started by one local function inside `startSession`, since both attach the same error listener (see: Decision 10). `scheduleReload()` sets `reloadPending` and calls `scheduleBuild()`. The loop of Decision 9 checks `reloadPending` at the start of each iteration, after clearing `pending`. When set it clears it and awaits `load()`. On success it starts a source watcher on the new source root, closes the old one, replaces the site and the bound build, clears the session's `configurationError`, and continues into the build. When `load` rejects, or the new watcher throws because the new source root is missing, the loop stores the error's message as `configurationError`, prints it to `process.stderr`, keeps the previous site, build, and watcher, and continues the loop without a build. A source change that arrives while `load` runs has set `pending` again, so the next iteration builds with the previous configuration. The status is failed with `configurationError` whenever one stands: the reload failure sets it and broadcasts `failed`; the loop's success branch of Decision 9 sets the status to failed with `configurationError` in place of idle while one stands, so a successful source build prints its line and broadcasts `built` and the page that reloads reconnects and is shown the standing report; and a source build that fails sets its own report, which the next success replaces with `configurationError` again. `docs/specs/dev-server.md`, Session, gains two sentences: a configuration that fails to load when the session starts fails the start, since there is nothing to serve or watch, and one that fails to reload is reported as a build failure, the previous configuration stays in force, and the report stands until a reload succeeds.

    The reload shares the build loop so a configuration save and a source save racing each other run one at a time, and so the full build that follows a reload is the same loop iteration with the same status reporting. The previous configuration stays in force because the author is mid-edit in the configuration exactly as they are mid-edit in a page, and the browser showing the report is how they learn. The report stands across source builds because those builds run under a configuration the author has already replaced, and a browser that cleared the report on one of them would tell the author the edit took. The directory is watched rather than the file because of the rename, and the listener compares the filename because the destination's changes arrive on the same watcher. A null filename is ignored because the destination is written in the watched directory on every build, and a platform that reported those writes without a name would otherwise reload and build without end, where a missed configuration change costs the author a restart. Rejected: a session that starts with no configuration and serves 404s until a reload succeeds, which adds a configuration-less state to every request handler for a case the command's exit status already reports.

12. **The session is `startSession` in `src/dev-server/start-session.ts`, taking a loader and the options the command takes, and returning the URL and a close function. A failure during the start closes what the start had opened.**

    The spec's Programmatic use section exports the session as a function taking a configuration, and the dev-server spec gives the session the printing of the URL and the reports. `src/index.ts:17-19` exports `build(configuration, projectDirectory = process.cwd())`, resolving through `resolveConfiguration` and binding once. A script that runs a session passes a configuration value, which has no file to watch, and the command passes a file. `server.close` takes a callback and waits for idle keep-alive sockets unless `closeAllConnections` ran first. `writeDestination` at `src/build/write-destination.ts:100` creates the destination before cleaning it, so a session whose first build failed before the write phase serves a destination that does not exist yet, and every request is a 404 until a build succeeds.

    `startSession(options: SessionOptions): Promise<Session>`, where `SessionOptions` is `{ load: () => Promise<ResolvedConfiguration>; configurationFile?: string; port?: number; https?: boolean }` and `Session` is `{ url: string; close: () => Promise<void> }`, both declared beside it. The module carries one marker naming `docs/specs/dev-server.md` and no section, since it enforces Session, Watching, Serving, and Build status alike. In order, the function: calls `load` and lets a rejection fail the start; reads the certificate pair when `https` is set (see: Decision 5); creates the server with the handler of Decisions 7 and 8 and listens (see: Decision 4); starts the source watcher (see: Decision 10); prints `Serving ${url}\n` to `process.stdout`, followed by `Network ${networkUrl}\n` when `networkInterfaces` lists a non-internal IPv4 address, the URL formed from the first such address and the same port and scheme; starts the configuration watcher when `configurationFile` is given (see: Decision 11); and calls `scheduleBuild()` for the first build without awaiting it (see: Decision 9). ## Out of scope

- **A reload on reconnection**, so a tab left open across a restart shows the new build. Declined. The spec reloads on a successful build, and a restart's first build reaches the tabs connected at the time.
- **A debounce before a build.** Declined (see: Decision 9).
- **A session that starts with a configuration it could not load.** Declined (see: Decision 11).
- **Watching a plugin's code or a module a data file imports.** Declined by the spec, which takes a restart.
- **Directory listings.** Declined. A URL ending in a slash with no `index.html` is a 404, as on a static host.
- **HTTP/2.** Declined. The six-connection limit it lifts is not reached in a dev session (see: Decision 8).
