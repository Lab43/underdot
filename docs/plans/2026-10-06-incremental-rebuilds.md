# Incremental rebuilds

## Goal

Deliver checklist step 7: a build that can be run again in one process and reruns only the units whose inputs changed, proven byte-equal to a full build of the same source. After this plan the build binds to a configuration once and keeps a memory of what it did, so the second and every later build reuse the parse of an unchanged page, the handled output of an unchanged static file, a hook's globals when the pages it saw are the same, and a page's body and finished document when nothing they read moved, and writes to the destination only the files whose contents changed. The dev-server session of step 8 is what calls a bound build repeatedly. Nothing public changes: the exported `build` and the command bind once and build once, so a build on its own reuses nothing.

## Context

### The spec sections governing the territory

- `docs/specs/build.md`, Incremental builds: every unit has inputs, a unit reruns when an input changed and is otherwise reused, the first build of a session runs everything, a build on its own reuses nothing, and a render's inputs are its page, every template in its chain, every global name it read whether or not defined, every file and handled output it read through the context, and every body it read. A change to the set of files is a change to inputs, and a template appearing or disappearing re-resolves chains. A configuration or plugin change invalidates everything.
- `docs/specs/build.md`, Determinism: an incremental build produces the same destination as a full build.
- `docs/specs/build.md`, Order of work: the six phases, each complete before the next.
- `docs/specs/build.md`, Errors: a build stops at the first failing unit.
- `docs/specs/plugins.md`, Dependencies: the four unit kinds and their inputs, and a plugin's obligations, which make a unit's output a function of its inputs.
- `docs/specs/plugins.md`, Render context: every read through the context is recorded as an input of the render. A read of an absent file yields no value.
- `docs/specs/plugins.md`, Page hooks: a hook sees every page's URL, output path, source path, and frontmatter, in source-path order, and never rendered content.
- `docs/specs/templates.md`, Variables: the merged set every file in a chain sees, built from the globals and every chain file's frontmatter, and that a value a body computes while rendering reaches no other file.
- `docs/specs/templates.md`, Data files: a module's default export is the value, so data can be computed.
- `docs/specs/dev-server.md`, Session and Watching: the session is the scope of incremental builds, a configuration change reloads it and starts a full build, and a plugin's code is not watched and takes a restart.
- `docs/specs/configuration.md`, The configuration file: the configuration is data, so the session owns the build engine and its memory.
- `docs/specs/ejs.md`, Variables and Includes: every merged variable is reachable by name, `locals` holds the same variables, and a partial renders with the including file's variables with `data` merged over them.

## Decisions

1. **The build binds to a configuration and keeps its memory in the closure.**

   `src/build/build.ts:21-34` is the whole pipeline, one function from a resolved configuration to a written destination, called by `src/index.ts:17-19` and `src/configuration/run-command.ts:15`. Nothing survives the call. The plugin objects it registers are the configuration's, made once when the configuration module loaded, so every build of one configuration registers the same instances.

   `src/build/build.ts` becomes `src/build/bind-build.ts`, exporting `bindBuild(configuration: ResolvedConfiguration): () => Promise<void>`. The returned function is one build. The memory is created inside `bindBuild` and lives in the closure, so every build the function runs shares it and nothing else can reach it. `registerPlugins` stays inside the returned function, so a registration error is a build failure and not a bind failure. `src/index.ts` and `src/configuration/run-command.ts` bind and call once.

   The configuration spec puts the engine and its memory with the session, and a closure is the strongest rung for that: a memory that could be handed to a build of a different configuration is a memory that can lie, and one nothing can hand anywhere cannot. The dev-server session of step 8 binds once per configuration load, which is exactly the spec's rule that a configuration change invalidates everything. Registering inside the build keeps the dev server's first build the place a bad plugin is reported, where the browser shows it. A result reused across builds is correct because the plugin contract makes a unit's output a function of its inputs, and a plugin that kept state between builds breaks that contract as surely as one that kept state between units. Rejected: `build(configuration, memory)` with an exported `createMemory`, which makes the pairing of a memory with its configuration the caller's promise. Rejected: a session object with a `build` method, which is a function with a wrapper, and which takes the dev-server spec's word for a narrower thing.

2. **A file's change is detected by stat, then by hash, in a table the memory keeps.**

   `src/source-tree/walk-source.ts:30-47` lists every file under the root, sorted. It never stats or reads a file. The bust plugin already hashes with the one-shot `hash` from `node:crypto`, in `plugins/bust/src/bust-reference.ts`.

   A new `src/build/hash-files.ts`, headed with a marker naming `docs/specs/build.md`, Incremental builds, exports `hashFiles(source: string, sourcePaths: string[], table: FileTable): Promise<FileTable>`, with `FileTable = Map<string, FileEntry>` and `FileEntry { mtimeNs: bigint; size: bigint; hash: string }` declared beside it. For every path, in units through `mapUnits`, it stats the file with `stat(path, { bigint: true })`. When the table holds the path with the same `mtimeNs` and `size`, the entry is kept. Otherwise the file is read and hashed with `hash('sha256', contents, 'hex')`. The result is a new table holding every path given and nothing else, which the memory keeps for the next build. The paths given are the walked paths after exclusion, so an excluded file is absent to the table as it is to everything.

   A stat is cheap and a hash costs the file's bytes, and images are most of a site's bytes, so a rebuild that hashed everything would read every image on every keystroke. The hash is what downstream units compare, so a save that changed nothing, or a checkout that touched every file, reruns nothing. Rebuilding the table from the walk each time is what removes a deleted file from it. The hash is SHA-256 because it is on the floor with no dependency and the bytes hashed per build are only the changed files. One miss is accepted and the build spec's Incremental builds section is amended to carry it: on a filesystem with coarse timestamps, a file rewritten to the same size within one timestamp tick of a build's stat keeps its earlier hash until it changes again or the session restarts. The tick is a nanosecond on APFS and a few milliseconds on ext4, where a build's stat cannot fall between two saves, and a second on HFS+ or two on FAT, where it can. Rejected: hashing every file every build, which is simpler and reads every image. Rejected: stat alone, under which a touch reruns everything the file feeds. Rejected: hashing a file whose timestamp is within a margin of when it was last hashed, as git does for its index, which the user declined as a rule for a case only removable media reaches. Rejected: taking the changed paths from step 8's watcher, which makes the destination only as correct as the watcher's event stream, and leaves nothing for a test to call.

3. **One mechanism reuses every unit: a record of the inputs it observed, each with the version seen, and its result.**

   A new `src/build/reuse-unit.ts`, headed with a marker naming `docs/specs/build.md`, Incremental builds, declares `InputKind = 'file' | 'output' | 'body' | 'global' | 'globals' | 'chain' | 'pages'`, `Version = string | undefined`, `Observe = (kind: InputKind, name: string) => void`, `UnitRecord<R> { inputs: Map<string, Version>; result: R }`, and `UnitRecords<R> = Map<string, UnitRecord<R>>`. It exports `reuseUnit<R>(records: UnitRecords<R>, key: string, lookup: (kind: InputKind, name: string) => Version, run: (observe: Observe) => Promise<R>): Promise<R>`. When the records hold the key and every recorded input's current version, from `lookup`, equals the version recorded, the recorded result is returned and `run` is not called. Otherwise `run` is called with an `observe` that records the input under `${kind}:${name}` with its current version, the result is stored under the key with those inputs, and returned. A `run` that throws stores nothing. An absent input records `undefined` as its version, so a file or global that did not exist is an input that changes when it appears. *(deviation: the map's values are `{ kind, name, version }` rather than the version alone, still keyed by `${kind}:${name}`. Replaying the inputs through `lookup(kind, name)` from the joined key alone would split the key back and cast the first part from string to `InputKind`, which the lint rule against unsafe type assertions rejects.)*

   Checking the previous run's inputs before running is correct because a unit's output is a function of its inputs, which the plugin contract requires, so a unit whose every input is unchanged would read the same inputs again and produce the same result. Recording during the run, rather than declaring up front, is what lets a render's inputs be whatever it read, which no one knows until it ran. A thrown run stores nothing so the next build tries it again. One function for every unit kind keeps the rule in one place and lets each kind's test be a test of its lookup and its observations. Rejected: a dirty set propagated through reverse dependencies, the same information inverted with a second data structure to keep right. Rejected: declaring a unit's inputs ahead of running it, which a render cannot do.

4. **The parse, the data read, and the handling of a file are reused by the file's hash, and a data module imports by its hash.**

   `src/build/read-site.ts:40-50` reads and parses every page and template on every build. `src/templates/read-data.ts:50-64` reads every JSON data file and imports every module data file through `src/shared/import-default.ts:6-8`, the one place a module is imported at a runtime path, which imports by file URL with no query. Node caches a module by URL and a query string on the URL yields a fresh module. Verified on 2026-10-06 on Node 24.19 and on the floor, Node 22.18.0, for a `.ts` module under type stripping: rewritten between two imports with different `v` queries it yielded the new export, and re-imported under the first query it yielded the first export from the cache. The same holds under the installed Vitest for `.ts` and `.js` modules, verified the same day with a throwaway test of the same shape. `src/plugins/handle-files.ts:26-36` runs every static file through its handlers on every build. `Output` at `handle-files.ts:15-19` holds a source path, an output path, and the handled bytes, or no bytes for a file copied as it sits.

   `readSite` takes the file table and `records: UnitRecords<FileContents>` and wraps each `readContents` in `reuseUnit` keyed by the source path, observing `('file', sourcePath)` with a lookup that answers from the table. `readData` takes the same and wraps each `readDataFile` the same way, after the extension and reserved-name checks that need no read. `importDefault` gains an optional second parameter, `version?: string`, appended to the file URL as `?v=${version}` through `URL`'s `searchParams`, and `readDataFile` passes the file's hash for a `.js` or `.ts` data file. `handleFiles` takes the table and `records: UnitRecords<Output[]>`, wraps each file's handling in `reuseUnit` the same way, and `Output` gains `hash: string`: the hash of the handled bytes, or the source file's hash from the table for a file copied as it sits. *(deviation: a static file absent from the table is an error naming it. The copy output's hash is read from the table, and the type cannot know that every walked path is there.)*

   Keying the import by content hash is the proven bypass of the module cache, in Node and under the test runner, and it reloads a module exactly when its file changed, which is the rule every other unit follows. A module changed back to an earlier content hits the cache and gets the earlier value, which is the value a fresh import would compute. Each distinct content of a data module stays in the module cache for the life of the session, one small module per save, which is bounded by the edits a session makes. An output carries its hash so a reader of handled output can depend on the bytes that will be served: a comment stripped by a minifier changes the source and not the output, and readers of the output stay reused. The build spec's Incremental builds section is amended in its last paragraph, beside the plugin-code rule: a data module's own file is its input, and a module it imports is treated as a plugin's code, not watched, so a change to it takes a restart. The Determinism rule binds the source directory, the configuration, and the plugins, and a module a data file imports is none of those, so it stays as written. A data value and a hook's globals are now shared by every build in a session, where a JSON value was parsed afresh per build. A template that mutates one in place already breaks the build today, since the mutation reaches every other render of the same build in whatever order they ran, so sharing across builds widens a defect the determinism rule already forbids and creates none. Rejected: tracking the modules a data module imports, which needs a loader hook for a case no site has. Rejected: clearing the module cache, which Node does not offer for ES modules. Declined: freezing every data value and hook global, because no site has mutated one and the rule belongs to the templates spec when one does.

5. **A hook's input is the list of pages as it sees them, and that list's hash versions every global the hooks define.**

   `src/plugins/run-page-hooks.ts:31-53` builds a `HookPage` per page from four fields and runs every hook. `HookGlobal` at `run-page-hooks.ts:21-25` carries a name, a plugin, and a value.

   `runPageHooks` takes `records: UnitRecords<HookGlobal[]>`. It builds the `HookPage` list as today, computes `pagesVersion` as the SHA-256 of `serialize(hookPages)` from `node:v8`, and wraps each hook's run in `reuseUnit` keyed by the plugin's name, observing `('pages', '')` with a lookup that answers `pagesVersion`. `HookGlobal` gains `version: string`, set to `pagesVersion`. The build spec's Incremental builds section is amended where it says adding or removing a static file, a data file, or a page reruns the hooks: a page added, removed, or renamed, or a page whose frontmatter changed, reruns every hook, a change to a page's body reruns none, and adding or removing any file re-evaluates the uniqueness rule.

   The pages list is everything a hook is given, so it is the whole of a hook's inputs, and the spec's existing sentence, written before hooks were designed, named static and data files that no hook can see. Serializing with `node:v8` keeps a date distinct from the string it prints as, which `JSON.stringify` would not, and frontmatter under the core schema holds nothing it cannot serialize. Versioning a hook's globals by the hook's input rather than by comparing its output needs no deep comparison of values a hook may fill with anything, and equal inputs give equal outputs by the plugin contract, so the version changes exactly when the output may have. Every hook sees the same list, so every hook's globals share one version, and a frontmatter edit re-renders the pages that read any hook's global. Rejected: versioning by the serialized output, which throws on a function a hook may return and buys a page that reads a collection nothing on a frontmatter edit, since the collection changed. Rejected: a per-hook subset of the pages, which a hook does not declare.

6. **Every global has a version, computed once per build.**

   `DataVariable` at `src/templates/read-data.ts:14-18` names its defining file, or its defining directory as `_data/team` when a directory defines it, at `read-data.ts:98`.

   A new `src/build/version-globals.ts`, headed with a marker naming `docs/specs/build.md`, Incremental builds, exports `versionGlobals(globals: Record<string, unknown>, dataVariables: DataVariable[], hookGlobals: HookGlobal[], files: FileTable): Map<string, string>`. A configuration global's version is the string `configuration`. A data variable's version is the hashes of every table entry whose path equals its `sourcePath` or starts with `${sourcePath}/`, as `path:hash` lines in path order, so `_data/team` versions by every file in the directory and never by `_data/team.json`. A hook global's version is its `version` field.

   A configuration global cannot change within a bound build, so a constant is its whole version. A data variable defined by a directory changes when any file in the directory does, and the table already has every file's hash, so no value is compared. The slash on the prefix is what keeps a directory from matching a file whose name it begins. Rejected: hashing each data value, which repeats what the file's hash already says.

7. **The render context records every read, the variables included, through an observe function it is given.**

   `src/plugins/bind-render-context.ts:93-128` holds the four context operations. `readFile` yields no value for a path outside the walked set. `readOutput` finds the handled output in a map keyed by output path at `bind-render-context.ts:79-80`. `readBody` throws while a body renders and for a URL no page has. `enterFile` makes the partial's context. At `bind-render-context.ts:131` the context copies the variables it was handed and assigns every helper onto the copy. A Proxy is how the build can see a variable read. Verified on 2026-10-06 on Node 24.19, and on the floor, Node 22.18.0, for the `has` trap under `with`: a `with (proxy)` block calls the `has` trap for every identifier it resolves, undefined names included, and then `get` for a found one. `Object.hasOwn(proxy, key)` calls the `getOwnPropertyDescriptor` trap. A spread of a proxy calls `ownKeys`, then `getOwnPropertyDescriptor` and `get` for every key. A second proxy whose traps consult the first with `in` and a property read reaches the first's traps. An `ownKeys` trap that returns a key twice makes the engine throw a `TypeError`. The fixture renderer at `test/fixtures/templated/fixture-renderer.ts:9` reads the first segment of a variable path with `Reflect.get` on the context's variables and walks the rest on the value.

   `MakeRenderContext` gains a fourth parameter, `observe: Observe`, and `bindRenderContext` takes the file table in place of the set of walked paths. `readFile` observes `('file', referencedPath)` before reading, whether or not the file exists. `readOutput` observes `('output', resolvedPath)`, the output path it looks up. `readBody` observes `('body', url)` after the check that a body may be read at all. `enterFile` passes the same `observe` to the partial's context. The copy at `bind-render-context.ts:131` and the helper assignments after it are replaced by a Proxy over the variables handed in, with five traps. `get` answers a registered helper, bound to this context as today, ahead of the target, and for any other string key observes `('global', key)` and forwards. `has` and `getOwnPropertyDescriptor` do the same, the latter answering a helper with a configurable, enumerable data descriptor. `ownKeys` observes `('globals', '')` and returns the target's keys with each helper name added once, left out when the target already has it. `set` forwards to the target. A symbol key is forwarded and never observed.

   The context's operations already are every read a render makes, so observing inside them is what the plugins spec's "every read through the context is recorded" asks for and changes no plugin. The proxy is the only way a variable read is visible, and `has` is what a `with` block consults, so an engine that reads through the object the build hands out records every name it resolves, defined or not, and the fixture renderer records exactly the names a page reads. Helpers are answered by the proxy rather than assigned, so an entered partial's variables, which a renderer hands in as a proxy of its own, are never copied and never written. The key list is deduplicated because a renderer may enter a partial with data under a helper's name, which no global or frontmatter key can carry, and a repeated key in `ownKeys` is a thrown `TypeError` on the next spread. `set` forwards because the target is the per-render object `renderBody` and `renderChain` already spread, so a scriptlet's assignment reaches no other file in the chain, as the templates spec requires. Enumeration observes every global at once because a template that lists its variables depends on all of them. Rejected: observing in the renderer, which moves the build's bookkeeping into every plugin. Rejected: a getter per global on the merged object, which a spread reads through just the same.

8. **The EJS plugin reads through the context's variables and layers include data without copying.**

   The EJS renderer at `plugins/ejs/src/render-ejs.ts:42` copies the context's variables before wrapping them in its own proxy, so EJS's `with` block never touches the build's object. Its include at `render-ejs.ts:30` spreads the variables and the include data into a new object for `enterFile`. Both spreads read every key through the recording proxy of Decision 7.

   `renderEjs` drops the copy at `render-ejs.ts:42`. Its locals proxy keeps a private `assignments` object: `has` answers `include`, then the EJS names as today, then whether `assignments` or the context's variables own the key, then whether the key is absent from `globalThis`. `get` answers `include`, then `assignments`, then a read of the context's variables. `set` writes to `assignments`. The include at `render-ejs.ts:30` hands `enterFile` a Proxy over a copy of `data` whose `has`, `get`, and `getOwnPropertyDescriptor` consult the copy and then the including file's variables, the descriptor from the variables made configurable, whose `ownKeys` returns the copy's keys and then each key of the variables the copy lacks, and whose `set` writes to the copy. *(deviation: reversed at the review gate. The include hands `enterFile` the data alone, and `enterFile` in `src/plugins/bind-render-context.ts` builds that Proxy over the file's own variables, so no renderer holds the merged object. The plugins spec's enter operation now says the partial renders with the file's variables and the data layered over them.)* `plugins/ejs/src/render-ejs.test.ts` keeps its test that a scriptlet's `var` leaves the context's variables unchanged and gains two: a variable read, a `locals` read, and a read inside a partial reach the context's variables object rather than a copy, through a Proxy whose traps are spies, and an include whose data carries a name the context's variables also hold renders and enumerates without error. *(deviation: the second test, and the layering tests with it, live in `src/plugins/bind-render-context.test.ts`. The EJS test asserts that `enterFile` receives the data alone.)*

   The two spreads are the only copies left between the build's proxy and EJS's `with` block, and each would observe every global on every render, so an EJS page would rerun on any global's change. The assignments overlay keeps the plugin's promise that a scriptlet's `var` changes nothing the context owns, without a copy. The layered include object is what the spec already says a partial renders with, the including file's variables with `data` over them, expressed as a view instead of a merge, so the build's proxy below it still sees each read. The EJS spec changes nothing. Rejected: having the build merge include data, which the plugins spec gives to the renderer and which would make the EJS merge rule the core's. *(deviation: reopened by the user at the review gate and taken, so that a renderer cannot hand a partial a copy and every engine with parameterized includes gets the view.)*

9. **A page's body and its finished document are two records, and its chain and every template in it are inputs of both.**

   `src/templates/render-pages.ts:71-75` renders every body, then every chain. `mergeVariables` at `render-pages.ts:25-31` spreads the globals and every chain file's frontmatter into one object per page, and `renderBody` and `renderChain` spread that object again per render with the built-ins added. `src/templates/resolve-chains.ts:81-84` resolves every page's chain on values, cheaply, every build.

   `renderPages` takes `versions`, a `Versions` object, with `findVersion(versions: Versions, kind: InputKind, name: string): Version` in a new `src/build/find-version.ts`, headed with a marker naming `docs/specs/build.md`, Incremental builds, holding `files: FileTable`, `outputs`, `globals`, `chains`, and `bodies`, the last four `Map<string, string>`, `outputs` keyed by output path, and `allGlobals: string`, every global's `name:version` joined in name order, computed once. `Versions` is declared in `src/build/bind-build.ts`, whose function produces its values, and `find-version.ts` imports the type. It takes `bodyRecords: UnitRecords<{ body: string; hash: string }>` and `pageRecords: UnitRecords<RenderedPage>`. Before the body phase it fills `versions.chains` with each page's source path mapped to its chain's source paths joined by newlines. For every page it merges the variables through `mergeVariables` as today, whether or not the body is reused, since the merge is a spread on values. `renderBody` runs inside `reuseUnit` keyed by the page's source path, observing `('file', ...)` for the page and each template of its chain and `('chain', page.sourcePath)`, rendering with a context made with that observe, and returning the body with its SHA-256. After the body phase it fills `versions.bodies` from each page's URL to its body's hash. `renderChain` runs inside `reuseUnit` over `pageRecords`, observing the same files and chain and `('body', page.url)`, and returns the `RenderedPage`, which gains `hash: string`, the SHA-256 of its contents. `findVersion` answers `file` from the table's hash, `output`, `global`, `chain`, and `body` from their maps, `globals` with `allGlobals`, and `pages` with nothing, since no render observes it and the hook phase has its own lookup. `bindBuild` creates `versions` after the file table, fills `outputs` from each handled output's path and hash and `globals` from `versionGlobals`, and hands it to `renderPages`.

   The templates spec merges every chain file's frontmatter into the variables a body renders with, so a template is an input of the body as much as of the chain, and a template edit reruns every body and every chain of the pages it wraps. The resolved chain is an input of its own because a template appearing in a search path changes which files are in the chain without changing any file already in it. A body and a chain are separate records so a change to a file, an output, or a body that only a page's templates read reruns the chain and not the body, and a page edit reruns both. A page's own body is a `body` input of its chain, under the same key as a body another page reads, so one lookup serves both. The merged variables are recomputed rather than recorded because a record holds a unit's result and the merge is not one, and the chain render needs them whether the body was reused or not. Rejected: one record per page, which re-renders a body whenever a file only its templates read changed. Rejected: deriving the chain from the files observed, which cannot see a template that was not there. Rejected: versioning a template by its frontmatter alone for the body's sake, which saves a body render on a template edit at the cost of a second version per template.

10. **The destination is the store for every public output, and a build writes only the files whose contents changed.**

    `writeDestination` at `src/build/write-destination.ts:71-95` plans every public output and page, cleans the destination top-down, keeping a regular file at a planned path at `write-destination.ts:60`, then writes every planned file. The clean pass walks every directory the planned files pass through, so it sees which planned paths already exist. A private output is filtered at `write-destination.ts:73` and never written. `readOutput` at `src/plugins/bind-render-context.ts:103-108` serves a handled output's bytes from memory synchronously, and `readBody` at `bind-render-context.ts:111-119` serves bodies from a map. Images are copied unhandled, as `Output` values with no bytes.

    `writeDestination` takes `written: Map<string, string>` from the memory, output path to the hash of the bytes last written there. Its clean pass collects the planned paths that exist as regular files and deletes from `written` every path at or under anything it removes. A planned file whose path is in that set and whose hash, an output's from Decision 4 or a page's from Decision 9, equals the table's entry is left alone. Every other planned file has its entry deleted, is written as today, and has its entry set once the write completes. The record of a handled output keeps its bytes and the record of a page keeps its text.

    A file the build already wrote, with the contents it would write again, is the build's own output sitting where it belongs, and rewriting it is work with no reader. Deleting the entry before the write and setting it after keeps a failed build's table true to the disk, so a file a failed write truncated is rewritten by the next build whether or not its contents changed. The existence check keeps a file removed from the destination from staying missing. Nothing checks a file's contents beyond that, because the destination is the build's own by the build spec's Destination rule, and a file something else edited there is outside the contract. *(result: the final review found the Destination rule did not say so, and the user ruled to amend `docs/specs/build.md`, Destination, in this change.)* Private outputs and bodies are never written and helpers read both synchronously, so they live in memory, and a public output's bytes stay beside them so a planned file found missing is written from the record with no rerun. Every result this plan records is text or a copy from source, so the memory holds the site's text and none of its images. A record whose key no longer exists, a deleted page's, is never consulted and is bounded by the files a session has ever seen. Rejected: re-hashing each destination file to confirm it, which reads every output on every build to learn what the table already says. Rejected: a page record holding only the hash, which cannot restore a file found missing without a rerun the write phase has no way to ask for. Deferred to step 9: dropping a result's bytes once written, for derivatives too large to keep, with the destination file's presence made an input of the producer so a missing one reruns it. Declined: pruning records, for the cost of a second pass over every map on every build.

12. **The plan ships as one PR.**

    Every prior plan with a whole-site change, PRs #47 through #51, shipped 450 to 830 changed lines as one PR, read from `gh pr view` on 2026-10-06, and this plan is larger. The plan format's sizing rule exists so a reviewer can hold a change in one sitting.

    The whole change ships as one PR, read phase by phase. The proof of Decision 11 is what a reviewer reads the mechanism against, and it holds only when every unit kind is reused. Split, the first PR carries a memory that reuses parses and handling but renders everything, the second a recording context no published renderer reads through, and the third the EJS plugin change whose reason sits in the PR before it. Each phase is green on its own and its catalogue cases hold at its boundary, but the proof a reviewer reads the mechanism against is the whole catalogue with every unit kind reused, which only the last phase delivers. The phases are the seams a reviewer reads by, which is what the sizing rule protects. Rejected: a stacked delivery with the EJS plugin as its own PR, which separates the plugin change from the proxy it exists to read through.
