# Sass plugin

## Goal

Ship `underdot-sass`, a file handler compiling a site's `.scss` stylesheets to CSS, the step 11 of the README's rebuild checklist. Sass follows `@use` imports on its own, so it is the first handler whose output depends on files it did not receive, and the build needs a way to hear about them. Sass also reports warnings, which the plugin contract has no channel for. The plan gives every plugin context a `warn` and file handlers a context of their own that declares a wrapped tool's reads, then builds the plugin on both.

## Context

What the build already promises a plugin, and where it falls short of a compiler that follows imports:

- A tool a plugin wraps may read files on its own, and the plugin declares those files as inputs of its output (see: docs/specs/plugins.md, Reading and writing). A unit's inputs include every file it declared, and the build reruns a unit when any input changed (see: docs/specs/plugins.md, Dependencies). No declaring mechanism exists yet: `FileHandler` is `(file: HandledFile) => …` with no context (`src/plugins/register-plugins.ts:15`).
- The plugins spec says there is no warning: a condition worth reporting is an error, and one not worth stopping for is not reported (see: docs/specs/plugins.md, Errors).
- Handler chains, renaming, partials compiling to nothing, and handling before any page renders are the File handlers section's (see: docs/specs/plugins.md, File handlers). An underscore-prefixed static file still passes through handlers and its output is never written, and files inside an underscore-prefixed directory are not classified at all (see: docs/specs/source-tree.md, Underscore prefix). Every walked file is in the build's file table, those in private directories included (`src/build/bind-build.ts:73-74`), and an excluded file is not (see: docs/specs/configuration.md, Excluded files).
- A dev session reruns only units whose inputs changed, and a build run on its own reuses nothing (see: docs/specs/build.md, Incremental builds). A unit that throws leaves no record (`src/build/reuse-unit.ts:44`), so it runs again on the next build.
- The destination is a function of the source and configuration (see: docs/specs/build.md, Determinism).

Where a handler's reads, a context's operations, and a warning's output would have to enter the code:

- `runHandlers(sourcePath, file, handlers)` calls each matching handler at `src/plugins/run-handlers.ts:42` and attributes a throw as `Handling <sourcePath> failed in <plugin>: <message>` through `attributePluginError` (`src/plugins/attribute-plugin-error.ts`). It is called once per static file from `handleFiles` (`src/plugins/handle-files.ts:55`), whose `lookup` versions a `file` input from the file table (`src/plugins/handle-files.ts:41`), and once per emitted file from `produceFiles` (`src/plugins/produce-files.ts:120`), with the emitted output path standing in for the source path. `produceFiles`' `lookup` knows only `parameters` and `output` inputs (`src/plugins/produce-files.ts:96`).
- The render context is made by `makeContext(sourcePath, variables, bodies, observe, emits)` (`src/plugins/bind-render-context.ts:97-117`). `enterFile` calls it again for a partial (`:191`). Each helper receives a copy `{ ...context, emit }` whose `emit` is bound to the helper's plugin (`:202-219`). `renderPages` calls `makeContext` at `src/templates/render-pages.ts:87` and `:106`, and attributes a render's throw to the helper's plugin or else the file's renderer, `file.renderer.pluginName` (`:68`).
- A page hook is called as `hook(hookPages)` (`src/plugins/run-page-hooks.ts:50`), and a producer as `produce({ readOutput })` (`src/plugins/produce-files.ts:110`).
- The core writes nothing to the terminal itself. `src/configuration/run-command.ts` and `src/dev-server/start-session.ts` do, and tests capture both streams with the `stdout` and `stderr` fixtures of `test/helpers/test.ts`. `test/helpers/make-render-context.ts` builds a stand-in `RenderContext` for the plugin packages' tests.

What Sass resolves, reports, and records, which the handler can only take as Sass gives it, run against `sass` 1.105.1 on Node 24.19.0 on 2026-10-07 in a scratch tree:

- `compileStringAsync(text, { url, loadPaths, logger })` resolves `@use 'vars'` against `url`'s directory, finding `_vars.scss`, then against each load path, so `@use '_sass/mix'` with the source root as a load path finds `_sass/_mix.scss` from any depth. `@use 'parts'` finds `parts/_index.scss`. A leading slash means the filesystem root. A missing import throws `Can't find stylesheet to import.`
- The result's `loadedUrls` lists the root stylesheet's URL and every file URL it loaded, and `css` is the expanded output with no trailing newline.
- A thrown error's `message` carries Sass's own report: the message, a snippet, and `src/styles/site.scss 1:8  root stylesheet` with the path relative to the working directory.
- A `logger` replaces Sass's printing. `warn(message, { deprecation, span, stack })` receives `@warn` and deprecations such as `@import` (`deprecation: true`), with `stack` like `src/styles/site.scss 4:9  root stylesheet\n`. `debug(message, { span })` receives `@debug`, with `span.url` and a zero-based `span.start.line` and `span.start.column`.
- `sass` declares `engines.node >=20.19.0`, under the toolchain's floor of 22.18.0. Weekly downloads for 2026-09-28 to 2026-10-04 were 37,974,138 for `sass` and 7,946,233 for `sass-embedded`.
- `underdot-sass` is on npm at 1.0.0, maintained by `lab43`, so v2 publishes under the existing name, checked with `npm view underdot-sass` on 2026-10-07.

## Decisions

1. **Every plugin context gets `warn(message: string)`, and the build prints each call to standard error as `<unit> warned in <plugin>: <message>` and continues.** The unit and plugin are the ones an error from the same call site would name: `Handling <sourcePath>`, `Rendering <file in the chain>`, `Running the page hook`, and `Producing <outputPath>`. A helper's `warn` names the helper's plugin, and a renderer's names the renderer's. A new `src/plugins/print-warning.ts` exports `printWarning(unit: string, pluginName: string, message: string): void`, writing `${unit} warned in ${pluginName}: ${message}\n` to `process.stderr`, beside `attribute-plugin-error.ts` whose format it mirrors. A warning changes no exit status and fails no build. The dev server prints it in the terminal and shows nothing in the browser. The user ruled on 2026-10-07 to print a Sass warning and keep building, over failing the build on it. The plugins spec's Errors section replaces its "There is no warning" paragraph with this rule and rewrites its rationale: the old objection, that a warning which fails nothing is read by nobody and so a deploy build ships the condition, holds for a condition in the build's output, and an engine's warning is mostly about the engine's future, a deprecation the output does not yet suffer from. Stopping the build for it makes every deprecation an emergency, and silencing it hides the notice until the engine's next major release turns it into an error. A condition Underdot itself detects is still an error or nothing, so the build adds no warnings of its own. The build spec's Errors section gains that a warning fails nothing and leaves the exit status alone. The dev-server spec's Build status section gains that a warning is printed in the terminal and never shown in the browser, which keeps the page and clears no report. Every context rather than the handler's alone, by the user's ruling, so the contract is one rule for every plugin. Rejected: a plugin writing to `process.stderr` itself, which names neither the plugin nor the unit. Rejected: a warning sink passed into `bindBuild` and the exported `build`, a lever no caller has asked for, when the commands are the only callers and both print to the same stream.

2. **A warning prints when its unit runs, and a reused unit prints nothing.** A build run on its own runs every unit and so prints every warning. A dev session prints a stylesheet's warnings on its first build and again whenever the stylesheet or a file it declared changes. Nothing new is recorded. The build spec's Incremental builds section gains that sentence. Rejected: recording warnings with a unit's result and replaying them on reuse, which repeats every warning on every save.

3. **A file handler receives a second argument, its context: `HandlerContext { sourceDirectory: string; declareFile: (sourcePath: string) => void; warn: (message: string) => void }`, declared in `src/plugins/run-handlers.ts` and exported from `src/index.ts`.** `sourceDirectory` is the absolute path of the source root. `declareFile` records a file under the source root, by its source path, as a `file` input of the unit running the handler, versioned from the file table as a read through the render context is. A path that is not a plain path (`isPlainPath`, `src/shared/is-plain-path.ts`) fails with `The handler declares ${JSON.stringify(sourcePath)}, which is not a plain path under the source root.`, and a plain path absent from the file table fails with `The handler declares ${sourcePath}, which the build does not see.`. Both are thrown inside the handler, so the existing catch attributes them to the unit and plugin. A wrapped tool reads from disk, so it needs a location on disk, and the source root is that one location for the file and for every load path. A declared file outside the source or excluded is a read the build cannot track, so it fails rather than going stale in silence. Declared files observed as `file` inputs need nothing new from `reuseUnit`. The plugins spec's File handlers section gains the context, and Reading and writing gains that a declared file outside the source root or excluded is a build error. Rejected: a `sourcePath` in the context, which an emitted file running through later handlers does not have. Rejected: `declareFile` taking an absolute path, which leaves the build converting paths for every plugin when the plugin already holds the root.

4. **Emitted files get the same handler context, and `produceFiles` versions `file` inputs.** `produceFiles` gains the `files: FileTable` parameter and its `lookup` returns `files.get(name)?.hash` for `file`. A Sass handler is unlikely to follow an emitting plugin, but the context is one type and the unit records what it is told.

5. **A page hook receives a second argument, `HookContext { warn }`, declared in `src/plugins/run-page-hooks.ts`. A producer's `ProducerContext` gains `warn`.** Both are additive to signatures existing plugins already satisfy. The plugins spec's Page hooks and Emitted files sections each gain the operation.

6. **The plugin is `underdot-sass`, factory and plugin name `sass`, with no options, registering one handler for `**/*.scss`.** It depends on `sass` ^1.105.1, the most downloaded of the two Dart Sass builds for Node. A file whose name starts with an underscore is a partial and compiles to nothing, the File handlers section's own example. Every other file compiles to CSS at its own path with `.scss` replaced by `.css`, Sass's output as it is with nothing appended. The output is Sass's default expanded style with no source map, and the factory takes no option, since compressed output, source maps, and `.sass` files are needs no site has stated, and a later PostCSS handler can minify by plugin order. Rejected: `sass-embedded`, a fifth of the downloads and a native binary per platform.

7. **Imports resolve relative to the stylesheet and then from the source root, and an import from outside the source root fails the build.** The handler compiles `file.contents` as UTF-8 with `compileStringAsync`, `url` set to `pathToFileURL(join(context.sourceDirectory, file.outputPath))` and `loadPaths: [context.sourceDirectory]`. After the compile it declares every entry of `loadedUrls` but the root stylesheet's own `url`, each as `relative(context.sourceDirectory, fileURLToPath(loadedUrl))` with the platform separator replaced by `/`, since source paths are posix whatever the platform. Everything the stylesheet loaded is then an input, and an import reaching outside the root fails the build through `declareFile` (decision 3), after Sass has read it. The root is skipped because the unit already observes its source file (`src/plugins/handle-files.ts:44`), and because the path the handler received is not a source path when an earlier handler renamed the file or the file was emitted, so declaring it would fail a valid chain. A shared partial kept in `_sass/` is then reachable as `@use '_sass/mixins'` from any depth, and never written. The handler hands Sass the output path, which is the source path when Sass is the first handler, so Sass's reports name the file the author edits. After a renaming handler, relative imports resolve against the renamed path's directory, which is the source directory unless the rename moved the file. No package importer is enabled. Rejected: mapping a leading slash to the source root, a custom importer no site has asked for.

8. **Sass's warnings go through the context, and its errors propagate as they are.** The handler passes a `logger`. Its `warn(message, { stack })` calls `context.warn` with `message`, and with `stack.trimEnd()` on a line below it when `stack` is given. Its `debug(message, { span })` calls `context.warn` with `message` and, below it, the location in Sass's stack format, `${relative(process.cwd(), fileURLToPath(span.url ?? url))} ${String(span.start.line + 1)}:${String(span.start.column + 1)}`. A thrown compile error propagates unwrapped, as the plugin contract requires (see: docs/specs/plugins.md, Errors).

9. **A dev session misses a file added later that would change what an `@use` resolves to.** Declared inputs are the files Sass loaded, not the candidates it tried, so adding `styles/_vars.scss` where `@use 'vars'` had resolved to `_vars.scss` at the root takes effect when the stylesheet or a file it loaded next changes, or on restart. An import that fails to resolve leaves no record and reruns every build. The build spec's Incremental builds section states the gap. Rejected: a custom importer that re-implements Sass's resolution through recorded reads, which duplicates partial, index, and extension rules Sass owns and must track across Sass releases.

10. **Two stacked PRs.** The core's contexts and the spec amendments are one reviewable scope with no Sass in it, and the package is another. The first lands warnings and declared reads proven with fixture handlers, and the second consumes them.

## Out of scope

- **`.sass` indented syntax, source maps, compressed output, and options.** Deferred until a site needs one.
- **Imports from `node_modules` or Sass's `pkg:` URLs.** Declined for now: such a read is outside the source root, so it fails by decision 3.
- **Showing warnings in the browser.** Declined by decision 1.
