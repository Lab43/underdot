# The srcset plugin

## Goal

Deliver checklist step 9: the emit mechanism, and the sixth workspace package, `underdot-srcset`, as its first consumer. After this plan a helper hands the build a file to produce and returns its URL at once, the build produces it after the renders, only when its inputs changed, and writes it through the handlers of the plugins after the emitting one. A page or template calls `imageSet(reference, preset, attributes)` and gets an `<img>` whose `srcset` names a derivative per requested width the image can fill, resized with sharp and converted to WebP unless the preset keeps the source's format. An original kept under an underscore is never written and ships as derivatives alone. The two deferrals the incremental-rebuilds plan left for this step close here: a derivative's bytes leave memory once written, and a derivative missing from the destination is produced again.

## Context

### The spec sections governing the territory

- `docs/specs/plugins.md`, Emitted files: a plugin emits a file by naming its output path and supplying a producer; emitting is available from helpers during a render; an emitted file passes through the handlers of the plugins after the emitting plugin and then falls under the output rules; two emits of one path with the same inputs are one output and with different inputs a uniqueness error naming both; the producer runs only when its inputs changed.
- `docs/specs/plugins.md`, Template helpers: a helper returns synchronously and hands asynchronous work, such as producing a derived file, to the build, returning what the template needs now, such as the derived file's URL.
- `docs/specs/plugins.md`, Render context: the context carries the build's emit operation, and every read through it is recorded as an input.
- `docs/specs/plugins.md`, Dependencies: producing one emitted file is a unit, its inputs are what it read through the context, and a producer's output is determined by its inputs.
- `docs/specs/plugins.md`, Errors: the report names the plugin, the unit, and the file, and a plugin never terminates the process.
- `docs/specs/build.md`, Order of work: producers run in phase 5 with the chain renders, because helpers emit during renders, and the destination is written in phase 6.
- `docs/specs/build.md`, Incremental builds: a unit reruns when an input changed and is otherwise reused, and a build on its own reuses nothing.
- `docs/specs/build.md`, Determinism: the same source, configuration, and plugins produce a byte-identical destination on every machine.
- `docs/specs/build.md`, Concurrency: image derivatives dominate build time, and the limit keeps memory bounded.
- `docs/specs/build.md`, Destination: the destination is the build's own, and a file edited there by anything but the build is outside the guarantee.
- `docs/specs/source-tree.md`, Underscore prefix: a path with an underscore-prefixed segment is never written, and such files still pass through handlers. `docs/specs/source-tree.md`, Output paths are unique: two sources at one output path fail naming both.
- `docs/specs/templates.md`, Relative paths: a reference resolves against the file being rendered, or from the source root with a leading slash.
- `docs/specs/bust.md`, References, and `docs/specs/svgo.md`, The helper: the two helpers that take a reference to a static file's output, resolve it as a read does, and fail for a reference no output is at.

## Decisions

1. **The context's emit is bound per helper to the helper's plugin.** The emit operation is the context's, available from helpers during a render, and an emitted file passes through the handlers of the plugins after the emitting one (see: The spec sections governing the territory). The context has no emit, nothing records the plugins' order, every helper is bound in one place, twelve test files hand-write the context, and the two plugin modules already form a type-only cycle (see: What the build lends an emit, and what it lacks).

   **`RenderContext` gains `emit: (outputPath: string, parameters: unknown, produce: Producer) => void`, with `Producer = (context: ProducerContext) => Promise<string | Uint8Array>` and `EmittedFile { pluginName: string; sourcePath: string; outputPath: string; parametersHash: string; produce: Producer }` declared in `src/plugins/bind-render-context.ts`. `ProducerContext` is `{ readOutput: (outputPath: string) => Buffer | undefined }`, declared in `src/plugins/produce-files.ts`, the module whose function makes its values, and imported as a type. `MakeRenderContext` gains a fifth parameter, `emits: EmittedFile[]`, the list the render fills. Each helper is called with a copy of the context whose `emit` is bound to the helper's plugin: it fails an `outputPath` that is not a plain path with `${sourcePath} emits ${JSON.stringify(outputPath)}, which is not a plain path under the destination.`, a `produce` that is not a function with `${sourcePath} emits ${outputPath} with a producer that is not a function.`, and parameters `serialize` from `node:v8` cannot serialize with `${sourcePath} emits ${outputPath} with parameters the build cannot serialize: ${message}`, and otherwise pushes `{ pluginName, sourcePath, outputPath, parametersHash, produce }` with the SHA-256 of the serialization. The context handed to a renderer, and the one `enterFile` makes, carry an `emit` that fails with `${sourcePath} emits ${outputPath} outside a helper, which only a helper can do.`. The plain-path check moves from `src/plugins/run-handlers.ts:50` to `src/shared/is-plain-path.ts` as `isPlainPath(path: unknown): path is string`, which both call. `Registry` gains `pluginNames: string[]`, the names in configuration order. `src/index.ts` exports `Producer` and `ProducerContext`. Every hand-written context literal gains an `emit`, a function that throws in a test that never emits. The file's existing marker covers the new checks, since it names the plugins spec whole.** The helper wrapper is the one place that knows which plugin is calling, so binding there is what lets the build attribute an emit and pick the handlers after it with no plugin naming itself. A copy per call costs an object of seven fields and keeps the renderer's context, and the partial's, unable to emit, which is the spec's rule. The parameters are hashed at emit time so a value the build cannot compare fails on the line that emitted it, attributed through the helper wrapper to the plugin and by the render to the file. Two parameter values are the same inputs when `serialize` writes them alike, so an object's keys count in their order. The path check is the handler's check, so an emitted path escaping the destination fails the same way a handler's would. The types sit where each value is made, as the structure convention places them, and `bind-render-context.ts` and `produce-files.ts` then import each other's types, a second type-only cycle of the kind the first already is. Rejected: a module-level record of the plugin whose helper is running, set around each call, which is implicit where a bound copy is read at the call site. Rejected: letting a renderer emit, attributed to its plugin, which the spec limits to helpers and no renderer has asked for. Rejected: keeping the raw parameters on the emit, which nothing reads once they are hashed. Rejected: sorting an object's keys before serializing, a canonical form the one emitting plugin has no need of. Rejected: declaring every emit type in `produce-files.ts` to avoid the cycle, which detaches `EmittedFile` from the function that makes its values.

2. **A render's emits are part of its result.** A render is reused while every input it observed stands, a reused render does not run its helpers, and the record maps keep deleted pages while the current results do not (see: What the build lends an emit, and what it lacks). The build must still produce what a reused page emitted, or a page nothing touched would lose its derivatives on the second build of a session.

   **`RenderedBody` and `RenderedPage` gain `emits: EmittedFile[]`. `renderBody` and `renderChain` each make an empty list, hand it to every context they make, and return it. `renderPages` returns `{ pages: RenderedPage[]; emits: EmittedFile[] }`, the emits of the current build's rendered bodies followed by those of its rendered pages, read from the results `mapUnits` returns and never from the record maps. `renderChain` keeps the body's emits out of the page's record.** A record holds a unit's result, and what a render emitted is as much its result as its text, so a reused render contributes the emits it recorded. The emits come from the current results so a page removed or renamed in a session stops emitting with its render. The body's emits stay out of the chain's record because a body can rerun to the same text, which reuses the chain, with different emits. Rejected: collecting emits in a list the build holds across the render phase, which a reused render never writes to.

3. **Producers run after the chains, one unit per output path, and their files pass through the handlers after the emitting plugin.** Producers run in phase 5 with the chain renders, a producer's unit has the reads through its context as inputs, two emits of one path with the same inputs are one output and with different inputs an error naming both, and the plugins' order decides which handlers an emitted file passes through (see: The spec sections governing the territory). `runHandlers` takes a `Buffer` and the handlers to run, may rename a file, and attributes a throw by the path given, and `findVersion` answers a kind the phase versions itself with nothing (see: What the build lends an emit, and what it lacks). A derivative must be the same whichever file emitted it first.

   **A new `src/plugins/produce-files.ts`, headed with markers naming `docs/specs/plugins.md`, Emitted files, and `docs/specs/build.md`, Incremental builds, declares `ProducerContext` (see: Decision 1) and `EmittedOutput { sourcePath: string; outputPath: string; contents: Buffer | undefined; hash: string }`, where `sourcePath` is the file that emitted it, `outputPath` is the path the handlers left it at, and no contents means the bytes were dropped once written. It exports `produceFiles(source, destination, emits: EmittedFile[], handlers: RegisteredHandler[], pluginNames: string[], outputs: Output[], written: ReadonlyMap<string, string>, records: UnitRecords<EmittedOutput[]>): Promise<EmittedOutput[]>`. It sorts the emits by output path then source path with `compareStrings`, which is `compare` from `src/build/write-destination.ts:17` moved to `src/shared/compare-strings.ts` and renamed for what it compares, and groups them by output path. In a group, an emit whose plugin differs from the first's fails with `Both ${first.pluginName} and ${other.pluginName} emit ${outputPath}.`, and one whose `parametersHash` differs fails with `${sourcePath} emits ${outputPath} twice with different inputs.` when the source paths are equal and `Both ${first.sourcePath} and ${other.sourcePath} emit ${outputPath} with different inputs.` otherwise. Each group is a unit through `mapUnits`, keyed by the emitted path in `reuseUnit`, with a lookup answering `output` from the outputs' hashes by output path and `parameters` with the group's `parametersHash`. `InputKind` gains `parameters`, its doc comment counting eight kinds, and `findVersion` answers it with nothing. The run observes `('parameters', '')`, makes a `ProducerContext` whose `readOutput` takes an output path as the handler phase left it, with no leading slash and no resolution, observes `('output', outputPath)`, and returns the output's contents or the copy read from source, and calls `produce` inside a catch that rethrows through `attributePluginError` as `Producing ${outputPath}`. A result that is neither a string nor a `Uint8Array` fails with `The producer ${pluginName} gave for ${outputPath} must return text or bytes.`. The result is handed to `runHandlers(outputPath, { outputPath, contents }, after)` as it is when it is a `Buffer` and through `Buffer.from` otherwise, where `after` is every handler whose plugin's index in `pluginNames` is greater than the emitting plugin's, and each handled file becomes an `EmittedOutput` with the SHA-256 of its bytes. Whether the unit ran or was reused, every output of its result is stamped with the group's first source path before it is returned. `bindBuild` keeps `producedRecords: UnitRecords<EmittedOutput[]>` and calls `produceFiles` after `renderPages`.** Grouping before running is what makes two pages' emits of one derivative one unit, and sorting first makes a collision name its two sources the same way whichever render finished first. The parameters are an input, under the generic mechanism, so a derivative whose width list changed reruns while its path stands. Reading by output path alone, from the source root, keeps a derivative a function of its parameters and the outputs it reads and never of the emitting file's directory, which is what lets the first emit stand for every emit of the path. The handler phase's attribution, by the path handled, already names a produced file by the only name it has. A `Buffer` is passed as it is so a derivative is not copied once more on its way to the handlers. The source path is restamped on reuse so a collision names the file that emits the path now and not the one that emitted it when the unit last ran. Rejected: running a producer the moment it is emitted, which starts work during a phase whose units run in no defined order and needs a second scheduler beside `mapUnits`. Rejected: a producer context bound to the emitting file, with relative resolution, under which two files in two directories emitting one path with one relative reference would read two sources and the output would depend on which rendered first. Rejected: giving the producer `readFile` and `readBody` as well, which no producer has asked for.

4. **A produced file's bytes leave memory once written, and a file found missing is produced again.** The destination is the build's own, a file edited there by anything but the build is outside the guarantee, and the concurrency limit keeps memory bounded while hundreds of derivatives are resized (see: The spec sections governing the territory). `writeDestination` skips a planned file that is present with the hash last written, `written` is kept true to the disk across builds, and the file's marker names the build spec whole (see: What the build lends an emit, and what it lacks). The incremental-rebuilds plan kept every result's bytes because they were text, and deferred dropping a derivative's to this step with the destination file's presence made an input of the producer. `EmittedOutput` carries the path the handlers left a produced file at (see: Decision 3). A site's derivatives are its images many times over.

   **`writeDestination` takes `emitted: EmittedOutput[]` between the outputs and the pages, plans the public ones with the rest under the same uniqueness check, and writes one as a page's text is written. After an emitted output's unit finishes, written or skipped, its `contents` is set to no value. A planned emitted output with no contents that the unit does not skip fails with `${outputPath} was produced in an earlier build and is missing from the destination, so it cannot be written again.`, under the file's existing marker. Before `produceFiles` consults a group's record, it checks every output of the recorded result: one with contents is whole, and one without is whole only when `written` holds its hash under its own output path and a regular file is at that path under the destination, checked with `stat`. A record with an output that is not whole is deleted, so the unit runs again.** The record's result is the same object the write phase holds, so dropping the bytes there leaves the record with the output's path and hash, which is all a reused unit needs when the file is on disk. The check sits beside the record rather than among the observed inputs because an input is versioned when the unit runs, and at that moment the file is not written yet. It checks each output's own path because a handler after the emitting plugin may have renamed the file, and the file on disk is at the handled path. `written` is consulted as well as the disk because the entry is deleted before a write and set after, so a write that failed midway leaves a file whose bytes the build cannot vouch for. A first build holds every derivative's bytes from its production to the write phase, since producing completes before writing: the site's derivatives once, which is the peak a one-off build pays, and every build after holds only the derivatives it reproduced. A private emitted output is never written, so its bytes stay, which costs nothing a site has stated. A derivative a page stops emitting is no longer planned, so the clean pass removes it, and its record stays unconsulted, bounded as every record is. Rejected: keeping every derivative's bytes, which holds a photo site's images in memory for the session. Rejected: a record holding only the hash and the write phase rerunning a producer for a missing file, which puts a producer in the phase after the one the spec places it in. Rejected: writing a derivative as soon as it is produced, which moves part of phase 6 into phase 5 to lower a peak no site has measured. Rejected: dropping handled outputs' bytes too, which `readOutput` serves to helpers from memory and the next build's renders read again.
