# Templates

## Goal

Deliver checklist plan 3.2: template resolution and its errors, rendering the chain, variables merged from frontmatter, the built-in variables, and writing rendered pages. After this plan a site with a renderer builds its pages into finished documents, the whole-site fixture proves the build against a committed expected output, and plan 3.3 has a variable merge to put the globals layer in front of.

## Decisions

1. **Template resolution.** The spec commits to this (see: docs/specs/templates.md, Template resolution): every page renders through a chain ending at a root template. A file with no `template` key takes the nearest `_` template, searching its own directory first and then each parent up to the source root, except that a template named `_` searches strictly above its own directory. `template: <name>` takes the nearest `_<name>` the same way. The chain ends at the first template whose default search finds nothing above it. The directory a file searches from is the one it belongs to. A page whose default search finds no `_` at all, and a `template: <name>` no directory on the search path satisfies, are build errors naming the file and the template it asked for. Two templates in one directory with one name and different extensions are a build error naming both. The spec says nothing about a chain that loops.

   **`resolveChains(pages: Page[], templates: Template[]): Template[][]` in a new `src/templates/resolve-chains.ts` resolves every page's chain, nearest template first, root last, in the pages' order. It first indexes the templates by directory and name, failing when two templates share both: `Both ${first} and ${second} are the template ${name} in ${directory}.`, with `the source root` in place of an empty directory. It then walks each page's chain. A file with no directive asks for `_`, and a file with `template: <name>` asks for `_<name>`. The search visits the file's directory, then each parent up to the source root, except that a template named `_` with no directive starts at its parent directory, and ends the chain when it has no parent. A found template is the next file in the chain and the search continues from it. When nothing is found, a page fails, and so does a template with a directive, with `No template ${name} is in the directory of ${sourcePath} or above it.`. A template with no directive that finds nothing is the root, and the chain ends. A found template already in the chain, the file itself included, fails with `${sourcePath} asks for ${found}, which is already in its chain.`, and the spec's Template resolution section is amended to commit to that error.** The spec's search is a function of the templates' directories and names and each file's directory and directive, all fields the read already produced, so resolution is a function on values with every rule a value test. The index makes each step of the walk a lookup, and building it is where two templates with one name in one directory are seen together, so the duplicate rule is checked once for the whole site rather than when a search happens to reach the pair. The chain is resolved for every page before any render, so a resolution error fails the build before any page renders and before any write. Nearest-first is the order rendering walks and the order `_chain` reads, so nothing reverses it later. A `_` template's default search skipping its own directory is what keeps it from being its own parent, and no other template's name can match the `_` it asks for, so the rule needs no other case. The cycle rule is new: a template that names itself, as `blog/_post.tpl` with `template: post` does, and two templates naming each other, are chains the search would follow forever, and a build that hangs is the one failure it must never produce. Rejected: resolving lazily during rendering, which would find a resolution error only for the pages that render before it and after writes may have started. Rejected: a map from page to chain, which the pages' order already indexes. *(deviation: `resolveChains` returns `PageChain[]`, each a `page` with its `chain`, and `renderPages` takes that list. The plan's parallel arrays had rendering read `chains[index]`, which `noUncheckedIndexedAccess` types as possibly undefined, so the read needed either a guard no input reaches or a non-null assertion lint forbids. The pair carries the same order with no index read.)*

2. **The error for a page whose default search finds no `_` uses the same message as a missing `template: <name>`, with `_` as the name.** The spec has both errors name the file and the template it asked for (see: Decision 1), and a page with no directive asks for `_`. One message shape holds both, so a reader learns one. Rejected: a second message saying the site has no root template, which is true of the page's search path only, since another directory may hold a root.

3. **The render context.** The spec has the renderer turn a body and the variables into a string, synchronously or not (see: docs/specs/plugins.md, Renderers), and has the render context carry the file being rendered and the variables the file renders with, as merged, the built-ins among them, and the `_chain` view (see: docs/specs/plugins.md, Render context).

   **`RenderContext` gains `variables: Record<string, unknown>`, the merged set the file renders with, the built-ins inside it. The renderer signature stays `(body, context)`.** The variables are one thing the spec's context carries, so they travel there rather than as a third parameter, and a renderer that wants only the body ignores the context as the fixture renderer did until now. The built-ins sit inside `variables` because the spec makes them variables, and a template reads `_content` the way it reads `title`. Rejected: separate `content` and `chain` fields on the context, which would put the two built-ins a renderer must pass to the template somewhere other than the set it passes.

4. **The variables.** The spec commits to one merged set built from the globals, then each template's frontmatter from the root down, then the page's, each layer overriding the keys before it. The built-ins are added and collide with nothing, and only frontmatter flows between files (see: docs/specs/templates.md, Variables). `_url` is the page's URL in every file of the chain, `_content` is the output of the file directly below and exists only in templates, and `_chain` is the frontmatter of each file below, nearest first, and is empty in a page (see: docs/specs/templates.md, Built-in variables). The globals layer is plan 3.3's.

   **The variables for each file in a chain are built from one merged set: each template's frontmatter from the root down to the nearest, then the page's frontmatter, each layer's keys overriding the layers before it, then `_url` set to the page's URL. The page renders with that set and `_chain` as an empty list. A template at position `i` of the nearest-first chain renders with that set, `_content` set to the output of the file below it, and `_chain` holding the frontmatter of the templates at positions `i - 1` down to `0` and then the page's, in that order. Each `_chain` entry is the file's `frontmatter` value, which holds the keys without the `template` directive, and the spec's `as written` wording for `_chain` is amended to say the directive is left out.** The merge is the spec's order restated on the chain the resolution produced (see: Decision 1), and the same set reaches every file because the spec has the root read what a section template set. `_chain` is built per file because the spec has it stop below the file rendering. The entries are the stored frontmatter because the directive is not a variable and the read already separates it, so a template reading `_chain[0].layout` gets what the file below declared and nothing the build uses for its own purposes. The globals layer goes in front of the templates' layers in this merge when plan 3.3 adds it. Rejected: keeping the directive in `_chain` entries, which would make `_chain[0].template` a second way to read what the build already resolved.

5. **The renderer on the page value.** The principle has a page be plain data holding its output path, its frontmatter, its body, the renderer for that body, and the directory it belongs to (see: docs/conventions/principles.md, A page is not its source file). The renderer is the one field the value lacks today.

   **`PageFile` and `TemplateFile` gain `render: Renderer`, the renderer registered for the file's extension, set at classification. `classifySource(sourcePaths, renderers: ReadonlyMap<string, { render: Renderer }>)` takes the registry's renderer map in place of the extension set, and its keys are the extensions that make a page.** Classification is where the extension is matched against the registry, so the renderer is known there and the value is complete after the read as the principle asks. The parameter's element type is what the registry entry satisfies, so the build passes the map it already holds, and the plugin name the entry also carries is left for checklist step 6, which attributes errors. Rendering then calls the file's own `render`, so the renderer for a file is a field read rather than a lookup that could miss, and the miss needs no unreachable branch. Rejected: looking the renderer up by extension at render time, which is the lookup classification already did, and whose failure branch no test can reach.

6. **Rendering.** The spec has the page's body render first with the renderer for its extension, its output become `_content` for its parent, and so on up to the root, each file rendering with the renderer for its own extension (see: docs/specs/templates.md, Rendering the chain). The build's phase 4 renders every page's body, phase 5 renders every page's template chain, phase 6 writes the destination, and each phase completes before the next begins (see: docs/specs/build.md, Order of work).

   **`renderPages(pages: Page[], chains: Template[][]): Promise<RenderedPage[]>` in a new `src/templates/render-pages.ts` renders every page in two passes through `runUnits`, and returns a `RenderedPage`, an `outputPath` and `contents`, per page in the pages' order. The first pass renders every page's body, each unit calling the page's `render` with its body and a context of its `sourcePath` and its variables. The second pass renders every page's chain, each unit calling each template's `render` in turn from the nearest to the root, with the template's body and a context of the template's `sourcePath` and its variables. The root's output is the page's contents. Each unit writes its result into the slot at its page's index.** Every body renders before any chain because checklist step 4 lets a template read another page's rendered body, and a chain rendering inside the body pass would read a body that may not exist yet. Two passes now is the shape checklist step 4 inherits, and the boundary costs one more call to the runner. The chain is one unit because the spec's dependency rule counts rendering one page as one unit and its templates render in sequence, each needing the output of the one below. Slots by index are what `readSite` does to keep the output free of scheduling, and the same holds here. The module carries the templates spec's marker for the merge and the chain, and its exported function carries the build spec's Order of work marker for the two passes. Rejected: one unit per page rendering body and chain together, which contradicts the committed phase order. *(deviation: the signature is `renderPages(pageChains: PageChain[])`, per the deviation under Decision 1. At the gate the user ruled against the passes updating a record in place, so `mapUnits` in `src/build/map-units.ts` runs units through `runUnits` and returns their results in the items' order, and each pass is a pure map: a page with its chain to its merged variables and rendered body, then that to the rendered page.)* Rejected: a module per spec section, which splits a merge, a chain walk, and two passes of a few lines each across four files.

7. **Expected output.** The testing convention has no test write a fixture, and has a build's output go to a temporary copy (see: docs/conventions/testing.md, Fixtures). The Vitest installed is 5.0.2, read from `node_modules/vitest/package.json`. Its `expect` carries `toMatchFileSnapshot(filepath)`, declared at `node_modules/vitest/dist/chunks/task-utils.d.BZm4GSQD.d.ts:78`, which compares a string against a file on disk and holds raw contents rather than a serialized snapshot. Its update mode, resolved at `node_modules/vitest/dist/chunks/index.C-uw7tH9.js:14498`, is `all` under `--update`, `none` when `std-env` reports CI, and `new` otherwise. Under `new` a missing file is written and a differing one fails. Under `none` a missing file fails.

   **The templated fixture's build is compared against a committed `test/fixtures/templated/expected/` directory. The test asserts that the list of files under the build equals the list under `expected/`, then asserts each built file's contents with `toMatchFileSnapshot` against the file of the same path under `expected/`. `vitest --update` rewrites the expected files. A test that builds a site with pages compares its output this way. The testing convention records the pattern and makes the update switch the one way a fixture is written.** A page's rendered document is what the build is for, and a reviewer reads the expected file as a site author reads a built page, which an assertion on a string inside a test does not give. The file-snapshot matcher is Vitest's own way to hold a string to a file on disk, so the update switch is the runner's, and a mismatch reports as a diff. The list check comes first because the matcher sees only the files the build produced, so a page the build stopped producing would otherwise leave its expected file behind unnoticed. The expected directory sits inside the fixture because it is part of the fixture's case, and the build writes to a copy of the fixture while the matcher reads the original, so the comparison holds the copy's output to the committed files. Rejected: a helper with its own environment switch that replaces `expected/` wholesale, which adds a switch the runner has and a helper the matcher already is. Rejected: inline snapshots, which put a document inside a test where nobody reads it as a document. Rejected: asserting each built file against a string in the test, which is the same content with less to look at.

8. **Writing rendered pages.** The spec writes a page to its output path, and has two sources planning one path fail naming both (see: docs/specs/source-tree.md, Output paths) (see: docs/specs/source-tree.md, Output paths are unique). The planner already runs that check over pages and static files together. The structure convention's worked example for where a type is declared is the planner's `Output`, imported by the writer (see: docs/conventions/structure.md, Types).

   **`Output` in `src/source-tree/plan-outputs.ts` is renamed `Copy`, and `writeDestination(source, destination, copies: Copy[], pages: RenderedPage[])` takes the two kinds of output as two parameters, each imported from the module that produces it. It cleans the destination against both lists' paths, copies each `Copy`, and writes each `RenderedPage` with `writeFile`. The convention's example is reworded for the new name.** The writer already cleans the destination against the planned paths and creates each output's directory, and a rendered page needs both, so the writer takes it as one more kind of output rather than a second writer repeating the cleaning. Two parameters keep each type declared where its values are made, which is the convention's rule and its own example. The planner keeps its uniqueness check as it is, so the rendered pages arrive at the writer checked. Rejected: a union of the two types declared in the writer, which declares a type in a module that produces neither value. Rejected: a planner that returns page entries for the writer to fill with contents later, which threads a mutable slot through the pipeline. Rejected: a second write function for pages, which cleans nothing and would leave the destination's guarantee split across two functions. *(deviation: at the gate the user ruled that the uniqueness check belongs where every output is known, which the planner never is once handlers and emits exist, so `src/source-tree/plan-outputs.ts` and `Copy` were deleted. `writeDestination(source, destination, staticFiles: StaticFile[], pages: RenderedPage[])` skips private static files, checks every output path for uniqueness in sorted order before touching the destination, and then cleans and writes. `RenderedPage` gained `sourcePath` so the error names both sources. The convention's example cites `RenderedPage`.)*

9. **`build` in `src/build/build.ts` runs, in order: register plugins, walk, classify with the registry's renderers, plan outputs, read the site, resolve chains, render pages, write the copies and the rendered pages.** Registration, the walk, classification, and the uniqueness check stay where plan 3.1 put them, so every setup and classification error still fails before any read. The read is the build spec's first phase, resolution follows it because it needs every template's directive, and rendering follows resolution. Writing last is phase 6 (see: Decision 6). Rejected: resolving chains inside the read, which would make a function on the disk carry a function on values. *(deviation: at the gate the user ruled that `readSite` takes the page files and the template files alone and returns a `Site` of pages and templates, since the static files passed through it unread. The build destructures the classification and hands the static files to the writer itself.)*

10. **The fixture renderer substitutes every `{{ path }}` in the body, where `path` is one or more identifiers joined by dots, with the value at that path in the context's variables: a string as it is, an absent value as the empty string, and any other value as its JSON. The templated fixture gains `blog/_.tpl` with frontmatter `section: Blog`, and every template and page gets a body that reads the merged set and the built-ins, so the expected output proves resolution, the merge, `_content`, `_chain`, and `_url` from one build.** The renderer is what the whole-site build proves the pipeline through, and a substitution that reads a path is the least a renderer can do and still show that each variable reached the file it should. JSON for non-strings is deterministic on every machine, where `String(date)` carries the machine's time zone, and it shows a date's type and `_chain`'s whole shape in the output. The added template gives `blog/hello.tpl` a chain three templates deep, `blog/_post.tpl` then `blog/_.tpl` then `_.tpl`, which is the spec's own example of a `_` template found below the root and searched strictly above (see: Decision 1). Rejected: a full template syntax, when every rule about rendering is a value test and the fixture proves the integration alone.

11. **Value builders.** The testing convention puts a helper two test files need under `test/helpers/`, as a module exporting that one function and named after it, never copied into each file (see: docs/conventions/testing.md, Helpers). `test/helpers/` holds `assert-absent.ts`, `fixture-path.ts`, and `test.ts` today.

    **Two helpers under `test/helpers/` build the page and template values the value tests take: `makePage(fields: Partial<Page> & { sourcePath: string }): Page` in `make-page.ts` and `makeTemplate(fields: Partial<Template> & { sourcePath: string }): Template` in `make-template.ts`. Each fills every other field with a default: the root directory, the extension `tpl`, one shared renderer that returns the body, empty frontmatter, no directive, and an empty body, and for a page the output path `index.html` and the URL `/`. A caller overrides the fields its case turns on.** The resolution tests and the rendering tests both build pages and templates by the dozen, and the planner's tests already build the classification's half of the same values, so the builders are the copy the helper rule stops. The full `Page` satisfies `PageFile`, so the planner's tests take the same builders. Rejected: one builder for both, which would take a discriminator to pick the fields a template has and a page lacks.

12. **Delivery is a single PR.** The change is two new modules with their tests, edits to four modules and their tests, the plugin type, the fixture with its expected output, and the doc edits, which one review holds and which plan 3.1's PR matched in size. No phase ships on its own: resolution without rendering proves nothing a site can see, and rendering without the writer change writes nothing.
